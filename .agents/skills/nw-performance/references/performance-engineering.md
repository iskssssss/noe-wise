# 性能工程

本文件用于 灵知 的性能调查、基准设计、优化和性能回归证据。产品端到端延迟、容量与可用性阈值归[平台非功能需求](../../../../docs/01-产品与需求/03-非功能需求.md#3-性能与容量)，Runtime 分段指标与 SLO 边界归对应 Harness/NFR 及 Gate 0 基线；验证范围与证据复用仍由[评审与验证规范](../../nw-verification/references/candidate-driven-delivery.md)决定。本文件只说明如何取得可信测量，不臆造 SLO、要求所有改动跑基准或新建统一性能 Gate。

## 确定用户路径

仅在用户明确要求调查/优化性能、实现现有性能验收，或当前变化已触及已定义性能预算时加载本文件。先写清用户可观察操作、完成条件、工作量范围、资源约束和停止条件；组件变快不等于完整路径变快，外部模型或网络耗时若被排除须明确说明。尚无批准阈值时可先建立固定场景的基线、定位热点并证明相对改善，但不能宣称满足 SLO；工作量定义、验收幅度或行为代价会改变任务目标时再请求事实所有者决定。

Runtime 场景沿真实组合路径并按 [Harness 01 NFR-2](../../../../harness-design/01-Agent-Workflow协作引擎-MVP需求分析.md#5-非功能需求)与 [Harness 06 Gate 0](../../../../harness-design/06-MVP-0技术底座实施方案.md#8-测试与验收矩阵)已经定义的分段及基线测量，不在本文件复制指标集合。宿主侧按实际需求测 SSE 或长会话 UI 的可观察响应，不用内核局部数字代替浏览器体验。

工作量分别控制事件数、字节数、对话轮次、Action/Observation 数、Inbox/Outbox 积压、活动 Execution、重建记录、可见 DOM 节点和并发度；这些维度不可互相替代。所选典型或尾部场景须来自已确认需求或匿名聚合特征，不能复制真实 prompt、输出、身份、凭据或可识别业务数据到 fixture 和报告。

## 建立可复现基线

沿用任务摘要、基准报告或测试产物，只记录当前比较或验收所需信息，不适用项直接省略。下表作为参考，不作为逐项填写模板；影响结果的配置保持可比，涉及日志开销时记录日志级别等相关条件：

| 字段 | 当前场景需说明 |
| :--- | :--- |
| 用户操作 | 精确入口、生产调用链和外部可观察完成点 |
| 工作量 | 固定维度、构造常量或 seed，以及代表典型/尾部场景的依据 |
| 环境 | revision、JDK/Node/浏览器、OS、依赖与资源限制；外部边界如何替代 |
| 计时 | setup 是否计入、起止点、冷/热状态、排除的网络或模型成本 |
| 资源 | 假设涉及资源压力时的 CPU、分配/峰值或保留内存口径，以及测量结束时有意保留的对象 |
| 判定 | 全部原始样本、采用的统计量、现有阈值来源或仅作对比的说明 |
| 行为 | 必须保持的不变量、功能验证和允许的可见差异 |

纯 JVM 热路径在确认微观成本确实支配用户路径时可用 JMH 或等价窄基准；数据库、事务、Inbox/Outbox 与重建路径使用 Testcontainers、Micrometer 或现有组合入口；浏览器响应使用 Playwright 的真实输入和可观察 UI 更新。仓库当前没有统一基准框架时，先选择能回答当前问题的最小工具，不为单个场景预建通用平台，也不为了测量新增生产 API 或复制生产算法。

冷态使用新实例/进程和私有数据根；热态明确保留的缓存及失效键。进行 before/after 对照时使用同一输入、完成条件、可达输出和相近运行环境，避免 fixture 暗中预热、只解析不保留结果，或让候选与基线承受不同后台负载。报告全部样本及判定统计量，不挑最快一次；基准过程与其他 CPU/数据库重任务串行或隔离其实际竞争资源。

性能预算是否属于必要 Gate 由需求事实源与评审与验证规范决定；已有必要 Gate 缺少 runner 校准或可信证据时，报告缺口并阻止对应完成声明，不能由本专题自行降格。设计新的受控 benchmark lane 回归预算时先校准拥有者、工作量、runner 与噪声范围，校准只用于该 lane 的噪声和相对回归判定；产品或 Harness 的外部可观察绝对 SLO 不得按机器速度自行缩放，事件数、字节数、比例和内存上限也不能借校准改变。本地浏览器诊断没有 CI 浏览器基线时只报告测量，不把手工观察冒充稳定门禁。

## 从证据到优化

用 profile、分阶段计时、查询/调用计数、allocation 或保留对象分析定位热点，明确待验证原因和必须保持的行为。纯调查在基线、热点与限制清楚时即可停止；实施优化先建立或复用可信基线，相关修改按模块批次完成后集中进行同输入 before/after 测量。需要区分多个原因时才拆分最小对照实验；没有独立证据时只声明该批修改的整体收益。先测最接近变化的可观察端点，验收或影响链需要时再增加端到端路径。

可以调查但不得预设结论的方向包括：重复解析/复制/校验、逐条数据库或远程调用、无界中间集合、错误数据结构、过宽订阅/重渲染、无失效或无上限缓存，以及把可延后的非活动视图工作放在首个可用结果之前。任何缓存或 singleflight 都须解释失效、容量、独立 waiter 取消和释放所有权；异步或延后工作不能越过持久提交、发布、校验或 writable readiness 等正确性边界。

性能证据不替代功能证据。按场景保持顺序、幂等、租户隔离、持久化/回放、错误、取消、并发、释放、模型可见内容和 UI 可访问行为。更快但导致无界保留、截断历史、遗漏 Tool/Observation、跳过 Policy/校验或改变生命周期的方案不是优化。

为新增或收紧的回归预算提供负控：原实现或受控重新引入目标成本时应失败，优化后在同一环境通过。负控不要求把旧代码提交进仓库；可用临时切换、可控 workload 或计数断言证明 Gate 能捕获目标回归。若收益在端到端消失、典型负载明显退化、噪声高于差异、复杂度大于收益，或取消/内存/持久语义无法说明并验证，则拒绝该优化并停止扩张范围。

## 交付证据

性能或效率改善须有对应实测支撑；未测量时只说明结构变化与预期，不宣称实际耗时、吞吐或资源使用已改善。

按任务性质报告证据：调查保留场景、工作量、基线/热点、实际命令、环境与排除项；实施优化增加可比 before/after 和受影响行为回归；新增或收紧回归预算时再增加负控；资源假设存在时说明对应 CPU 或内存口径。区分历史数字、本次本地测量和 CI 证据；场景需要长期取舍时才按[Note 治理规范](../../nw-docs/references/notes-governance.md)记录，基准实现与场景阈值留在其代码或需求所有者处。
