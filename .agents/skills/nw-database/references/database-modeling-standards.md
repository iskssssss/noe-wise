# 数据库模型与字段设计规范

本文定义 灵知 在 PostgreSQL 16 上的通用数据建模、字段和字段更新要求，属于[工程规范](../../nw-engineering/references/engineering-standards.md)的专题正文。适用于新模型设计及任务范围内的模型、接口改造；宿主领域关系归[数据模型设计](../../../../docs/02-架构与设计/03-数据模型设计.md)，Runtime 对象、状态、精度和恢复不变量归 [Harness 03](../../../../harness-design/03-核心对象模型与状态机.md)，事务边界归 [Harness 06](../../../../harness-design/06-MVP-0技术底座实施方案.md#6-一致性与并发规则)。

本文表达已批准的目标规范，不证明所有存量实现已经符合。现有宿主字段契约的待统一范围见[未实现主题](../../../../docs/02-架构与设计/11-未实现功能清单.md#21-宿主数据库模型与字段契约统一)；代码、schema 和接口按明确模块实施，不因规范发布自动操作现有数据库。

## 1. 规则层级与外部依据

在项目最高原则及授权边界内，字段规则按“当前已批准的领域契约 → 本通用规范 → 字段类别默认值”适用。领域差异必须有业务含义或协议依据；旧字段类型、旧接口行为或历史数据不自动构成领域例外。尚未明确的领域语义先在所属契约中确定，不通过临时默认值、截断或类型转换掩盖。

| 参考来源 | 采用的原则 | 项目处理 |
|---|---|---|
| [PostgreSQL 字符类型](https://www.postgresql.org/docs/16/datatype-character.html)与[约束](https://www.postgresql.org/docs/16/ddl-constraints.html) | 按类型语义存储，以数据库约束保护完整性 | 使用 `boolean`、范围 `CHECK` 和业务长度限制；`varchar(n)` 不比 `text` 天然更快，`char(n)` 具有空格填充语义 |
| [Google AIP-140](https://google.aip.dev/140) | 同概念同名、不同概念不同名，字段含义清晰 | 统一词汇和接口映射；保留 `created_at` 等项目命名，布尔字段不强制统一添加 `is_` |
| [RFC 8259 §6](https://www.rfc-editor.org/rfc/rfc8259.html#section-6)与 [RFC 7396 §2](https://www.rfc-editor.org/rfc/rfc7396.html#section-2) | 明确数值互操作范围，区分字段缺失与清除 | 宿主 ID 使用字符串，更新显式识别字段存在性；显式区分字段缺失与清除，不把普通更新接口声明为完整 Merge Patch 协议 |

外部资料提供技术依据；字段长度档位、命名和公共字段组合是本项目的设计选择，外部规约的其他条款不自动成为项目要求。

## 2. 模型归属与身份

每张表明确所属领域、权威写入方、数据性质、唯一性范围，以及正常保留和删除条件。同一业务事实只有一个权威来源；业务对象、发布版本、事实账本、执行状态、可靠投递记录和查询投影按各自职责建模，不建立全局模型容器或强制统一的 `BaseEntity`。

- 业务资源保存稳定身份；编辑和发布不产生新的资源身份。业务键与主键分开，例如 `agent_key` 的唯一性由租户和业务键共同限定。
- 发布版本保存不可变内容；发布追加完整快照并原子推进当前指针。新执行按领域受理边界解析当前发布，在途执行和恢复继续使用精确冻结版本。
- 事实账本按契约追加，纠错追加更正事实；处理状态与不可变正文分开。查询投影和缓存明确来源、进度和重建方式，不成为另一套可独立修改的权威。
- 纯关系表、幂等记录和内容寻址表可以使用复合主键；有独立状态和生命周期的关系才建为独立实体，不为形式统一增加雪花 ID。
- 表和字段使用小写 `snake_case`；业务对象名使用含义明确的复数名，不添加无含义的 `t_`、`tb_`。主键、唯一约束、外键、检查约束和索引显式命名；表、字段、约束和索引有准确注释。

### 2.1 SDK 与平台存储命名空间

SDK 自有表统一使用 `agent_runtime_` 前缀，PostgreSQL 与 SQLite 按同一 Runtime 所有权命名；平台业务表统一使用 `nw_` 加稳定业务对象名或必要领域名。命名空间表示数据与迁移的归属，不改变领域写权，也不允许 SDK 依赖平台业务表。约束、索引、序列、函数、策略和 trigger 按其实际所属对象命名，不能只改表名而留下动态 SQL 或关联对象引用。Flyway schema history 属于迁移元数据，保留各自迁移器的名称，不作为业务表强加前缀；完整目标映射、历史对象与元数据例外见[名称清单](../../../../tools/database/table_names.json)，清单本身不证明迁移和消费者已验收。

初始化与迁移链按目标模型同步；重写历史链仅用于新建或另行明确授权重建的环境，不能用于直接升级既有数据库，也不通过修改 checksum、静默 baseline 或旧名视图伪装升级。数据操作授权与执行要求见[数据库与迁移](../../nw-engineering/references/engineering-standards.md#数据库与迁移)，实际初始化入口与环境前提见[开发与部署指南](../../../../docs/04-指南与运维/01-开发与部署指南.md#31-sdk-数据库初始化)。

## 3. 字段定义与命名

### 3.1 完整定义

字段的存储类型、精度、空值、默认值与约束由 DDL 和类型化校验表达；对外表示归 OpenAPI，非直观的业务含义、单位、写入权限和可变性在所属契约用中文补充。只同步实际受影响的表示，不要求每个字段在 DDL 注释、代码注释、OpenAPI 和字段字典重复填写同一清单；来源之间不得冲突。

注释解释非直观语义。例如：`max_total_tokens` 表示“Agent 总 Token 预算覆盖；NULL 表示继承；非空必须大于 0；新 Run 受理时冻结”，不能仅写“最大 Token 数”而遗漏继承和生效时点。

### 3.2 命名词汇

| 类别 | 默认命名 | 约束 |
|---|---|---|
| 实体身份 | `id`、`agent_id`、`tenant_id` | 引用字段与目标身份保持同类型 |
| 稳定业务键 | `agent_key`、`capability_key` | 与主键区分，明确唯一性范围 |
| 外部标识 | `external_user_id`、`external_ref` | 保留外部编码，不冒充内部主键 |
| 显示文本 | `name`、`title`、`description` | 名称默认不要求唯一，业务键承担稳定寻址 |
| 布尔属性 | `enabled`、`initialized`、`has_draft_changes` | 表达状态，避免 `flag`、`enable` 和双重否定 |
| 生命周期状态 | `status`，多维度使用 `delivery_status` 等限定名 | 每个状态字段只表达一个维度 |
| 时间点 | `created_at`、`published_at`、`expires_at` | 与日期、持续时间区分 |
| 纯日期 | `billing_date`、`effective_date` | 不保存伪造的午夜时刻 |
| 数量与单位 | `retry_count`、`size_bytes`、`timeout_ms`、`max_wall_time_seconds` | 名称或契约明确单位 |
| 并发与版本 | `lock_version`、`draft_revision`、`published_revision`、`schema_version` | 分别表示写入竞争、草稿修订、发布修订和格式版本，不混用 |

数据库字段与 JSON API 默认使用 `snake_case`，Java 属性使用 `camelCase`。既有名称语义清楚时可以作为该概念的统一名称；同一概念不新增别名，避免无明确职责的 `data`、`value`、`flag` 等字段。领域固定协议编码归所属契约，不因命名规范任意改写。

## 4. 类型、长度、空值与精度

持久化与恢复必须保持公开契约规定的身份、相等性及时间和数值精度。数据库类型不能无损表示时，明确编码方式或调整获批准契约，不能临时截断、忽略字段或以恢复时的默认值补造事实。

### 4.1 字符串默认长度

以下为没有更具体领域约束时采用的项目默认值，不是行业强制标准。已有领域或外部协议明确边界时以其为准，并同步入口校验、DDL、OpenAPI 和前端约束。

| 字段类别 | 默认类型 | 使用范围 |
|---|---|---|
| 状态、短类型编码 | `varchar(32)` | `status`、主体类型 |
| 普通业务编码 | `varchar(64)` | 产品内短编码 |
| 稳定业务键 | `varchar(128)` | `agent_key`、资源键 |
| 显示名称 | `varchar(128)` | Agent、渠道、知识库名称 |
| 标题 | `varchar(256)` | 文档标题、任务标题 |
| 短摘要 | `varchar(512)` | 列表摘要、简短说明 |
| 普通描述、备注 | `varchar(2000)` | 有明确输入长度的管理文本 |
| 提示词、正文、错误详情 | `text` | 另行定义请求和存储预算 |
| 外部标识、URL、路径 | 按外部契约选择 `varchar(n)` 或 `text` | 不套用名称或业务键档位 |
| SHA-256 十六进制摘要 | `varchar(64)` 加格式检查 | 恰好 64 位小写十六进制 |

统一采用 UTF-8。“字符数”默认指 Unicode 码点数，数据库、Java 校验和前端计数必须对齐；Java/JavaScript 的 UTF-16 长度不能直接视为相同口径。需要字节限制时另外声明 UTF-8 字节预算，不将字符数、字节数或 Token 数混用。

名称和业务键可以按已定义规则去除首尾空白；提示词、正文、签名材料和外部原始标识不得统一 trim、转换大小写或替换字符。超限明确拒绝，禁止通过截断或显式类型转换满足长度约束。`text` 不代表允许无界请求，入口和存储预算仍需受控。

### 4.2 ID

宿主实体 ID 使用雪花 `bigint`，Java 使用 `Long`，API、OpenAPI、TypeScript、前端表单和路由使用十进制字符串；前端不转为 `Number` 存储或比较。该要求不自动改变普通计数和其他数值字段。雪花生成器明确 Worker ID 分配、合法范围及异常处理，多实例不能依赖相同默认 Worker ID。

Runtime 不透明文本身份、复合身份和内容摘要继续遵循独立契约，由宿主边界完成转换；外部标识不强制解析为雪花 ID。完整 ID 必须在 DTO、序列化、客户端和数据库往返后保持相等。

### 4.3 布尔、状态与数值

- 布尔使用 `boolean`，默认非空；只有明确的“继承”或“未知”语义才允许可空布尔。超过两个业务状态时使用状态字段，不堆叠相互矛盾的开关。
- 状态和类型默认使用稳定字符串及 `CHECK`，禁止保存 Java 枚举 ordinal。新宿主状态编码默认小写 `snake_case`；Runtime 和外部协议编码遵循所属契约。
- 有界次数使用 `integer`，累计量及可能较大的字节数、Token 数使用 `bigint`；非负或正数范围通过约束表达，不能用不存在的 PostgreSQL `unsigned` 类型表达。
- 金额和价格按[计费契约](../../../../docs/02-架构与设计/14-用量与账单设计.md)使用整数最小单位或 `numeric(p,s)`，Java 使用 `Long` 或 `BigDecimal`，精确小数接口使用十进制字符串；币种和计量单位明确。
- 向量、相似度等允许近似计算的数据可以使用领域要求的浮点或向量类型，不将金额规则扩大为全库禁用浮点。

`numeric(p,s)` 会对超出 scale 的输入舍入；应用必须先校验精度，或按明确的业务舍入规则处理，不把数据库自动舍入当作输入校验。业务数值拒绝不适用的 `NaN` 和无穷值，不通过默认零值掩盖缺报或未知。技术依据见 [PostgreSQL 数值类型](https://www.postgresql.org/docs/16/datatype-numeric.html)。

### 4.4 NULL、空值与默认值

- 必填字段使用 `NOT NULL`；每个可空字段说明 NULL 的唯一含义。
- 不用 `0`、`-1`、空字符串或特殊日期代替“无关联”“未发生”或“未知”。`0` 和 `false` 是有效值，不能被当作未提供。
- 默认值只表达真实业务状态。可选外键默认 NULL，继承配置的覆盖值默认 NULL；`published_at` 等业务事件时间在事件发生前为空，不默认当前时间。
- 非空、非空白和非 NULL 是不同要求，按含义分别校验。同一列不能让 NULL 同时代表“继承”和“关闭”；两种状态都存在时增加明确模式。
- PostgreSQL 的 `CHECK (value > 0)` 不拒绝 NULL，必填数值同时声明 `NOT NULL`。普通唯一约束允许的 NULL 组合必须符合业务语义；公共资源键、可空唯一字段和软删除唯一性使用明确的约束或部分唯一索引，不把 NULL 自动视为唯一值。

### 4.5 时间

普通绝对时刻使用 `timestamptz` / `Instant`，纯日期使用 `date`；自有业务 API 和业务日界遵循[全系统时间契约](../../../../docs/02-架构与设计/13-全系统时间契约.md)。`timestamptz` 保存绝对时刻，不保留输入时区名称；确需保留原始时区的业务单独存时区字段，技术依据见 [PostgreSQL 时间类型](https://www.postgresql.org/docs/16/datatype-datetime.html)。

- `occurred_at` 表示业务发生时间，`recorded_at` 或既有 `ingested_at` 表示记录时间，延迟入库时不能互相替代。
- 管理资源 `created_at` 创建后不变，`updated_at` 随成功的业务修改更新；插入默认值不会自动维护更新时间，更新 SQL 必须明确写入。
- 记录时间由数据库取样，业务事件时间由可信发生方提供；同一操作需要一致时刻时复用同一样本。数据库时间函数按语义选择，事务开始时间不能冒充实际晚到事件的发生时间。
- 持续时间明确单位；Runtime 要求纳秒级无损往返时保留专用编码，不降为微秒精度，不以宿主时间默认值重建恢复事实。

### 4.6 固定配置、动态 JSON 与原始材料

**默认采用关系型建模；除具有明确必要性外，不使用 `json`、`jsonb` 存储业务字段。** 按字段结构、关系和生命周期选择列或表，不以减少表数量为目标，也不机械地为每个嵌套对象建表。API 使用 JSON、Java 使用嵌套 DTO，不决定数据库的存储类型。

固定结构的代码类型及必要 JSON 的字段名统一维护，遵守[工程规范：固定结构与 JSON 边界](../../nw-engineering/references/engineering-standards.md#固定结构与-json-边界)。使用实体类不自动允许将整个实体序列化进 JSON 列，仍须按本节判断各字段和关系的存储归属。

| 数据性质 | 默认建模方式 | 判断依据 |
|---|---|---|
| 结构固定、归属与生命周期一致的单值属性 | 同表类型化列 | 例如 Agent 五项预算覆盖，不因 API 中属于同一对象就存为 JSON |
| 一对多明细或配置集合 | 子表 | 每项有明确字段，通过父引用、必要的唯一约束和顺序字段表达关系 |
| 多对多资源关系 | 关联表 | 用双方引用、唯一约束及必要的关系属性表达，不把资源 ID 列表塞入 JSON |
| 一对一但需要独立权限、维护或生命周期的数据 | 独立表 | 依据实际职责拆分；少量同生命周期属性保留在原表 |
| 结构固定的草稿与发布内容 | 类型化草稿列或表、不可变版本表及版本子表 | 草稿和发布的可变性分别定义；发布集合关联精确版本 |
| 结构由用户或外部协议定义、无法用稳定列与关系表合理表达的开放文档 | 论证必要性后使用 JSON | 例如用户提交的 JSON Schema 文档；名称或来源本身不构成豁免 |

身份、租户、状态、关联、版本、幂等键，以及需要独立查询、更新、关联、排序或数据库约束的固定业务字段，必须使用类型化列。固定配置不得因“便于扩展”收进 `config`、`settings`、`extra` 等通用容器；不能把本应由外键、唯一约束或 `CHECK` 保护的关系和状态全部交给 JSON 校验。

使用 JSON 必须在所属设计中说明以下内容；未明确必要性和约束时，不得新增该 JSON 字段：

1. 内容的业务含义、结构定义方，以及稳定列或关系表无法合理表达它的具体原因；“开发方便”“减少表数量”“以后可能扩展”均不足以单独构成理由。
2. 固定字段与动态内容的边界、唯一权威来源、预期读写方式，以及必须外置的身份、关系与约束。
3. 结构或协议版本、校验责任、允许值、未知字段处理和大小限制；结构演进时如何读取已有版本。
4. 可变性、保留与清理条件；用于冻结、回放或摘要时，如何保证精确版本引用与内容一致性。

“动态”“草稿”“快照”“审计载荷”“不可变”均不自动豁免上述要求。固定结构的审计事实使用类型化列；确需保留开放结构的事件内容时单独论证。关系型发布快照可以由不可变版本行及其子行共同表达，所有内容冻结和当前发布指针推进必须原子完成；执行与恢复引用精确版本，不从当前可变配置拼出历史快照。大型不可变正文的保存与引用仍遵循[存储增长规则](#73-保留与存储增长)，关系化不意味着在每条执行记录中重复复制完整正文。

确需使用 JSON 时，解析查询通常选择 `jsonb`；选用 `json` 也需说明类型语义依据。已知稳定部分在 Java 中使用明确类型，不默认退化为 `Map<String,Object>`。动态业务配置不承载凭据或绕过所属凭据管理契约。不得将业务 JSON 序列化为 `text`、`bytea`，或把固定业务模型改为无约束的通用 key/value、EAV 表来绕过本节要求。

具有明确原始字节契约的材料按原始存储处理：验签原文、精确回放正文使用原始 `bytea`，必要时另有解析投影，并明确哪份内容为权威。需要逐字节保真的材料不能仅存为 `jsonb`，因为它不保留原始空白、对象键顺序和重复键；不能从 `jsonb` 重新序列化后冒充原始字节。规范化摘要声明算法、格式版本和范围，也不为数据库存储方便把二进制转成 Base64 文本。原始材料的保真要求不能作为固定业务字段整体序列化的理由。技术依据见 [PostgreSQL JSON 类型](https://www.postgresql.org/docs/16/datatype-json.html)。

## 5. 公共字段与可信写入方

公共字段按表的职责配置，不要求所有表继承同一基础实体。

| 表的职责 | 默认配置 |
|---|---|
| 后台管理资源 | 身份、必要租户字段、创建与更新时间、创建与最后修改操作者 |
| 需要并发编辑的管理资源 | 另有明确 CAS 版本；已有 `draft_revision` 能表达时不重复增加 `lock_version` |
| 发布版本 | 资源引用、发布修订、冻结内容、发布时间与发布操作者 |
| 事实、用量、审计 | 事实身份、来源、发生或记录时间、必要操作者，不机械添加更新时间 |
| 执行状态与队列 | 所属身份、状态、版本、必要租约及领取字段 |
| 需要回收站的资源 | 按需增加 `deleted_at` 和删除操作者，不默认给所有表加软删除字段 |

管理资源支持成员、平台管理员、服务主体和系统任务混合写入时，创建和修改操作者使用 `type + id`，例如 `created_by_type`、`created_by_id` 以及对应的 `updated_by_type`、`updated_by_id`。主体类型归身份契约，ID 保持对应主体的编码和归属；不能把不同主体的同值 ID 当作同一个人。

操作者和租户来自可信执行上下文，不由请求自由指定；系统任务记录可追踪的系统身份，不使用虚构用户 `0`。创建字段不可被普通更新覆盖。操作者字段保存创建和最后修改来源，完整过程由审计记录承担；展示名称不作为身份。

## 6. 部分更新的字段语义

| 请求状态 | 行为 |
|---|---|
| 字段未出现 | 保持原值 |
| 字段出现且为 `null` | 对可空字段清空，对继承字段移除覆盖，对必填字段返回字段校验错误 |
| 字段出现且有值 | 校验并赋值，包括合法的 `0`、`false` 和空集合 |

嵌套类型化更新对象递归识别字段是否出现；数组整体替换，空数组表示清空。仅对符合 [JSON 必要性要求](#46-固定配置动态-json-与原始材料)的动态 JSON 字段，默认整体替换，不自动深度合并；该更新语义不构成使用 JSON 存储的理由。空字符串只表示真实空文本，不能清除 ID；空对象不能作为隐式“恢复全部默认值”指令。类型化嵌套空对象没有指定子字段，不能据此重置整个对象；父字段显式 NULL 的清空或继承含义仍按该字段契约判断。

DTO 必须保留字段存在性，不能用一个可空属性同时表达“未传”和“显式清空”。SQL 必须支持显式写 NULL，不能依赖 MyBatis 默认忽略空值完成更新。只读身份、归属、创建信息和发布事实不能通过通用更新绕过授权或生命周期；状态操作按所属状态机执行。

典型判定：未传 `model_config_id` 保持原配置，显式 NULL 移除模型覆盖；未传 `execution_config` 保持原预算，显式 NULL 按继承契约移除预算覆盖，`{}` 不修改其子字段。该目标不保留空字符串清除 ID、空对象重置预算的旧接口约定；实施时同步 DTO、服务、Mapper、OpenAPI、客户端和直接调用方。

## 7. 隔离、约束、并发与生命周期

### 7.1 租户与引用

机构私有数据的租户归属非空，业务唯一性包含必要租户维度。租户表启用并强制 RLS，覆盖读写检查；普通业务连接不得使用能够绕过 RLS 的角色。连接复用和后台任务正确绑定并恢复租户上下文，不从任意业务参数推导身份。

同租户对象关系优先使用包含租户的复合外键，防止合法资源 ID 被错误关联到其他租户。公共资源可以没有租户；公共和私有资源共表时，归属判别、约束、各自唯一性及读写策略必须明确，不能把所有 NULL 租户行自动视为公开。

同库、同生命周期且写入顺序允许的关系使用物理外键。跨服务引用、独立保留的清理墓碑、跨事务后续才产生的事实明确引用校验、失效和修复方式；约束匹配实际事务和写序，不提前要求尚不应存在的事实。删除约束时说明替代一致性保证并验证失败路径。

独立资源默认限制删除；只有完全依附父对象且保留周期一致的数据才使用级联。需要事务提交时检查的关系使用延迟约束，不用禁用约束解决写序问题。

### 7.2 并发、幂等与索引

事务按[工程规范](../../nw-engineering/references/engineering-standards.md#事务日志与可观测性)及所属领域契约保护状态、账本和 Outbox 的原子性。原子操作共享事务所有者的会话/连接，辅助组件不另提交。模型、HTTP、文件上传等外部工作通常在短事务外执行，以操作事实和回执衔接；Runtime 具体原子边界遵循 Harness，不另建状态机。

关键更新使用预期状态或版本条件并检查影响行数，不无条件覆盖。幂等同时校验键和请求内容：同键同内容返回既有进度或结果，同键异内容明确冲突。外部结果未知保留未知状态，不能因没有成功回执而盲目重放。

索引由实际租户过滤、关联、排序、分页和队列领取路径反推，避免重复已有主键或唯一约束索引。外键引用侧索引按连接及删除访问判断；JSON GIN、分区、冗余字段和汇总表须有查询或保留需求依据。

### 7.3 保留与存储增长

停用限制使用，归档退出日常管理，软删除提供恢复，物理删除回收数据，分别定义。需要回收站的对象明确业务键能否复用；恢复发生唯一键冲突时返回业务冲突，不覆盖已有对象。发布版本、账本和执行材料按完整引用及所属保留规则回收，终态或 ACK 不自动解除恢复引用。

执行中、等待处理或结果未知的操作，其必要恢复材料和幂等回执不得被普通 TTL 提前清除。数据库以外的文件与对象存储使用持久清理意图和可重试状态，删除失败后仍能继续收尾；生命周期和授权操作遵循[清理与保留规范](../../../../docs/04-指南与运维/11-数据清理与保留规范.md)。

大型不可变正文按所属范围保存一次，其他记录引用精确身份、格式和摘要；去重不跨越租户授权边界，回收核对完整引用。列表及高频查询只读取必要字段，避免默认加载完整快照、附件或 checkpoint。

## 8. 实施与验收

数据库访问与迁移遵循[工程规范](../../nw-engineering/references/engineering-standards.md#数据库与迁移)。变更按明确模块同步字段定义、DDL、Java 类型、OpenAPI、前端类型及直接消费者；默认档位只用于没有更具体约束的字段，不因发布本规范机械替换所有历史字段。历史迁移可按目标模型改写或合并，不新增历史兼容义务；现有数据库转换、重建和清理需要明确环境、范围、授权及恢复方式。

按[验证规范](../../nw-verification/references/candidate-driven-delivery.md#测试路由)选择本次实际变化涉及的场景，不要求每个字段改动执行全部检查。

| 变化 | 代表性验收 |
|---|---|
| 关系建模与 JSON 例外 | 固定结构有明确代码类型，固定属性用列、明细与关系用表；必要 JSON 的结构字段名有统一定义，并具备版本、校验、大小和生命周期约束；固定快照的版本与子项不可原地修改，恢复不读取当前配置；禁止序列化或通用 key/value 绕过 |
| 类型与边界 | 长度达限和超限、中文及 emoji、空白、数值上下界和精度溢出；大整数 ID 全链路往返 |
| 部分更新 | 未传、NULL、空字符串、空对象、空数组、`0`、`false` 分别判定；必填字段不能清空 |
| 来源与可变性 | 租户及操作者不能伪造，创建字段不能被普通更新覆盖，发布正文不可原地修改 |
| 约束与并发 | 可空唯一键、软删除恢复冲突、跨租户关联、CAS 竞争及同键异内容冲突；RLS 使用实际受限角色验证 |
| 时间与原始材料 | 跨时区往返、延迟入库、Runtime 精确时间及原始字节和摘要一致性 |
| schema 与生命周期 | 隔离 PostgreSQL 16 环境的完整迁移链、引用保护、清理重试及受影响高频查询计划 |

纯规范修改检查格式、链接、规则一致性及代表性场景的通过/拒绝条件，不以文档检查冒充数据库、接口或性能验收。
