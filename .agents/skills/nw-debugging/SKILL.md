# 系统排障

适用于故障、构建失败、异常结果及跨组件问题的定位。调查和修改范围遵循[开发流程](../nw-workflow/references/development-workflow.md#自主执行边界)，修复与验收遵循[评审与验证规范](../nw-verification/references/candidate-driven-delivery.md#测试路由)。测试资源争用、时钟和异步清理的专门方法见[测试可靠性](../nw-test-reliability/references/test-reliability.md)，性能测量见[性能工程](../nw-performance/references/performance-engineering.md)。

## 从现象定位边界

1. 保存原始错误、触发输入、预期与实际行为、相关版本和运行条件；先读完整的相关错误与调用链，区分实现、夹具、环境和无关旧失败。已有可信复现与报告直接复用。
2. 核对真实入口、最近相关变更及生效配置。能安全复现时使用最小相关拓扑；不能稳定复现时，先收集能区分假设的证据，不把猜测当成根因。
3. 多组件问题沿实际调用、数据、状态和配置传播检查各边界的输入与输出，定位首次偏离契约的位置，再深入对应组件。使用现有日志、回执、持久事实和观测；证据不足且授权允许修改时才补最小诊断，不记录凭据或完整敏感载荷。
4. 对照相同契约下的正常路径，确认输入、身份与范围、版本、配置和装配差异；历史实现只能作为线索，不能覆盖当前契约。沿错误值或状态的来源追溯到产生它的边界。

例如检索最终为空时，依次核对检索是否执行、候选、分数与过滤、版本范围、排除、证据预算和实际交付；前端未展示时，核对生成、持久化或发送、接收、状态筛选和渲染。按真实链路选取相关环节，不从最终症状直接归因于 Embedding、网络或 UI。

## 验证假设与修复

在已有摘要中写清“现有证据为何支持该原因，以及什么观察会推翻它”。每个诊断实验只改变能区分当前假设的必要变量，并定义预期观察；有新证据再调整假设，不在未解释的失败上叠加猜测性修补。单一变量约束用于诊断实验，生产修复仍按模块集中完成相关实现、测试和配置。

根因成立后修复产生错误的边界，并核对同一业务决定的其他直接入口与消费者，集中修正已确认的同类问题，避免逐入口重复发现；调查只沿实际调用与数据传播扩大，不转为无关全仓审计。恢复当前目标行为，不增加历史兼容或无需求的通用兜底。修复前失败证据、修复后回归和验证范围统一按[测试路由](../nw-verification/references/candidate-driven-delivery.md#测试路由)执行，报告区分根因证据、已修复范围和未验证部分。

紧急止损可在授权范围内先行，分别记录止损依据、影响与待查原因；恢复服务或单次重试通过不证明根因已解决。无法安全复现时使用已有事故证据及受控替代检查，并明确仍缺的证据，不通过在真实环境重放未知副作用来补证据。

## 疑难问题升级

多轮尝试不再产生能区分原因的证据时，停止重复修补，整理原始事实、已排除假设和下一项最小检查。需要独立视角且已有委派授权时，再交给合适的协助者；不固定失败次数、模型、人数或会话形式。用户指定的模型与预算按该任务执行。

交接包括最小复现输入、实际证据、尝试结果、剩余假设、资源状态和权限；按[协作规则](../nw-coordination/SKILL.md)避免原负责人重复执行。更换负责人不代替原验收，不放宽阈值或重放 UNKNOWN；外部阻塞和正常等待不自动触发升级。

## 继续与停止条件

- 无相关输入变化或新诊断，不重复同一失败命令；确有可验证瞬态变化时才做有边界的重试。外部调用或派发结果未知时先核对原执行事实，重试须符合所属契约。
- 修复不断暴露不同位置的共享状态、耦合或互相矛盾的假设时，重新核对架构与契约；依据证据决定扩大调查，不按固定失败次数推定架构错误。
- 环境阻塞、不可验证的外部状态或关键语义未决时，说明已知事实、缺失证据与下一步，只暂停受影响部分；必要证据仍缺失时不声明该范围已修复。
