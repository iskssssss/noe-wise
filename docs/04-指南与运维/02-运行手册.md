# 灵知 运行手册
> **范围**：生产与预发的健康检查、发布回滚及常见运行故障处理。部署边界和环境变量以[开发与部署指南](01-开发与部署指南.md)为准。
> Agent Runtime 数据与发布恢复约束见 [Harness 06 §7](../../harness-design/06-MVP-0技术底座实施方案.md#7-架构一致性与发布门禁)，操作授权见[开发流程规范](../../.agents/skills/nw-workflow/references/development-workflow.md#阶段交付与授权)。

## 1. 事件处理原则

1. 先记录告警时间、版本、命名空间和影响租户；不要在事故期间直接修改生产
   `values.yaml` 或手工替换密钥。
2. 使用只读健康检查确认影响范围，再执行最小且可回退的缓解动作。
3. 每次发布和故障处理保存用于复核的版本、执行结果、监控链接和必要时间线；日志、异常与敏感载荷的脱敏按 [工程规范](../../.agents/skills/nw-engineering/references/engineering-standards.md#事务日志与可观测性)。

## 2. 健康检查

机构后端由 Ingress 转发 `/health`、`/health/live`、`/health/ready`、`/health/deps`；平台服务使用 `/actuator/health`。`/metrics` 仅供受控采集网络访问。

```bash
kubectl -n skillforge get pods,svc,ingress
curl -fsS https://<institution-host>/health/live
curl -fsS https://<institution-host>/health/ready
curl -fsS https://<institution-host>/health/deps
curl -fsS https://<platform-host>/actuator/health
```

- `/health/live` 失败：检查 backend Pod 事件、容器日志和最近镜像变更；避免以
  重启掩盖持续崩溃。
- `/health/ready` 返回 503：根据响应中的 PostgreSQL 或 Redis 条目处理依赖；在依赖恢复前不要扩容机构 API。
- `/metrics` 应由 Prometheus 在集群内部抓取；确认 `skillforge_up` 和目标
  `up` 指标后再关闭告警。

## 3. 发布与回滚

发布前执行 [发布检查清单](../../deploy/runbook/checklist-release.md)，并记录 Helm
release 的当前 revision：

```bash
helm -n skillforge history skillforge
helm -n skillforge status skillforge
```

若新版本导致健康检查、关键 API 或错误率恶化，先暂停流量提升并确认该 revision 与数据库 schema、数据转换是否仍然匹配。只有不包含不兼容迁移时，才可直接回滚 Helm revision：

```bash
helm -n skillforge rollback skillforge <revision> --wait --timeout 5m
kubectl -n skillforge rollout status deployment/skillforge-backend --timeout=5m
kubectl -n skillforge rollout status deployment/skillforge-frontend --timeout=5m
```

回滚后复查 `/health/ready`、错误率、Inbox/Outbox、Execution Ledger、活动 Pending 和关键用户路径。存在不兼容迁移时，按预先验证的应用 + schema + 数据快照组合恢复，不得只回滚应用。

## 4. Flyway 迁移失败

1. 立即停止后续应用 rollout，保留失败 Pod 日志和 Flyway 校验输出。
2. 确认迁移是否开始执行及其事务边界；不得盲目执行 Flyway repair 或手工 DDL。
3. 对照备份与迁移脚本评估前向修复或经审批的恢复方案；涉及数据变换时须由
   数据库 Owner 审核。
4. 在预发以生产快照演练修复，获得确认后再恢复生产发布。

```bash
kubectl -n skillforge logs deploy/skillforge-institution-service --since=30m
# Flyway 随服务启动执行；异常时检查应用日志中的 migration 校验信息
```

## 5. 密钥轮换

`SECRET_KEY` 会使既有 JWT 失效；`ENCRYPTION_KEYS` 的首项是活动 KEK，保留旧项
直到所有已加密 Connector 凭证完成重加密和验证。轮换通过受控 Secret 管理，不把
密钥写入 Git 或 Helm values。

1. 生成新密钥并在密钥管理系统中保存版本与回退窗口。
2. 将新 KEK 放在 `ENCRYPTION_KEYS` 数组首项、旧 KEK 暂保留；分批重启并验证
   新旧凭证均可解密。
3. 完成凭证重加密、抽样验证和审计后，移除旧 KEK。
4. 轮换 JWT `SECRET_KEY` 前公告会话失效，滚动发布后验证登录、刷新令牌与 API
   鉴权；仅在计划窗口内撤销旧密钥。

## 6. 后台任务积压

1. 检查 Redis 可用性、调度任务日志、任务失败率和任务执行时长。
2. 在资源和下游连接器容量允许时调整服务副本数；不要仅因积压无限制提升并发或预取。
3. 针对毒性任务，保留安全关联标识、脱敏异常、重试与副作用状态后隔离；仅按对应恢复契约重放，原始敏感载荷不复制到日志或工单。

```bash
kubectl -n skillforge get pods -l app.kubernetes.io/component=institution
kubectl -n skillforge logs deploy/skillforge-institution-service --since=30m
```

队列恢复后复查 Inbox/Outbox 积压、失败任务、活动 Pending 和执行账本，避免重复决策或重复外部副作用。

## 7. 连接器不健康

1. 通过 `/health/deps`、连接器健康检查任务和审计日志确认是否为单一租户、单一
   Connector 实例或上游服务故障。
2. 验证 DNS/TLS/网络策略、凭证有效期和上游限流；禁止在日志或工单中复制凭证。
3. 若 Connector 支持已定义的业务降级，按授权切换并明确结果语义；生产路径不以 Mock 成功代替实际调用。不支持降级时暂停相关写操作，避免错误重试造成重复写入。
4. 上游恢复后用无副作用探测和最小业务请求验证，再按授权恢复流量；是否需要复盘按 [postmortem 规则](../../.agents/skills/nw-docs/references/postmortem.md#何时写)。

## 8. 升级后的验收记录

每次事件和发布在变更记录中至少包含：版本与 Helm revision、开始/恢复时间、影响
范围、执行人、健康与队列证据、是否轮换密钥、后续行动项。
