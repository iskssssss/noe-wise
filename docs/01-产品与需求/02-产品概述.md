# 灵知 产品概述

> 本文面向产品使用者、贡献者和研发团队，是产品定位、品牌、目标用户、核心价值、成功指标和非目标的唯一事实源。用户旅程与功能要求见[产品需求文档](01-PRD.md)，技术契约见 [Harness Design](../../harness-design/README.md)。

## 1. 产品定位与品牌

灵知 是面向 B 端机构的通用智能 Agent 平台。机构将专业知识、操作工具、工作方法和业务流程配置给 Agent，通过自有渠道、独立会话端或开放平台服务最终用户。Agent 理解用户想完成什么，结合当前上下文、知识与记忆形成判断，选择受授权的能力采取行动，并交付回答、业务结果或可使用的成果。

产品中文名为 **灵知**，英文名为 **NoeWise**；中文与英文名称分别使用，不连写为一个名称。“灵”表达灵敏、灵活，“知”表达理解与认知；NoeWise 按 **noesis（认知、思维）＋wise（智慧）** 的思路构造，直接突出智能，适用于 Agent 产品及整个平台。

平台以 Agent 为用户交互和智能决策中心。Workflow 承载需要确定步骤的执行，专业 Agent 委派承载边界明确的分工，持续会话承载上下文与任务的延续，机构后台和平台后台承载配置、发布与治理。陪伴、知识服务、研究、内容生产和业务办理都是这一体系的应用场景；行业规则由机构资源和产品配置表达。

## 2. 要解决的问题与核心价值

| 用户或机构遇到的问题 | 产品价值 | 形成的结果 |
| :--- | :--- | :--- |
| 用户知道目标，却无法一次说清全部步骤和参数 | Agent 理解意图、结合已有材料判断，必要时澄清 | 从自然语言需求进入可推进的任务 |
| 专业知识分散，回答缺少依据 | 按授权范围检索知识与来源，整合证据并说明限制 | 可核查、能追溯来源的回答与研究结果 |
| 回答停留在建议，实际工作仍需人工完成 | 调用工具、执行流程、使用 Skill 指导工作 | 业务操作、计算、文件或其他成果交付 |
| 长任务等待期间无法继续交流，恢复时又需重复背景 | 让持续会话与前后台任务共存，按受控记忆延续必要事实 | 用户可继续对话、补充材料、查看进度并恢复任务 |
| 单一助手覆盖不了所有专业工作 | 主助手向获授权的专业 Agent 委派明确子任务并汇总结果 | 在同一用户体验中完成专业分工 |
| 机构无法判断 Agent 使用了哪些资源、产生哪些成本 | 版本发布、权限策略、执行投影、用量与审计共同治理 | 可配置、可检查、可维护的智能服务 |

上述价值是产品目标，具体交付范围和证据从[当前阶段](#8-当前阶段与实现依据)进入。模型、知识来源、工具和机构策略都会影响结果质量；产品通过引用、确认、失败说明与运行记录支持用户判断结果是否可用。

## 3. 目标用户

| 角色 | 目标 | 使用入口 |
| :--- | :--- | :--- |
| 最终用户 | 获得专业回答、完成任务、使用成果，并在持续会话中跟进和纠正 | 独立会话端、机构渠道或机构自有应用 |
| 机构建设者与运营人员 | 配置和发布 Agent 及能力，接入业务系统，治理会话、任务、知识、用量与风险 | 机构管理后台及获授权的开放 API |
| 平台运营方 | 提供公共模型、Agent 模板和能力资源，管理机构、资源发布、供应商用量及平台运行 | 平台运营后台 |
| 开发者 / ISV | 构建可复用 Skill、Tool、知识接入与 Workflow，并通过公开契约集成到机构应用 | 开发工具、能力包、开放平台和 Runtime SDK |

机构建设者负责将能力组合为可用服务，运营人员负责持续检查其效果与运行情况。最终用户身份与机构成员、集成调用主体分别治理；进入同一机构也不意味着具有相同资源或数据权限。

## 4. 产品能力地图

### 4.1 理解与判断

Agent 根据用户输入、对话历史、任务事实和当前可用能力理解目标，决定直接回答、检索资料、调用工具、推进流程、请求补充或委派专业工作。模型提供智能判断，运行时负责输入受理、上下文组织、策略检查和行动结果回注。

### 4.2 知识与记忆

知识提供获授权的资料与证据，记忆提供需要跨输入延续的用户和业务事实。二者按所属范围、版本与来源治理；Agent 通过受控入口按需使用，不能把全部历史或全部资料无条件装入每次请求。记忆产品增强与多源研究的范围分别见 [FR-9 与 FR-19](../../harness-design/04-后续阶段需求扩展-P1-P3.md)。

### 4.3 行动与交付

Agent 只挂载 Skill、Tool、Knowledge Source、Workflow 四类业务能力。它们共同支持从判断到结果的推进，但有不同职责：

| 对象 | 产品职责 | 使用边界 |
| :--- | :--- | :--- |
| Agent | 理解目标、选择行动、处理观察并整合结果 | 作为会话决策入口，行动受当前发布配置与授权约束 |
| Skill | 提供工作方法、指令、脚本、参考资料与资产 | 标准能力包按需加载；执行脚本仍需获授权的 Tool |
| Tool | 提供可调用的操作、计算或外部服务 | 通过明确输入契约和部署授权调用，结果进入 Agent 的观察 |
| Knowledge Source | 提供版本化、获授权的知识来源 | 经 Knowledge Runtime 查询并返回证据，由 Agent 组织回复 |
| Workflow | 按确定步骤推进业务执行，管理等待与恢复 | 由 Agent 下达执行指令，执行状态由 Workflow 所属账本维护 |
| 专业 Agent 委派 | 使用专业 Agent 自身的模型、知识与能力完成子任务 | 属于独立委派授权，不是第五种可挂载能力；主助手整合交付 |

文件、网页和其他产物由获授权的执行能力生成，经宿主发布后提供受控读取、下载或隔离预览。对话文字、执行成功和产物可交付分别核验，避免把执行中间文件或未完成结果当作正式成果。所属设计见[代码执行与产物交付](../02-架构与设计/12-代码执行沙箱与产物交付.md)。

### 4.4 持续服务与协作

Session 保持用户交互的连续性，Execution 表达各项执行的进度与结果。Workflow 等待确认或后台运行时，用户可继续交流并查询、取消或恢复目标任务；恢复需使用准确的任务身份。

首期专业协作采用主助手原生委派：主助手从冻结的授权名单中选择目标，子 Agent 使用自身已发布定义处理明确子任务，结果回到主助手。工作室可进一步收窄成员范围，结构化计划是按需采用的协作方式。子 Agent 为叶子执行者，首期不引入递归委派、对等协商或自治群体，详见 [Agent 委派专题](../../harness-design/08-Agent委派与多智能体运行时.md)。

### 4.5 机构治理与平台运营

机构控制面负责 Agent 和资源配置、草稿校验、不可变版本发布、精确挂载、渠道接入、成员权限、记忆与数据治理、任务观测和成本分析。平台控制面负责公共资源、机构与供应商管理。渠道传输、模型 Provider、Connector、Builder、Marketplace、Handoff、Trace、Usage 与 Billing 各自承担接入、生产或治理职责，不混入四类可挂载能力。

第三方应用可通过 Tenant Open Platform 维护获授权资源并代理终端用户参与会话；资源维护与会话执行使用各自受控入口。开放平台完整范围及当前缺口见[开放平台需求](../../harness-design/04-后续阶段需求扩展-P1-P3.md#fr-21-tenant-open-platformp1)与[未实现主题索引](../02-架构与设计/11-未实现功能清单.md)。

## 5. 典型应用场景

| 场景 | 用户希望得到什么 | 能力组合与边界 |
| :--- | :--- | :--- |
| 机构知识服务 | 基于制度、产品和服务资料获得可核查的回答 | Agent + Knowledge Source；只消费授权来源，证据不足时说明限制 |
| 研究与报告 | 收集资料、比较观点并形成带来源的报告 | Agent + Knowledge + Skill + Tool；多源研究按 FR-19 及对应实施范围验收 |
| 文件与产物交付 | 从材料得到文档、表格、演示文稿或网页，并继续修订 | Agent + 相应 Skill/Tool + 受控产物交付；运行环境、格式和权限依已启用能力确定 |
| 业务办理 | 查询、提交或推进业务，并在关键步骤确认 | Agent + Tool/Workflow；外部业务权限、确认和结果核验按所属契约执行 |
| 持续陪伴与服务 | 延续必要偏好和历史事实，在新一轮交流中继续服务 | Agent + Persona/Memory/关系配置；具体关系和情绪规则由产品配置表达 |
| 专业分工 | 把研究、分析或制作等子任务交给专业 Agent，再得到统一结果 | 主助手 + 获授权子 Agent；工作室和计划按需使用，单聊不强制创建团队计划 |

这些场景用于说明产品组合，不表示每种行业方案、文件格式、外部业务接入或部署方式均已完成验收。

## 6. 成功指标

### 6.1 北极星指标

**安装到首个成功调用耗时**：从机构完成首个 Agent/Workflow 配置，到最终用户或 OpenAPI 完成第一次真实业务调用的中位时间。它衡量机构把知识、工具和工作方法转为可用智能服务的启动成本。

### 6.2 产品护栏

| 指标 | 既有定义 | 与产品价值的关系 |
| :--- | :--- | :--- |
| 任务完成率 | Execution 到达业务成功终态的比例 | 判断行动是否形成可核验业务结果，文件类任务另核对交付物 |
| 恢复成功率 | 挂起后准确恢复且不重复执行的比例 | 检查补充、确认和回调是否延续正确任务 |
| 会话连续性 | Workflow 等待或后台运行时普通对话仍可正常处理的比例 | 检查任务等待是否影响持续服务 |
| 输出有序率 | 回复、任务通知与主动消息按 Session 顺序投递的比例 | 帮助用户理解进度与最终结果的先后关系 |
| 回放一致率 | 从持久事实重建的模型输入、状态和结果与原执行一致的比例 | 支撑问题追溯与恢复核验，不以重新生成同一模型文本代替 |
| 单次成功成本 | 完成一次业务目标的模型、工具和基础设施成本 | 评估智能服务的运营效率 |
| 人工介入率 | 因策略、权限、失败或用户选择进入人工处理的比例 | 分析哪些工作需要人协助，不能将正常确认一律视为失败 |
| 租户隔离缺陷数 | 必须为零的安全护栏 | 保证机构数据、凭据与资源授权边界 |

知识回答还需核对引用与来源，研究和文件交付还需核对内容与成果是否符合任务要求；这些检查不替代上述指标，也不在本文新增数值门槛。性能、容量和可用性目标由[非功能需求](03-非功能需求.md)维护。

## 7. 产品非目标

### 7.1 MVP-0 不交付

MVP-0 的完整边界见 [Harness 01](../../harness-design/01-Agent-Workflow协作引擎-MVP需求分析.md#6-mvp-0-范围边界)：不固化熟悉度、情绪值、关系阶段或称呼策略；不以该阶段承诺完整任务运营、主动触达配置、高级记忆治理、任意 Workflow 节点续跑、动态插件安装或对等多智能体协商。专业 Agent 委派仍归 FR-15/P2，局部实现不改写阶段划分。

### 7.2 平台长期边界

- 行业规则放在机构资源和产品配置中，Kernel 保持通用职责。
- 开放式决策归 Agent，确定步骤与执行状态归 Workflow；Agent 只消费公开执行契约，不拼装内部恢复快照。
- 图谱、GraphRAG、图抽取和图谱运营不属于产品范围，历史设计不形成恢复承诺。
- 首期专业委派遵循当前主从与叶子执行基线，新增协作模式需要另行批准。
- 不为与当前已批准架构冲突的旧入口、旧 schema 或旧行为建设兼容路径。

## 8. 当前阶段与实现依据

项目处于预发布阶段。MVP-0 形成 Stateful Agent Runtime 与 Multi-Execution Session Runtime；P1 将记忆、知识研究、开放接入和运营等能力产品化；P2 增强长任务、专业委派与生产工具；P3 的动态插件及生态扩展需独立立项。阶段目标与产品结果见[实施路线图](04-实施路线图.md)，Runtime 里程碑与退出门禁见 [Harness 06](../../harness-design/06-MVP-0技术底座实施方案.md)。

目标设计从[Harness](../../harness-design/README.md)和[宿主未实现主题](../02-架构与设计/11-未实现功能清单.md)查询，实际行为以当前源码及对应候选的验证为准。当前已有的产物交付、原生委派或其他局部能力并不代表所属阶段或全部场景完成。路线图维护阶段结果，实施记录维护证据，本文不复制随版本变化的完成清单。
