# 实施路线图

> 本文面向内部产品与研发团队，说明每个阶段带给用户的成果、依赖和验收出口。产品目标见[产品概述](02-产品概述.md)，用户行为见[PRD](01-PRD.md)。
> Runtime 分期与 FR 归[Harness 01][mvp]、[Harness 04][later]，Gate 0、M1–M7 及退出门禁归[Harness 06][implementation]。委派专题当前基线归[Harness 08][delegation]。

## 1. 路线原则

围绕通用智能 Agent 推进：先让用户在持续会话中完成目标，再让机构可配置、可治理地提供服务，随后增强长任务和专业协作。Workflow 提供确定执行能力，Persona、关系和记忆支持持续服务；具体行业与陪伴产品规则不能成为 Kernel 的固定前提。

阶段表达目标范围与依赖，不是按日期推断的完工状态。MVP-0 先形成 Stateful Agent Runtime 与 Multi-Execution Session Runtime；P1/P2 增加产品能力而不建立第二套入口和执行状态。当前代码、局部验收、服务就绪与整阶段完成分别判读。

产品批次可在明确边界内并行实现，依赖能力通过必要门禁后才能作为正式交付前提。目标设计见 [Harness](../../harness-design/README.md)，实际完成度以当前源码和对应候选的验证为准。

## 2. 阶段总览

| 阶段 | 用户与机构成果 | 关键依赖 | 验收出口 |
| :--- | :--- | :--- | :--- |
| MVP-0 | Agent 能理解目标、使用授权能力并在等待时持续对话，准确恢复和接收结果 | Gate 0 → M1–M7，类型契约、统一入口、上下文策略、执行恢复和 SDK 装配 | 两项底座、两个指定真实纵向样例及 Harness 06 门禁通过 |
| P1 | 机构能配置、集成和运营智能服务，用户能获得更充分证据、可管理任务和可解释费用 | 已验收 MVP-0 能力；版本化资源、持久用量和事件输出 | FR-9/10/12/14/19/20/21、FR-22 基础及所属宿主闭环分别通过 |
| P2 | 用户能推进复杂长任务，利用专业 Agent 分工、计划清单与会话派生继续探索 | 已验收会话、执行、授权、恢复和事实域；各产品增强按依赖接入 | FR-13/15/16/23、高级记忆和完整生产工具在批准范围通过 |
| P3 | 经独立立项获取动态插件与生态能力 | 独立需求、隔离安全与供应链方案 | 由批准的新范围确定，当前路线不宣告已承诺或已实现 |

## 3. MVP-0：技术底座

### 3.1 用户成果与依赖

用户可在一个绑定 Agent 的持续会话表达目标、使用已授权的 Skill、Tool、Knowledge Source 和 Workflow。Agent 将观察、决策、行动与结果记录下来，等待的任务不冻结普通对话，用户能够查看、取消和准确恢复活动任务。

工程依赖顺序沿用[Harness 06 实施总路径](../../harness-design/06-MVP-0技术底座实施方案.md#3-实施总路径)：Gate 0 冻结设计边界，M1 建立契约与内核，M2 统一输入，M3 建立有状态上下文，M4 建立多执行会话，M5 接通 Workflow 与恢复，M6 收敛决策主干，M7 完成 Runtime SDK。具体工作包和条件归[里程碑拆解](../../harness-design/06-MVP-0技术底座实施方案.md#4-里程碑拆解)，不以 M6 接线替代 M7 SDK 验收。

附件、工具文件、工作区与正式成果按所属宿主契约接入这个主干。它们的实现批次可以有独立证据，但不改写 Runtime 阶段编号，也不代替两项底座验收。

### 3.2 验收出口

- Stateful Agent Runtime：固定 Persona 版本，按租户、用户与 Agent 续接关系和基础记忆，输入、能力与输出经过策略，替换产品关系 schema 不修改 Kernel。
- Multi-Execution Session Runtime：同一 Session 两个真实 Execution，一个等待 HITL、另一个后台完成；用户继续对话，结果按序送达，点选准确恢复，重启后活动清单可重建。
- SDK 与宿主通过同一公开 façade、Ports 和适配器运行；已替换边界的旧入口与旁路删除，满足[架构一致性与发布门禁](../../harness-design/06-MVP-0技术底座实施方案.md#7-架构一致性与发布门禁)。

上述两个样例保留 Harness 06 的指定范围。通用 Agent 的产品旅程通过这些底座承载，不能把改写定位当成取消已有验收要求。

### 3.3 非包含范围

MVP-0 不交付具体陪伴关系规则、完整记忆运营、多源迭代研究、完整轨迹费用产品、任意节点 checkpoint 续跑、Agent 委派或动态插件。触发入口和基础记录不代表主动触达产品、完整回放和运营界面已完成；挂起恢复不等于任意位置宕机续跑。

## 4. P1：产品化

### 4.1 用户成果与依赖

P1 将智能服务从可运行变为可配置、可管理和可集成。用户得到来源更充分的答案、可理解的待办交互和任务反馈；机构能治理记忆与会话、发布版本、运营任务并将服务接入自身应用。

| 产品成果 | 依赖与所属需求 | 验收出口 |
| :--- | :--- | :--- |
| 持续服务可治理 | MVP-0 FR-17；P1 FR-9、FR-10 | 记忆有来源和纠正入口，会话保留、导出、删除及回放按授权验证；具体 Persona/关系 schema 可配置 |
| 研究结果有充分证据 | MVP-0 FR-7 知识模式与证据；P1 FR-19 | 多源查询、链接追踪、充分性与冲突评估受预算和来源约束，写回提案经治理，不由知识层直接回复 |
| 等待与任务运营可用 | MVP-0 FR-4、FR-18；P1 FR-12 | 多挂起交互、语义唤醒与任务视图绑定准确目标，不因单个任务终态终止会话 |
| 过程与费用可解释 | 持久 Session/Action/Execution/Usage/Audit 事实；P1 FR-20 | TraceView 关联调用及价格快照，未决费用与追加调整可对账，未知量不按零计费 |
| 应用完成完整交互回环 | 统一准入、版本资源、知识治理和 Outbox；P1 FR-14、FR-21 | 资源维护、消息、附件、恢复、取消、Webhook/cursor 与对账按分面授权验证，重投不重复业务 |
| 配置从草稿走向服务 | 版本化资源与 Workflow schema；P1 FR-22 基础及宿主工作 | 五区基础 Builder、节点目录、校验 Problems、revision/If-Match、不可变发布及隔离测试闭环；基础 Handoff 和计费分析可用 |
| 授权的主动服务 | Trigger 基础与产品策略 | 授权、频控、安静时段、退订和审计可验证，渠道投递与业务完成分别表达 |

精确需求和验收归[Harness 04][later]；完整旅程以[PRD](01-PRD.md)的四类角色场景连接这些能力。

### 4.2 非包含范围

P1 不实现任意节点恢复与分布式接管、递归委派、完整 Builder 调试与多人协作、Marketplace 全供应链、完整坐席工作台或企业合规。Marketplace 在 P1 只消费已发布目录。冲突消解、衰减、审核与元认知工具仍按 Harness 04 的 FR-9 详细 P1 验收条目实施，不因“高级记忆”的总表标签迁到 P2。

## 5. P2：高级执行与委派

### 5.1 用户成果与依赖

| 产品成果 | 依赖与所属需求 | 验收出口 |
| :--- | :--- | :--- |
| 长任务在故障后安全继续 | 持久执行、冻结版本和恢复基线；FR-13 | 任意节点 checkpoint、租约接管与 fencing 可验证；不能安全续跑时明确失败，不能静默重放副作用 |
| 专业 Agent 分工并由主助手整合 | Agent 运行、独立会话、授权、Entry/Wait 协调；FR-15 与[Harness 08][delegation] | 名单内直接委派或可选结构化计划，子 Agent 使用自身完整能力；补充、等待、取消和恢复有真实 Run 结果与安全回执 |
| 计划可查看和调整 | 计划、Execution 和结果事实；FR-16 | Todo 状态与执行结果关联，调整只作用于未执行项，日志可回放，不靠勾选伪造完成 |
| 从已有上下文探索新方向 | 授权会话与快照事实；FR-23 | Fork 按所属契约派生，原会话与新会话的身份、材料和后续变化边界可验证 |
| 复杂生产服务可维护 | 已验收版本资源与运营基础；FR-22、宿主工作及待明确的高级记忆增量 | 高级记忆、完整 Builder 画布/调试/diff/历史/协作、Marketplace 制品供应链、坐席和企业合规按批准范围验收 |

**待明确的记忆增量**：Harness 04 分期总表保留 P2“高级记忆／FR-9 其余”，但详细验收表将 FR-9.7、FR-9.8、FR-9.16、FR-9.18 等列为 P1，未单列对应的 P2 增量。本文保留详细条目的 P1 归属与总表的高级增强方向；P2 具体新增范围须在所属需求中明确后才能拆解，不凭本次文档重写自行调期。

### 5.2 首期委派边界

委派保持 P2 FR-15 归属，具体实现和验收以 Harness 08 当前专题为准：主助手使用普通 Chat Run，自身配置授权目标名单；可选工作室只收窄名单。子 Agent 是不能继续委派的叶子执行者，使用独立能力和会话；普通消息不强制建 DAG，主助手的最终答复仍由原 Run 产生。

首期不包含递归深度、环协议或父子预算分割。旧 FR-15 扩展材料中相关历史表述不能恢复为本路线承诺；若需扩展，应先在委派专题完成明确设计。委派不新增第五类 Capability，不让子 Agent 直接向用户会话写消息或复制父 Agent 私有上下文。

### 5.3 非包含范围

P2 不包含对等自治群体、动态插件热更新与跨进程生态安装。已有取消或恢复接口不证明分布式执行韧性已通过；已有结构化计划或工作室界面不证明整个 FR-15 或 P2 已验收。

## 6. P3：插件生态

P3 需要独立需求评审。候选用户成果是安全安装和更新外部能力、管理生态制品与更开放的多智能体协作；候选范围包括动态插件安装、热更新、跨进程隔离、供应链强化、生态市场、沙箱强化和对等多智能体协议。

依赖、兼容或迁移策略、权限、隔离和验收出口由新立项确定。MVP-0 的显式注册、Spring 装配、现有 Marketplace 目录和首期叶子委派均不是 P3 完成证据。

## 7. 并行产品工作流

| 工作流 | 接入依赖与边界 |
| :--- | :--- |
| 身份、机构与应用 | 入口先完成可信身份和资源绑定；机构授权和费用独立，不在 Runtime 内推断缺失归属 |
| 渠道、聊天与附件 | 输入和控制经统一准入，输出经 Outbox；纯附件、授权材料与成果引用遵守[宿主契约](../02-架构与设计/04-接口与事件契约.md) |
| 工具、技能与知识 | 版本资源显式部署和挂载；知识模式与 Operator 由任务选择；Connector 和 Provider 不成为新 Capability |
| 工作区与成果 | 项目文件、候选输出和正式成果分别治理；保存、备份、任务完成和正式交付分别提供真实状态 |
| Builder 与 Marketplace | 生产、校验、发布和分发版本化资源，不建立 Tool invoke 或 Workflow run/resume 旁路；测试经隔离 Session |
| 人工与任务运营 | 消费受控历史和执行投影；人工协助不改变工具权限、不直接读取 checkpoint、不冒充用户输入 |
| 会话话术与风格学习 | 复用会话、知识和 Agent 发布，按[专项需求](05-会话话术与风格学习需求.md)交付人工辅助回复；数据基线、闭环、持续优化和条件扩展的目标依赖见[相关设计](../02-架构与设计/22-会话话术与风格学习设计.md) |
| 费用与观测 | 外部计费调用经过统一守卫；业务因果、技术尝试与持久用量分别追踪，投影可重建 |

图谱、GraphRAG、图抽取和图谱运营不进入任何阶段；历史材料或兼容代码不能成为恢复范围的依据。

### 7.1 完成度判定

阶段是否退出按该阶段完整门禁判定，不能从某个页面存在、局部测试通过或设计文档落地推断。SDK、正式成果、会话工作区与原生委派分别核验对应消费者、授权、持久化和恢复；真实供应商与生产环境另行验证。公开仓库不附带内部历史运行报告，也不以当前整理重新确认历史测试结论。

## 8. 发布门禁

Runtime 发布条件归[Harness 06 架构一致性与发布门禁](../../harness-design/06-MVP-0技术底座实施方案.md#7-架构一致性与发布门禁)。产品验收按[PRD](01-PRD.md)连接目标、材料、行动、人工协作和结果，并对所交付批次验证真实消费边界。

验证范围与证据复用遵循[评审与验证规范](../../.agents/skills/nw-verification/references/candidate-driven-delivery.md)，宿主发布操作见[发布检查清单](../../deploy/runbook/checklist-release.md)。本路线不提供部署、数据操作或外部业务变更授权；实际阶段状态按有效证据记录，不从规划文本推断。
