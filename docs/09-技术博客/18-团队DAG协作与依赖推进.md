# 团队 DAG：依赖完成才推进，失败也要能交付有用结果

前置阅读：[03 课](03-提示词设计总览分层组装与验证.md)、[16 课](16-原生Agent委派与父子生命周期.md)、[17 课](17-委派目标快照权限与预算边界.md)

把任务分给多个 Agent 后，真正困难的不是同时启动几个子 Run，而是决定谁在什么条件下可以继续。研究助手要比较虚构资料 A 与 B：A 采用关键词匹配和批次更新，没有更新延迟数据；B 采用语义检索，没有更新周期或性能测量。内部技术团队需要一份选型报告，草稿会从 D1 修订为 D2，发布必须审批。若这些依赖只存在于聊天里的“等大家做完”，恢复、重试和部分失败都会打乱顺序。

有向无环图（DAG）把工作节点和依赖边变成可持久判断的事实。节点可由独立 Run 承担；边表示后继获得推进资格所需的结果，不表示前驱可以把权限、上下文或成功状态传给后继。团队 DAG 管理的是任务协作关系，不能把节点“看起来做过”当作依赖满足。

## 从交付物反推节点，而不是从 Agent 名单出发

这个案例可以拆成六个节点：N1 核验 A，N2 核验 B，N3 建立证据矩阵，N4 形成 D1，N5 根据审阅意见形成 D2，N6 审批并在批准后发布。N1 与 N2 没有相互依赖，可以并行；N3 需要读取两者的终态结果；N4 依赖 N3；N5 依赖 D1 和有效审阅意见；发布 Action 只有在 D2 的审批通过后才有资格提出。

下面是 DAG 的伪代码示意：

```text
N1 audit_A          deps=[]                 output=source_assessment
N2 audit_B          deps=[]                 output=source_assessment
N3 compare_evidence deps=[N1, N2]           policy=allow_partial_with_gaps
N4 draft_D1         deps=[N3]               requires=matrix_committed
N5 revise_D2        deps=[N4, review_input] requires=review_bound_to_D1
N6 publish          deps=[N5, approval]     requires=approval_bound_to_D2
```

`allow_partial_with_gaps` 不是把失败当成功，而是一条明确的降级策略：只有当 N3 能识别每个前驱的终态，并把缺口带入结果时，才允许继续。若任务要求完整基准测试，策略就应是“任一必要测量缺失则阻塞”。依赖策略属于任务定义，不能由调度器看到超时后临时猜测。

## 用状态推演一次正常路径

t0，DAG 已提交，N1、N2 从待领取变为可领取。两个 worker 分别创建子 Run；调度器不会提前领取 N3。t1，N1 完成，交付“A 是关键词匹配、批次更新、无延迟数据”。N3 仍等待 N2。t2，N2 完成，交付“B 是语义检索、无更新周期、无性能测量”。调度器读取两个已提交终态，才把 N3 变为可领取。

t3，N3 产生证据矩阵：查询机制可比较，更新及时性和性能不可比较。t4，N4 生成 D1，结论只覆盖证据支持的维度。技术负责人提出“把证据缺口放在建议前”，该审阅意见绑定 D1；N5 据此生成 D2。审批记录必须绑定 D2，不能拿 D1 的批准发布 D2。只有审批通过后，N6 才能提出发布 Action。

重复的节点领取请求应返回同一个节点身份，不能平行制造两个 D1。worker 崩溃后重新领取时，也要从节点已提交状态继续；旧 worker 迟到提交，必须因版本不匹配而被拒绝。这些是运行时一致性要求，不应寄希望于 Agent 记得自己是不是“第一次”。

## 失败传播不等于全图熔断

假设 N2 读取 B 时超时。一次调用 Attempt 失败不必立即让 N2 终态失败；它可以在允许范围内重试只读操作。若预算耗尽仍未取得资料，N2 以 `blocked` 结束，并说明是读取失败，而不是“B 没有更新机制”。N3 随后依据预先定义的部分交付策略运行：使用 N1 的事实，加上 N2 的阻塞原因，产出不完整证据矩阵。

这样 N4 仍能生成 D1，但必须写明 B 尚未核验，不能给出选型建议。若 N2 之后通过用户补料形成新的有效结果，系统应创建可追踪的新版本或重新打开受影响节点，令 N3、D1 的派生结果失效，再生成 D2。直接改写旧矩阵会让审阅者无法判断 D2 为什么变化。

另一类失败是依赖本身不成立。例如审阅意见针对 D1，但当前候选已经是由其他证据生成的 D2；N5 不能套用过期意见。发布节点遇到拒绝审批则终止发布分支，保留 D2 草稿。取消 DAG 只能阻止未开始或仍可停止的节点，不能撤销已经发送到外部的效果。

## 给模型增加依赖感知，而不让它调度自己

下面的增量提示词接在第 03、16、17 课的相关片段之后，用于某个节点的模型准备结果时。节点目标和结果合同来自 DAG 定义；前驱状态、可用产物、当前权限及预算由运行时提供。

```text
[新增：团队依赖与部分交付]
只使用运行状态中已提交且属于当前节点依赖的产物。
前驱仍在运行、等待或结果未知时，不得声称依赖已满足，也不得猜测其内容。
前驱失败或阻塞时，按当前节点的部分交付策略行动：允许降级则列出可用结果与缺口；不允许则返回阻塞原因。
输出必须匹配节点结果合同，并标明所引用的前驱结果版本。
不得自行把后继节点设为可运行、跳过审批或发布报告。
```

使用这段提示词的时机，是运行时已经判定节点可推进并组装本轮上下文之后。它帮助模型正确解释依赖，而不是授予领取节点的权力。预期行为是 N3 在 N2 阻塞且允许部分交付时生成带缺口矩阵。失败对照是把 `blocked` 当成“检查完成且没有发现问题”，进而在 D1 中写“B 性能优于 A”。节点资格、版本检查和审批仍由运行时强制。

## DAG 的取舍

DAG 适合依赖稳定、结果合同明确的协作。把每个小步骤都做成节点会增加存储、调度和版本传播成本；把整份报告做成一个节点又失去并行与局部恢复价值。一个实用切分标准是：节点是否能独立验收，失败是否有独立处理策略，产物是否会被多个后继引用。三者都是否定时，通常不必拆。

## 小练习

N1 已完成，N2 因无权读取 B 而 `blocked`；N3 允许部分交付，N4 可以生成带缺口草稿。随后有人把 N4 手工标为完成，并要求直接发布 D1。系统应怎样推进？

预期结果：N3 生成只包含 A 事实和 B 阻塞原因的矩阵，N4 可形成 D1，但 D1 明确不能比较性能与更新及时性。手工“完成”不构成发布资格；没有绑定 D1 或后续 D2 的有效审批，发布节点保持不可运行。权限恢复后应重新核验 B，并让受影响派生结果按版本重新生成。
