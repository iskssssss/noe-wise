# 单一事实源与文档驱动开发

前置阅读：[33 Agent Runtime 的微内核与插件边界](33-Agent-Runtime的微内核与插件边界.md)、[35 Skill 编辑校验与不可变版本发布](35-Skill编辑校验与不可变版本发布.md)、[41 Agent 契约、真实链路、并发与行为评测](41-Agent契约真实链路并发与行为评测.md)。

研究与报告助手要比较两份虚构资料中的检索方案 A 与 B，再向内部技术团队提交选型报告。有人说“方案 A 的结论写在设计说明里”，有人从运行记录看到一次失败的检索，又有人在模板里改了审批文案。若这些材料都能互相改写含义，读者很快就无法回答：报告依据的规则是什么，哪次任务实际做了什么，当前该遵循哪份结论。

单一事实源不是把所有内容塞进一份大文档，而是让每类事实有明确所有者。文档驱动开发也不是先写文档再照抄成代码；它要求先把设计中尚待实现的约束写在正确位置，再让实现、验证和操作记录各自证明可观察的部分。

## 先区分事实的种类

以报告助手为例，检索方案 A/B 的选型规则、证据不足时的输出要求、发布必须审批的条件，属于设计与契约；报告模板的版本、可用工具与所需权限，属于可发布能力的定义；某个 Run 在何时调用了哪个 Action、返回成功还是结果未知，属于运行账本；遇到故障后怎样排查、怎样恢复，属于运维指南；某次取舍为何改变，则属于历史决策。

这些内容可以彼此链接，却不应互相覆盖。设计文档不能用一条成功日志证明“已经实现”；运行记录也不能因为旧任务曾绕过审批，就取消当前审批约束。模板只能说明它需要审批能力，不能自行宣布审批已完成。历史决策保留当时的理由，但被新决策取代后，不再定义当前行为。

| 事实 | 所有者 | 常见引用者 |
| --- | --- | --- |
| A/B 比较的证据标准与审批条件 | 设计或公开契约 | 实现、测试、模板说明 |
| Skill、模板、工具和权限的发布版本 | 能力定义与发布记录 | Run 准备、安装说明 |
| Action、Attempt、状态转换和结果未知 | 运行账本 | 审计视图、故障排查、结算 |
| 部署、告警、恢复和人工处置步骤 | 运维指南 | 值班手册、演练记录 |
| 取舍背景、替代方案和适用范围 | 决策记录 | 设计说明、后续变更 |

表中的“所有者”不是编辑权限的代名词，而是解释权的归属。其他页面可以说明用途，但应链接回所有者，避免复制一段定义后悄悄漂移。

## 变更从定位事实源开始

当技术团队提出“证据不足的报告必须单列缺口”时，先判断这是输出契约、模板内容，还是两者都要变。若它改变报告的可接受结果，应先更新设计或契约；若它只改变呈现格式，再更新模板定义。然后让测试引用预期行为，让实现落实检查，让运行账本保留实际产出的版本。引用方随着所有者更新，而不是各自写一套“最新版规则”。

这个顺序还能揭露遗漏。若有人只改了页面提示，却没有能说明 Run 如何拒绝直接发布的契约，问题不是“文档不够多”，而是审批语义还没有被放进该拥有它的事实源。相反，若每份说明都抄录 Action 状态枚举，状态新增时就需要在多处猜测谁应先修改。

文档链接应指向稳定的概念或章节，不把会话、临时讨论和个人判断当成长期依据。没有所有者的新事实，先为它建立合适的归属；发现两个来源给出冲突定义时，修正引用方或完成明确的决策，而不是在两边都补一段解释来掩盖冲突。

## 让文档、实现与证据各司其职

文档描述要实现什么和为什么；代码、配置与发布版本描述当前实际装配了什么；测试说明哪些行为已被验证；运行账本说明某次真实过程发生了什么。四者相互校验，但证明范围不同。一次测试通过不证明所有环境都已部署；一条账本记录也不证明所有输入都符合契约。

报告助手恢复旧 Run 时尤其依赖这种区分。它读取冻结的模板与工具版本来理解当时任务，读取账本判断哪些 Attempt 已提交，读取当前权限决定恢复时能否再发起新 Action。任何一项都不能被另一项替代，否则恢复会把历史事实、当前规则和未来意图混在一起。

练习：团队决定“无法取得资料 B 时，报告必须列出证据缺口，且不得请求发布审批”。列出需要变更或引用的事实源，并说明每个来源保存什么。

预期结果：设计或契约定义缺口与审批条件；模板版本定义展示方式；测试断言不会发起审批 Action；运行账本记录实际缺口和未发起审批的事实。运维指南只在恢复或人工处置需要时说明操作，不重复定义业务规则。
