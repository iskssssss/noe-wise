# 网站产物预览：报告里的脚本不该拥有主应用身份

前置阅读：[08 课](08-HTTP工具的受控出网与执行边界.md)、[22 课](22-审批回调与挂起恢复.md)、[27 课](27-从临时文件到正式成果产物生命周期.md)

报告从 Markdown 变成带筛选按钮的 HTML 后，预览不再只是“打开一个文件”。页面可能执行脚本、发起网络请求、导航到其他站点，甚至尝试读取主应用的存储。

研究助手生成的内容即使服务于内部团队，也应按不可信主动内容处理。生成模型没有恶意，不代表它输出的 HTML、依赖脚本或嵌入资料安全。预览需要把内容运行环境与业务应用身份分开。

## 不要在主应用同源路径直接打开

浏览器按源隔离许多能力。源由协议、主机和端口共同决定，在主应用的 /preview 路径打开 HTML 并没有形成新的源。脚本可能接触同源接口和存储，具体影响取决于应用配置。

独立预览源配合 iframe sandbox 与内容安全策略，可以限制脚本、表单、导航和网络等能力。需要哪些能力就显式开放，不能为了兼容一个图表库就把所有限制取消。若内容根本不需要脚本，静态预览通常更容易控制。

Cookie 还需要单独考虑。不同端口不隔离 Cookie，父域设置的 Domain cookie 可能发送给子域。仅把 preview 放到子域，并不能自动保证它收不到应用凭据。独立站点、主机限定 Cookie 和明确的认证设计需要一起核对。

sandbox 属性也不是万能。特别要避免在内容与父页面同源时随意组合可执行脚本和保留同源能力的配置，让内容有机会削弱隔离。

## 身份校验与内容源隔离解决不同问题

源隔离控制页面能接触什么，访问校验控制谁能看到页面。公开预览和私有预览不能共享一个含糊的“带 token 链接”设计。

可选择的几种模式各有取舍：

| 模式 | 适用选择 | 需要说明的限制 |
| :-- | :-- | :-- |
| 公开只读预览 | 内容本来就允许公开 | 地址可被转发，不能当私密入口 |
| 短期 bearer 票据 | 明确允许持有链接者临时访问 | 票据可转移，不证明当前持有者身份 |
| 经认证兑换一次性票据 | 需要核对当前主体 | 兑换时校验主体、资源与范围，并建立受控访问会话 |

在票据中写入 subject，并不自动证明打开链接的人就是该 subject。要实现这个绑定，访问端需要可验证的认证上下文，或者通过已认证的入口完成兑换。票据应有有限寿命、明确产物范围，并避免出现在可泄漏的日志或外发引用中。

## 产物树里的资源也要受控

HTML 的相对资源路径不能逃出产物根目录。服务端应规范化路径并验证归属，拒绝穿越、非预期文件和跨产物引用。报告里的图片、样式和脚本也要遵守相同访问范围，而不只是入口 HTML 需要权限。

缓存不能把私有内容分享给其他用户。缓存键、响应头和 CDN 规则都应与访问模式一致。登出或撤权后，下一次访问应重新符合策略；若系统选择使用短期票据，应明确其失效延迟和撤销能力。

CSP 可以限制连接目的地、脚本来源和嵌入能力，但不是服务端鉴权的替代。浏览器请求下载文件时，后端仍需核对产物状态和当前权限。

## 预览不代表正式发布

用户可以预览 D2 草稿进行审批，预览入口的存在不意味着报告已经开放给整个团队。预览授权范围、报告发布范围和分享策略应分别记录。

当审批被撤回或产物版本改变时，界面也需要呈现正确对象。旧页面若继续展示 D1，应清楚标明版本；用户不能在看 D1 的预览时无意中批准 D2。最稳妥的方式是让审批动作携带当前展示的内容版本，由后端再次核对。

若产物包含高风险主动内容，下载后离线查看、生成无脚本快照或限制为静态格式都是可选方案。隔离越强，交互能力越有限，需要根据读者真正需要的功能取舍。

## 审查一个看起来安全的方案

练习：主应用位于 app.example.test，预览位于同主机的另一个端口，开发者准备把应用 Cookie 和短期 bearer 链接一起用于“私有预览”。指出问题并给出改法。

预期结果：不同端口不会隔离 Cookie；bearer 链接可转移，不能单凭票据中的 subject 断言持有者身份。应重新选择隔离源和 Cookie 范围，明确预览是可转移票据访问还是绑定认证主体，并对每个产物资源实施访问检查。D2 能预览仍不表示已经批准发布。
