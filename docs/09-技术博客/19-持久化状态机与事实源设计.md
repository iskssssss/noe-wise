# 持久化状态机：恢复时相信事实，而不是最近一条聊天消息

前置阅读：[02 课](02-Session-Run与Execution为什么需要分开.md)、[04 课](04-Agent-Loop的动作观察与模型输出失败处理.md)、[18 课](18-团队DAG协作与依赖推进.md)

研究助手核验了两份虚构资料：A 采用关键词匹配和批次更新，却没有更新延迟数据；B 采用语义检索，却没有更新周期或性能测量。它为内部技术团队生成草稿 D1，审阅后形成 D2，发布必须审批。若服务在“D2 已保存”与“界面显示 D2”之间崩溃，恢复器应该相信哪一个状态？答案不能是内存中残留的变量，也不能是用户恰好看到的最近一条消息。

可恢复系统需要明确的持久事实源：决定下一步的状态先以事务方式提交，界面消息、流式片段、缓存和搜索索引都只是它的投影。投影可以延迟、重复甚至暂时缺失；只要事实仍在，系统就能重建观察。反过来，即使界面提前显示“发布成功”，没有对应的持久终态也不能把它当成真。

## 先分清五种生命周期

Session 是长期会话，保存参与关系与可持续交互边界；Run 是一次 Agent 任务推进，保存目标、等待原因、结果与终态；Execution 只表示 Workflow 执行，不能拿来统称所有 Agent 工作。Action 是一次有业务含义的动作，例如“请求审批”或“发布 D2”；Attempt 是某个 Action 的一次实际调用尝试，例如向发布服务发送一条请求。

这些对象不能被一个 `status` 字段揉在一起。Session 仍可继续时，某个 Run 可以已经完成；Run 等待审批时，一个资料核验 Action 可以完成，发布 Action 还未创建；一个发布 Action 可能只有一次超时的 Attempt，结果为 Unknown。对象边界决定恢复器能否判断应该继续会话、恢复任务、推进 Workflow，还是核对一次调用。

状态名可以因系统而异，但迁移必须表达合法方向。下面是伪代码示意：

```text
Run:    READY -> RUNNING -> WAITING_APPROVAL -> RUNNING -> COMPLETED
                         \-> BLOCKED
Action: PROPOSED -> ACCEPTED -> DISPATCHING -> SUCCEEDED
                                      \-> FAILED
                                      \-> UNKNOWN
Attempt: CREATED -> SENT -> ACKNOWLEDGED
                    \-> NO_RESPONSE
```

`NO_RESPONSE` 只描述没有收到响应，不能直接推导 Action 为 `FAILED`。同样，Run 被取消只阻止尚未发生的推进，不能撤销已经发送的 Attempt。状态机的价值正在于禁止这些看似方便、实际丢失信息的跳转。

## 每次迁移都要说明自己基于哪个版本

假设 Run 当前为 `WAITING_APPROVAL`，版本 12，等待 D2 的审批。worker W1 在较早时刻读到版本 10，当时等待的还是 D1；worker W2 已经把审阅意见写入并生成 D2。此时 W1 收到迟到消息，试图把 Run 直接改成“可发布”。如果更新条件只有 `run_id`，W1 会覆盖新事实。

更安全的写法是条件更新。以下为 SQL 风格伪代码，不对应特定表结构：

```sql
UPDATE run_state
SET state = :next_state, version = version + 1, waiting_for = :target
WHERE run_id = :run_id
  AND version = :expected_version
  AND state = :expected_state;
```

受影响行数为零表示前提已经变化，worker 必须重新读取事实并重新决策，不能把更新再发一次直到“成功”。同一对象、同一版本却出现两个不同状态，属于冲突或数据损坏，应停止自动推进并保留诊断信息。版本号不是装饰性的时间戳，而是写入权的条件。

唯一约束也承担事实保护。一次委派、一个审批目标和一个 Action 应有稳定身份；相同命令重放时找到原记录，而不是再造一份 D2。终态通常保持单调：完成之后到达的旧“运行中”事件不能让状态倒退。需要重新工作时，创建新版本或新的 Run，并记录它与旧结果的关系。

## 沿着崩溃点推演 D1 与 D2

t0，A、B 核验结果已经提交，Run 版本 7。t1，生成 D1 的 Action 成功，事务保存报告版本 D1、引用的资料版本和 Run 版本 8。若进程在响应界面前崩溃，恢复后仍能查到 D1；界面稍后重建“草稿已生成”，不需要再次调用模型。

t2，审阅意见绑定 D1，修订 Action 生成 D2，Run 变为等待 D2 审批。若缓存仍展示 D1，那只是过期投影，不能批准或发布 D1。审批请求必须携带 D2 的身份。t3，一条针对 D1 的旧批准到达，受理层发现等待目标不匹配，记录为无效输入，Run 继续等待 D2。

t4，D2 审批通过并提交，系统准备发布。若发布请求已经发送却没有回包，Action 进入 Unknown；不能因为 Run 的目标是“发布报告”就写成已完成。恢复器应停在可核对状态，由下一课讨论怎样处理外部副作用。这里的核心是：事实源准确保存“不知道”，而不是为了让状态图好看而选择成功或失败。

## 快照表、事件日志与投影怎样取舍

当前状态表便于条件更新和快速判断，追加事件便于审计“为什么变成这样”。两者可以同事务维护，也可以用事件重建状态，但一个业务决定只能有一个权威判定来源。最危险的设计是写状态表失败后仍发事件，或事件与状态各自接受独立修改，再让恢复器猜谁更新。

完整事件溯源能保留丰富历史，代价是版本演化、重放和修复更复杂。多数系统可以采用“权威当前状态 + 不可变审计事件 + 可重建投影”：状态负责下一步，事件解释迁移，投影服务查询。无论选择哪种方式，模型输出都只是候选，只有运行时校验并提交的迁移才是事实。

## 小练习

Run 在版本 20 等待 D2 审批。旧 worker 持有版本 18 的 D1 批准结果；界面因为缓存延迟仍显示“D1 已批准”，而数据库中 D2 尚未批准。旧 worker 尝试提交发布状态，应该发生什么？

预期结果：版本与等待目标检查拒绝更新，Run 保持等待 D2。界面从持久事实重建并修正展示；系统可以记录迟到的 D1 批准，但不能据此创建发布 Action。没有任何代码根据聊天消息或缓存文本宣布报告已发布。
