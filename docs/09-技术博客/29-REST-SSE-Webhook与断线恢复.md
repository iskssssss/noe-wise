# REST、SSE 与 Webhook：断线以后，进度从哪里续上

前置阅读：[19 课](19-持久化状态机与事实源设计.md)、[21 课](21-Inbox-Outbox与可靠事件交付.md)、[27 课](27-从临时文件到正式成果产物生命周期.md)

用户刚看到“正在核验方案 B”，页面就断线了。任务仍在后端运行，重新连接后却只显示空聊天框。若前端为了恢复页面再次提交研究请求，用户可能得到两份报告，甚至触发两次发布。

命令受理、实时展示和外部通知应该使用不同通道。REST 适合表达请求与查询，SSE 适合向浏览器推送事件，Webhook 适合通知另一个服务。三者可以共享运行事实，却不能互相代替可靠存储。

## 提交成功与任务完成是两个响应

创建 Run 的接口在受理后返回稳定标识与受理状态。客户端断线重试时使用约定的请求身份，服务端按幂等规则返回同一任务，而不是每个 POST 都新建一次运行。

查询接口返回当前状态、产物和必要的待办。SSE 提供随后发生的变化。浏览器连接断开只影响观察，不自动取消 Run；用户需要取消时发送明确控制命令。

事件中的标识也有不同用途：event_id 用于去重，cursor 或序号用于恢复位置，run_id 等用于关联业务对象。不要用时间戳代替严格顺序，因为同一毫秒可能产生多个事件。

## 实时推送必须有可重放的依据

SSE 的自动重连和 Last-Event-ID 只是传输约定；服务器仍需保存足够的事件或状态来解释游标。内存广播丢了消息，浏览器重连也无法凭空补回。

一个事件示例可以是：

```json
{
  "event_id": "evt-18",
  "cursor": "18",
  "run_id": "R1",
  "type": "artifact_validated",
  "artifact_id": "report-P2",
  "state_version": 7
}
```

这里的连续数字仅说明一个流内的顺序，不要求所有租户共享全局序号。客户端按该流的协议处理重复与缺口，不应比较不同流的游标大小。

事件保留期到了，旧游标无法重放时，服务端应返回明确的重新同步信号。客户端读取快照和其对应水位，再从水位之后继续订阅，而不是悄悄从“现在”开始，漏掉中间终态。

## 快照与订阅之间不能留下看不见的缝隙

假设客户端先读快照，稍后才开始订阅，中间发生了发布完成事件。如果快照没有对应游标，客户端可能永远不知道这个变化。

一种设计是快照响应携带一致的流位置，客户端从该位置之后重放。另一种是先订阅并缓冲事件，再读取带版本的快照，丢弃已经被快照覆盖的事件，按顺序归并剩余部分。两种方案都需要说明一致性边界，不能把“先查再订阅”当作天然可靠。

慢客户端还需要背压处理。服务器不能无限缓存每个连接；超过窗口时断开并要求恢复，是比静默丢事件更诚实的选择。

## Webhook 要允许对方重复收到

发布完成后通知外部系统，可以通过 Outbox 调度 Webhook。发送者保存投递状态、重试计划和截止条件；接收者通过稳定事件身份去重，并在可靠受理后响应成功。

签名应覆盖明确的请求内容与必要的时间或 nonce 信息，密钥支持轮换。接收者还要限制重放窗口、核对事件范围并验证业务权限。签名证明消息来自持有密钥的一方，不证明其中的业务状态永远有效。

超时后重投同一事件，保持 event_id 稳定，单次 HTTP 投递可以有新的 Attempt。接收方若在发送响应前崩溃，下一次投递应返回已有受理结果，避免重复执行下游效果。

长期不可达需要可见的失败状态与人工补投入口。不能因为报告确实发布成功，就在界面上把“外部通知成功”也一并打勾。

## 把断线恢复画出来

练习：客户端已消费游标 18，断线期间产生 19、20；重连时收到 18、19、20，又发现原游标超出保留窗口。分别说明短断线和过期游标的处理。

预期结果：短断线按 event_id 或流协议去重，顺序消费新事件；过期游标走明确的快照同步，并从快照水位之后接续，不能混用旧状态。整个过程不重新提交研究命令。报告任务是否完成，取决于持久状态与成果记录，而非浏览器是否完整看过每一帧。
