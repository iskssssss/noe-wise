# 幂等与未知结果：超时之后，最危险的是自信地再做一次

前置阅读：[03 课](03-提示词设计总览分层组装与验证.md)、[04 课](04-Agent-Loop的动作观察与模型输出失败处理.md)、[19 课](19-持久化状态机与事实源设计.md)

研究助手已经把虚构资料 A、B 写进内部选型报告。A 采用关键词匹配和批次更新，没有更新延迟数据；B 采用语义检索，没有更新周期或性能测量。草稿 D1 经审阅修订为 D2，技术负责人批准发布 D2。系统向内部知识库发送发布请求，连接却在收到响应前断开。此时“再试一次”可能把同一报告发布两遍。

这里要区分 Action 与 Attempt。Action 是“发布报告 D2”这个有业务含义的动作，拥有稳定身份、目标版本和审批依据；Attempt 是执行该 Action 的一次调用尝试。一个 Action 可以有多个 Attempt，但是否允许下一次尝试取决于上一次结果。网络超时只说明调用方没有拿到确定响应，不能证明接收方没有执行。

## Unknown 是必须保存的业务信息

请求发出后无回包至少有四种可能：请求未到达；请求到达但尚未处理；报告已发布而响应丢失；下游拒绝了请求但错误响应丢失。调用方观察到的字节和计时无法区分这些情况。因此 Attempt 可以记录 `NO_RESPONSE`，Action 则进入 `UNKNOWN`，等待核对。

把超时直接写成 `FAILED` 会授权调度器自动重试；把它写成 `SUCCEEDED` 又会欺骗用户。Unknown 看起来不够“整洁”，却保留了做出安全决定所需的信息。面向用户的诚实表述应是：“D2 的发布请求已发送，当前无法确认是否生效，正在核对原动作。”不能说“发布失败，请重试”，也不能说“应该已经成功”。

下面是处理路径的伪代码示意：

```text
if attempt.failed_before_send:
    action remains retryable
elif downstream_returned_definitive_rejection:
    action becomes failed or waits for corrected input
elif downstream_returned_success_receipt:
    action becomes succeeded
elif request_may_have_been_sent and response_missing:
    action becomes unknown
    reconcile(original_action_id, original_idempotency_key)
```

“发送前失败”必须来自可信执行适配层，例如本地参数校验未通过；不能因为超时很短就猜测请求没离开进程。HTTP 5xx 也未必代表业务效果没有发生，仍要根据下游接口契约判断。

## 稳定身份要贯穿本地与下游

本地先为发布 D2 建立稳定 `action_id`，并用唯一约束防止同一审批重复创建发布 Action。若下游支持幂等键，所有针对这个 Action 的允许重投都携带同一个键和相同效果载荷。下游保存键与结果，再次收到同键请求时返回原结果，而不是再次发布。

幂等键不能随便复用。D1 与 D2 是不同报告版本，应有不同业务身份；同一个键对应的内容如果变化，下游应拒绝冲突。键还需要明确保留期限，过期后重投是否仍安全不能靠调用方想当然。仅在本地给 Attempt 去重，也无法阻止请求已经到达下游后再次生效。

更好的下游接口还会提供按业务键或远端操作号查询状态。发布 Attempt 超时后，运行时先查原动作：若查询确认 D2 已发布，提交成功回执；若确认未受理，才根据当前权限、审批和重试策略创建新的 Attempt；若返回处理中，就等待；若无法查询或结果不可信，Action 保持 Unknown，交给人工核验。

这些措施不能泛化出“外部效果恰好一次”的保证。本地事务无法包住远端知识库。实际保证来自下游幂等、状态查询、业务对账或人工确认的组合，并受各自契约限制。缺少这些能力时，系统只能降低重复概率并如实保留不确定性。

## 取消不能撤销已经发出的效果

假设发布请求发出后，用户看到长时间无响应，于是取消 Run。取消可以阻止新的 Attempt 和后续动作，却不能把网络中的请求收回来，也不能删除下游已经提交的报告。若产品确实支持撤回，应把“撤回 D2”建成另一个需要授权、可审计的 Action，而不是把原 Attempt 从记录里抹掉。

同理，审批只覆盖绑定版本和范围。D2 的批准不能在 Unknown 后被用来创建“发布一份略作修改的 D2”；内容改变就需要新的报告身份和相应审批。恢复器必须读取当前权限和审批事实，不能因为原 Action 曾获批准就永久允许重投。

## 在第 03 课模板后追加 Unknown 处理

下面的增量提示词用于模型解释动作结果、决定是否提出后续动作时。Action 状态、Attempt 发送阶段、下游回执、查询结果、当前权限与审批均由运行时提供；用户说“我看见超时了”只能作为线索，不能覆盖这些事实。

```text
[新增：外部副作用与未知结果]
根据已提交的 Action 与 Attempt 状态报告结果。
unknown 表示外部效果尚未确认，不得改写为 failed、succeeded 或“很可能成功”。
结果未知时，优先提出对原 action_id 的状态查询或核对；不得创建新的业务动作来替代原动作。
只有运行状态确认效果未发生，或运行时明确说明可用同一幂等键安全重投时，才可提出新的 Attempt。
取消只表示停止后续推进；不得声称它撤销了已经发送的请求。
对用户说明已知事实、未知部分、正在采取的核对方式和需要人工确认的条件。
```

设计这段说明，是为了让模型在没有肯定答案时仍能给出可执行、诚实的响应。预期行为是发布 D2 超时后引用原 Action 查询，并把报告状态显示为“发布结果待核对”。失败对照是模型看到 `timeout` 就生成第二个发布 Action，或为了安抚用户宣称“已成功”。提示词不能阻止外调；运行时必须拦截重复业务动作并控制 Attempt。

## 安全与可用性的取舍

在 Unknown 状态停住会延迟交付，但盲重试可能制造不可逆重复。效果越难撤销，系统越应偏向核对；纯只读请求通常可以采用有限重试。下游若没有幂等与查询能力，集成成本看似较低，故障处理成本却转移给运营人员。接口选型时应把状态查询、业务键和冲突语义视为可靠性能力，而不只是一个可选请求头。

## 小练习

D2 已获批准。Attempt-1 携带键 `publish-D2` 发出后超时，用户随后点击“重试”并立刻取消 Run。下游支持按该键查询，查询返回“处理中”。系统应怎样处理？

预期结果：保留同一个发布 Action，拒绝创建新的发布动作，不把超时标成失败；查询“处理中”后继续保持 Unknown 或受控等待。取消阻止新的发布 Attempt，却不撤销 Attempt-1；必要的结果核对按恢复策略独立进行。系统向用户说明 D2 可能仍会发布，需继续核对原键；确认结果前不宣称成功或失败。
