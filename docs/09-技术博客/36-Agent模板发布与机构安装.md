# Agent 模板发布与机构安装

前置阅读：[35 Skill 编辑校验与不可变版本发布](35-Skill编辑校验与不可变版本发布.md)。

报告助手在一个团队试用成功后，其他团队也想安装它。若直接复制一份现成 Agent，模板作者随后修复检索策略时，谁会收到更新、谁保持本地改动、谁有发布权限都会变得含糊。模板必须被当作可发布制品，而不是一段可随时覆盖的配置。

统一教学案例里，模板教助手比较 A/B：`source-a@v1` 支持关键词匹配和批次更新，但没有延迟测量；`source-b@v1` 支持语义检索，但没有更新周期或性能测量。资料内容是教学构造。团队安装模板后，要用自己的资料连接、审批角色和预算生成内部技术报告，发布仍需该团队用户审批。

## 模板与安装实例分开

模板定义角色、默认提示词、推荐 Skill、工具清单和可配置项。安装后生成的是团队自己的实例：它绑定本团队的资料范围、审批人、预算和名称。模板升级不应直接覆盖实例，因为团队可能已把“方案 A/B”改成自己的评审维度。

可以把安装看成一次显式复制加引用：

```text
template@2.1 + team settings -> installation#47
installation#47 records template@2.1 and local overrides
```

这份来源关系使管理员能看见可升级项，也能在升级前比较差异。实例从不继承模板的运行中状态；每个团队的 Session、Run 和审批记录都独立。

模板包与租户实例可以用下面的教学结构区分：

```json
{
  "template": {
    "version": "report-agent@2.1",
    "required_capabilities": ["evidence.search", "report.draft"],
    "config_schema": ["evidence_connection", "approval_role"]
  },
  "installation": {
    "id": "installation-47",
    "tenant": "team-blue",
    "template_version": "report-agent@2.1",
    "secret_refs": ["secret://team-blue/evidence-reader"],
    "local_overrides": {"approval_role": "architecture-reviewer"}
  }
}
```

模板只声明配置槽位和能力需求，不能包含 `secret://team-blue/evidence-reader` 指向的值。安装记录保存的是本团队可解析的密钥引用，实际凭据留在密钥系统中；导出模板、复制模板版本或让另一团队安装时，都不能复制原团队的密钥引用，更不能复制密钥内容。

## 发布与安装都需要权限

模板作者可以发布新版本，团队管理员才可以安装或升级。安装过程应先校验团队是否拥有模板要求的资料库、工具和审批渠道；缺失依赖应阻止安装，而不是创建一个“看似可用”的助手，等它第一次写报告才失败。

模板也不该携带可复制的凭据。它可以声明“需要资料检索能力”，具体连接由安装团队在自己的权限边界内提供。这样同一模板能服务多个团队，又不会让一个团队借到另一个团队的数据源。

假设蓝队安装后把资料连接绑定到自己的知识库，绿队随后安装同一模板。绿队必须重新选择连接并授权；若安装器直接复制蓝队实例，绿队不仅会拿到错误审批人，还可能尝试访问蓝队资料。即使密钥系统最终拒绝访问，这个实例也已经违反了租户归属，不能把失败推迟到第一次 Run。

## 升级是一项选择

报告助手模板的新版本增加了“证据不足单列”规则。管理员可以预览模板差异、保留本地覆盖或接受默认更新；升级完成后，新 Run 才冻结新定义。已经等待审批的旧报告继续按旧版本执行，避免审核人与报告看到两套相互矛盾的规则。

安装时应把模板依赖解析为精确版本并锁定：Skill、工具 schema 和资源的内容指纹记录到团队实例中。模板作者发布新版 Skill，不会让已有助手在下次运行时悄悄换行为。升级才会重新解析依赖，并让管理员看到模板变化、实例覆盖、锁定依赖变化和能力缺口；无法自动合并的设置进入待处理状态，不能用“取最新”丢掉团队自定义的审批人或资料范围。

升级判断应做三方比较，而不是把新模板与当前实例直接相减。三方分别是：实例上次安装的基础模板 `2.1`、准备升级的新模板 `2.2`、团队当前实例。若 `2.2` 把默认报告格式从“摘要”改为“证据表”，而团队从未改过该字段，可以采用新默认；若团队已自定义为“摘要加风险清单”，则形成冲突，等待管理员选择。团队新增的审批人和资料范围没有模板对应项，应原样保留。

具体到 A/B 报告，模板 `2.2` 新增“没有测量时禁止比较性能”。蓝队本地只改了标题格式，因此规则可以升级、标题保留；若蓝队曾主动删除证据缺口章节，新规则与本地覆盖发生语义冲突，升级预览必须把它列出来，不能自动复活或继续删除。

模板实例必须绑定一个团队。资料范围、审批角色、预算和产物存储只能从该团队配置取得；模板作者即使能管理模板，也不能由此读取任何团队报告。新版要求新增发布工具、更高预算或更宽资源范围时，升级必须重新获得授权，旧安装记录不是永久许可。

安装还要避免半成品。可以在同一事务中创建实例和依赖锁，或让草稿安装在全部检查完成前不可激活；无论实现如何，发现列表和运行时都应区分正在安装、安装失败与已可用。重试使用稳定请求身份，防止双击生成两份绑定同一团队的助手。

一次安装可以依次经历 `preparing`、`validating`、`ready`，失败则进入 `failed` 并记录可重试原因。只有 `ready` 实例进入发现列表并接受新 Run。假设实例元数据已写入，但密钥引用校验超时：系统不能把它标成可用，也不能在重试时再创建 `installation-48`；同一安装请求应续接或返回 `installation-47`。若依赖已下载而最终授权被拒绝，隔离区制品可以按缓存策略复用，但租户实例、权限绑定和“安装成功”事件都不能部分生效。

练习：设计模板升级页面需要显示的四类信息：模板变化、实例覆盖、缺失依赖和受影响范围。

预期结果：管理员能从基础模板、新模板和当前实例判断哪些默认值可更新、哪些本地覆盖必须保留、哪些冲突需要选择；页面只显示密钥引用状态，不复制或展示密钥值。缺少审批渠道或资料连接时安装、升级停在不可激活状态；重试不会生成重复实例，旧 Run 也不因模板发布而改变。
