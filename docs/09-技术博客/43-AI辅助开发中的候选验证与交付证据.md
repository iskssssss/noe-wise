# AI 辅助开发中的候选验证与交付证据

前置阅读：[41 Agent 契约、真实链路、并发与行为评测](41-Agent契约真实链路并发与行为评测.md)、[42 单一事实源与文档驱动开发](42-单一事实源与文档驱动开发.md)。

研究与报告助手新增了一条规则：资料 B 缺少可用证据时，报告要明确列出缺口，并且不能进入发布审批。AI 可以很快建议修改检索分支、报告模板和状态判断，却不能因为代码看起来合理，就替代权限校验、状态迁移、幂等处理或人工审查。工程协作需要把 AI 的产出变成一个可辨认的候选，再用与风险相称的证据决定是否交付。

候选是一组准备被验证的改动，以及它依赖的输入、预期行为和范围边界。它不是“AI 已经写完”的同义词。候选应回答：改变了哪个事实源和实现点，什么输入会触发新行为，哪些旧行为必须保持，失败时系统停在哪里，哪些内容刻意不在这次验证内。

## 把自然语言要求转成可验证断言

“证据不足时不要审批”应继续拆解。给定资料 A 可读、资料 B 无可用证据、用户有读取 A/B 的权限，Run 应生成含缺口的草稿；它不应创建审批 Action，也不应调用发布工具。若资料 B 的检索结果未知，则不能把未知伪装成证据不足；应保留查询线索并等待核实或按策略停止。

这类断言把模型生成文本和运行时边界分开验证。文本断言检查是否说明缺口；状态断言检查 Run 是否停在正确位置；副作用断言检查没有发生审批或发布；账本断言检查 Action 和 Attempt 是否留下可追溯记录。每一条都应能指向对应的输入和可观察结果，避免只写“功能正常”。

AI 还可能遗漏并发和重试。若一个旧的审批回调在规则更新后到达，系统仍要先验证它是否对应可审批的冻结事实；不得仅因回调有效就推进状态。若调用结果未知，也不能生成第二个发布 Attempt 来“试试看”。这些约束来自系统契约，不能交给生成模型临场判断。

## 证据要说明证明了什么

交付记录至少区分三类信息。已运行的证据写明实际执行了哪些测试、检查或演练，以及结果覆盖的输入；静态审查记录审查了哪些状态、权限、并发或副作用路径；尚未验证的内容直接写出边界，例如外部审批渠道、特定部署环境或异常恢复分支尚未在本候选中运行。

不要把静态阅读写成“已验证”，也不要用一个局部测试通过暗示所有链路安全。反过来，未覆盖的范围也不意味着候选没有价值；它让后续人员知道还需补哪条证据，并避免把推测当成已知事实。

一个紧凑的候选记录可以包含如下内容：

```text
目标：资料 B 缺证据时阻止审批
输入：A 可读；B 无证据；调用者具有读取权限
断言：生成缺口说明；无审批 Action；无发布 Attempt
已运行证据：对应状态机与组合测试的实际结果
静态审查：权限交集、未知结果、重复回调的处理路径
未验证边界：外部审批服务故障和生产配置
回退范围：恢复上一版模板与规则，不改写既有 Run 账本
```

其中“实际结果”必须来自本次真实执行，不能由 AI 根据代码猜写。记录也应保留失败结果：如果测试发现旧回调仍能触发审批，候选就尚未满足断言，应先修复或明确停止交付。

## 小批次协作降低混淆

把一次改动限制在清楚的行为单元：先完成契约、实现和针对性验证，再扩展到下一条规则。不同人或不同 AI 处理并行任务时，为每个任务固定输入版本、文件边界和交付物；共享的状态机、权限规则和公共接口由明确负责人整合。这样不是为了增加流程，而是避免两个候选对同一条迁移给出互相冲突的修改。

可回滚也需要准确含义。回退代码或模板版本不应删除已发生的 Attempt、已批准记录或外部副作用；这些仍是账本事实。对未知副作用先查询、对重复输入先去重、对权限变化重新检查，才能在修改失败时安全停止，而不是用重放掩盖问题。

练习：为“资料 B 的检索超时，随后收到一个旧审批回调”写一份候选验证计划。分别列出输入、两个必须成立的断言、一项禁止发生的副作用、已运行证据和一个未验证边界。

预期结果：计划会区分“明确无证据”和“结果未知”；旧回调不能让 Run 进入已审批；不会新建发布 Attempt；证据只陈述实际执行过的检查，并明确外部渠道或部署场景若尚未执行。
