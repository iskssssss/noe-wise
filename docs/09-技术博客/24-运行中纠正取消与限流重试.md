# 纠正、取消与重试：让运行中的变化有明确落点

前置阅读：[04 课](04-Agent-Loop的动作观察与模型输出失败处理.md)、[19 课](19-持久化状态机与事实源设计.md)、[20 课](20-幂等外部副作用与未知结果.md)、[23 课](23-单会话多执行输入路由.md)

研究助手正在检索资料，用户说：“不要比较部署成本了，改看更新机制。”几秒后，旧查询返回；与此同时，模型供应商又给出限流响应。把这些事情统一叫“重试”很危险：任务范围变了，旧结果回来了，网络调用还需要等待，它们各自需要不同处理。

运行控制要回答两个问题：新的意图何时生效，已经开始的工作怎样收敛。清楚的版本和动作记录，比一句“遵循用户最新要求”更能说明系统行为。

## 纠正形成新版本，不抹掉已经发生的事

受理纠正后，保存任务版本从 T1 到 T2 的变更，记录新的范围和约束。尚未派发的动作按 T2 重新判断；已发出的动作仍属于 T1，返回时标明它的归属。

旧结果不一定全部无用。原查询若恰好包含更新机制，可以按当前范围重新筛选后使用；如果只涉及部署成本，则留作历史，不能继续支配结论。运行时可以在下一决策点让模型看到当前任务和仍相关的观察，而不是覆盖旧请求，让记录看起来从未改过方向。

冻结请求也不保证一定发送。发送前应再次检查取消、任务版本策略、权限和预算。若 T1 请求尚未发出而已过时，丢弃候选并按 T2 准备，通常比再让它跑完更清晰。

## 取消停止未来动作，不宣称回滚

取消请求可以把 Run 置为 cancelling，停止派发新动作，并尝试中断可取消的调用。已完成的观察仍需保存，已发送的外部写入仍需核对。等受控工作收敛后，再形成 cancelled 或其他明确终态。

“取消成功”在产品界面里最好说明范围，例如“已停止后续工作，发布结果仍待确认”。如果发布请求在取消前已经被对方接收，取消 Run 不会让报告自动消失。撤下报告是另一个有权限与结果的动作。

这里有一个常见竞态：worker 准备提交结果时，用户刚好取消。数据库条件更新决定哪个状态迁移有效，失败的一方重新读取当前事实。模型不能依据自己较早看到的 running 状态覆盖取消。

## 限流重试保持原动作语义

429 或供应商的限流错误通常需要等待，再在截止时间和预算内重试。执行器可以遵循合法的 Retry-After，结合带抖动的退避，避免所有 worker 同时再发请求。具体策略应区分模型调用、只读工具和写入工具。

同一 Action 的重试创建新的 Attempt，保留参数和稳定业务身份。若纠正改变了动作目的，应创建新 Action，不能用原幂等键发送一套不同内容。

预算耗尽、截止时间已到或已取消时，不再调度重试。认证失败、参数错误也不应沿用限流策略。写请求超时属于可能的未知效果，必须先按第 20 课处理，不能因为它“也是网络错误”就进入普通退避队列。

## 在下个决策点更新提示词

模型需要理解变化，但输入应来自已受理的纠正与已提交运行状态。使用时机是纠正、取消或重试结果进入下一轮时，追加以下片段：

```text
[新增：运行控制反馈]
按 current_task_version 的目标和约束推进。
旧观察保留其任务版本；只使用仍适用于当前范围的证据。
取消后说明已完成、已停止和仍待核对的部分，不再主动提出新工作。
限流等待由运行时调度，不通过重复工具动作绕过等待。
结果 unknown 的外部写入如实报告；没有核对依据时不建议盲重发。
```

它的设计目的，是让模型正确消费控制事实，而不是让模型决定取消是否生效。预期行为是改为比较更新机制，说明部署成本已移出范围。失败对照是输出“已经撤销所有操作”，但实际上发布请求仍在对方处理中。

重试也不需要每次向用户发一条进度消息。界面可以归并重复等待，只有状态变化或需要输入时再呈现，后续课程会讨论这种视图处理。

## 排列一次竞态时间线

练习：T1 查询已发送；用户提交 T2；旧查询返回；接着发布请求发出但未收到响应，用户取消。分别写出旧资料、发布动作、Run 和对用户的说明。

预期结果：旧资料保留 T1 来源并按 T2 相关性筛选；发布动作保留未知结果，不能被取消直接改成失败或成功；Run 停止新派发并收敛；说明应区分“研究已停止”和“发布仍待核对”。只有获得对方可确认结果后，才更新效果记录。
