# Inbox 与 Outbox：把本地提交和可靠传递接起来

前置阅读：[19 课](19-持久化状态机与事实源设计.md)、[20 课](20-幂等外部副作用与未知结果.md)

研究助手用两份虚构资料形成内部技术选型报告：A 采用关键词匹配和批次更新，却没有更新延迟数据；B 采用语义检索，却没有更新周期或性能测量。草稿 D1 修订为 D2，发布前必须审批。审批回调可能重复到达，报告待发布事件也可能在发送后丢失确认。若只靠“收到就处理、失败就重发”，重复审批和重复发布迟早会发生。

Inbox 与 Outbox 解决的是两个不同的本地原子性缺口。Inbox 让“记住这个输入已受理”和“应用它产生的业务变化”处于同一事务；Outbox 让“提交业务变化”和“记录必须对外投递的事件”处于同一事务。它们都不把外部系统纳入本地数据库事务，也不承诺任意副作用恰好发生一次。

## Inbox 防止同一输入改变两次状态

假设审批系统发送事件 `approval-82`，内容是“批准报告 D2”。网络重试让同一事件到达三次。受理服务先校验来源身份、签名、目标报告版本和负载指纹，再在一个事务中插入 Inbox 记录并推进等待 D2 的 Run。伪代码示意如下：

```text
begin transaction
  insert inbox(sender, event_id, payload_hash)
    -- sender + event_id 唯一
  assert run.waiting_for == "approval:D2"
  update run with expected version
  record approval fact for D2
commit
```

第一次处理提交后，第二、三次插入命中唯一约束，系统读取原受理结果并返回，不再推进 Run。若进程在事务提交前崩溃，Inbox 与业务变化一起回滚，重投可以重新处理；若在提交后、响应前崩溃，重投会发现已有记录。这正是“同一事务”的意义。

先写 Inbox、再用另一个事务更新 Run 会留下丢失窗口：进程在两者之间崩溃，重投被判定为重复，但审批永远没有生效。先更新 Run、后写 Inbox 则留下重复窗口。把两步放进同一数据库事务，才能使本地受理结果一致。

事件身份还需要作用域。不同发送方都可能使用 `82`，所以唯一键通常包含发送方或通道；同一身份却带来不同 `payload_hash` 时不能按普通重复静默忽略，这意味着上游错误复用了身份或内容被篡改，应拒绝并告警。即使事件身份全新，针对 D1 的迟到批准也不能推进正在等待 D2 的 Run；Inbox 去重不能替代业务版本检查。

## Outbox 防止业务提交后忘记发送

审批 D2 被受理后，本地需要创建“D2 已具备发布资格”的业务事实，并通知发布适配器。如果先提交 Run，随后进程在发消息前崩溃，报告会永远停住；如果先发消息再提交 Run，事务回滚后外部却可能已经发布。

Outbox 做法是在同一个本地事务中更新业务状态并插入待投递记录：

```text
begin transaction
  update action set state = "READY_TO_DISPATCH"
    where action_id = :publish_D2 and version = :expected
  assert affected_rows == 1, otherwise rollback
  insert outbox(event_id, aggregate_id, aggregate_version, payload, state="PENDING")
commit
```

独立 dispatcher 领取 `PENDING` 记录，携带原 `event_id` 投递，收到确定确认后再把它标为已送达。事务回滚时，业务变化和 Outbox 都不存在；事务提交后，即使进程立刻崩溃，另一个 worker 仍能找到待投递记录。Outbox 保存的是已提交事实的传递责任，不是临时拼一条“差不多”的新消息。

## 发送与确认之间仍然不是原子的

dispatcher 可能已经把事件送到接收方，却在标记 Outbox 前崩溃。恢复后它会重投同一个 `event_id`，因此传输语义通常是至少一次。若接收方也是受控服务，它应在同一事务中用 Inbox 去重并完成自己的业务写入；这样重复事件只在接收方应用一次。

如果接收方是外部知识库，Outbox 无法强迫它实现 Inbox。此时仍需要第 20 课的下游幂等键、状态查询或人工对账。把 Outbox 标记为“已发送”只能说明 dispatcher 的本地观察，不能证明外部报告只创建一次。更不能声称“Outbox 与远端发布在一个事务里”，除非双方真的共享一个受支持的事务协议，而这在常见 HTTP 集成中并不存在。

确认本身也要受版本约束。worker W1 领取事件后租约过期，W2 重投并确认成功；W1 随后返回的迟到确认不能覆盖更高版本状态或改写失败诊断。Outbox 记录应通过条件更新确认当前领取权。事件之间有顺序要求时，可按同一业务对象的版本投递，而不要假设整个系统存在全局顺序。

## 一次完整时序

t0，D1 已保存但未审批。t1，审阅者提交修改意见，系统生成 D2 并等待审批。t2，`approval-82` 到达；Inbox 与“D2 已批准”在同一事务提交，同时创建发布 Action 及 Outbox 事件 `publish-D2-11`。t3，审批事件重投，被 Inbox 识别为同一输入，不再创建第二个 Action。

t4，dispatcher 发送 `publish-D2-11`，接收方处理成功，但确认丢失。本地 Outbox 仍为待投递，不能直接声称发布失败。t5，dispatcher 用相同事件身份重投；受控接收方的 Inbox 返回第一次结果，或者外部接收方依据相同幂等键返回原发布记录。确认后，本地才提交送达状态。若接收方无法去重也无法查询，发布 Action 保持 Unknown，不能靠 Outbox 推导成功。

## 代价与边界

Inbox、Outbox 会增加表容量、索引竞争、清理和监控成本。保留期必须覆盖可能的重投窗口；清理过早会让旧事件重新产生效果。大载荷可以放在版本化存储中，Outbox 保存引用与摘要，但 dispatcher 必须能在重投时取回完全相同的有效载荷。积压监控应关注最老未投递时间、重试次数和冲突，而不只是队列长度。

这种模式适合“本地事务 + 不可靠消息或调用”的边界。若全部操作都在一个数据库事务内，直接事务提交即可；若外部系统没有幂等或核对能力，Outbox 只能保证消息不会被本地遗忘，不能解决外部重复效果。

## 小练习

`approval-82` 已在 Inbox 中提交并创建 Outbox 事件 `publish-D2-11`。dispatcher 把事件送达后在写确认前崩溃；与此同时，旧的 D1 批准事件第一次到达。恢复后系统应如何处理？

预期结果：若接收方 Inbox 或幂等契约允许重投，dispatcher 使用同一个 `publish-D2-11`；否则先查询核对原效果，无法确认时暂停有副作用的投递。两条路径都不创建新的发布 Action。D1 批准虽然是新的输入身份，仍因目标版本不匹配而不能推进 Run。D2 的业务状态、Inbox 与 Outbox 各自保持可追溯事实；无法确认外部效果时，发布结果继续为 Unknown。
