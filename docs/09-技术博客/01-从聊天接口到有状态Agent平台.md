# 从一个问题开始：研究助手为什么需要运行状态

前置阅读：具备基本的接口调用与数据处理经验即可。

用户把两份检索方案资料交给助手，希望得到一份供内部技术团队讨论的选型报告。方案 A 强调关键词匹配，方案 B 强调语义检索。资料没有覆盖所有条件，用户也还没有允许助手发布报告。

如果任务只是“概括这两个段落”，一次模型请求可能已经够用。可用户通常会接着问：“刚才提到的更新延迟，有原文依据吗？”又或者：“保留草稿，等我确认范围后继续。”这时，我们需要保存的已经不只是答案。助手必须知道正在完成什么、哪些判断有依据、哪一步还在等待。

这条学习路线从这个小任务开始。后面会加入检索、代码计算、长期记忆、专家分工和审批，但每加入一种能力，都要回答同一个问题：系统如何知道它实际做到了哪一步？

## 给第一版助手划一个小范围

先用两份虚构资料做练习。它们只是教学输入，不代表真实产品能力：

| 来源 | 资料正文 | 可以支持的判断 |
| :-- | :-- | :-- |
| source-a，版本 v1 | 方案 A 支持关键词匹配；索引按批次更新；未提供延迟测量 | 支持关键词查询，更新方式是批次 |
| source-b，版本 v1 | 方案 B 支持语义检索；未提供更新周期或性能测量 | 支持语义查询 |

任务是比较“查询方式”和“更新信息”，给出简短草稿，并指出选型前还缺什么。这里没有足够证据判断谁更快，也没有充分证据判断 B 不支持关键词查询。资料没有提到，不等于能力不存在。

我们可以把成功条件写得很具体：每个重要判断带来源；缺失信息明确留空或说明；不把草稿称为已发布报告。相比“生成一份专业、全面的报告”，这样的要求更容易发现错误。

第一版不需要自动浏览整个互联网，不需要多个 Agent，也不必提前搭建完整平台。把输入、判断和输出的边界走通，就能看出哪些能力确实值得加入。

## 文本之外，还要留下什么

一次模型调用有请求和响应，任务却有目标、证据和进度。把这两种生命周期混在一起，浏览器一断线，系统就只能重新提问。重新提问也许生成相近的文本，却不能证明它延续了原来的任务。

研究助手至少要保留这些事实：

- 用户要比较哪些维度，面向谁，哪些操作还没有授权。
- 本次使用的资料及版本，已经得到的可引用观察。
- 任务处于推进、等待还是结束，等待什么才能继续。
- 已经交付的草稿，以及仍然存在的证据缺口。

这些事实不必一开始就拆成复杂数据库。教学阶段可以先写成结构化记录。真正需要跨进程恢复时，再为它们确定持久化方式。

下面是示意记录，不是可直接对接的 API：

```json
{
  "goal": "比较方案 A 与 B，形成内部选型报告草稿",
  "scope": ["查询方式", "更新信息"],
  "sources": ["source-a@v1", "source-b@v1"],
  "constraints": ["重要判断附来源", "发布前等待审批"],
  "status": "draft_ready",
  "missing": ["可比较的延迟测量", "方案 B 的更新周期"],
  "published": false
}
```

这里的 draft_ready 只是教学状态。它表达“草稿已经形成”，没有暗示“任务所有问题都已解决”。后面引入运行对象时，我们会让任务状态、文档状态和发布状态各自承担明确责任。

## 模型负责建议，运行时负责让事情发生

模型可以建议“读取原文”或“发布报告”，但建议不能直接成为已经执行的事实。运行时是接收候选动作、验证条件、调用能力并记录结果的程序。

这个分工在只读问答里也有用。模型引用了 source-c，程序可以发现它根本不在资料清单里；模型给出了合法的 JSON，程序仍不能据此断言内容正确。格式检查处理字段问题，证据核对处理结论问题，授权检查处理动作能否发生的问题。

一个简化的推进过程可以写成伪代码：

```text
task = accept_user_request()
view = assemble(task, supplied_sources)
candidate = ask_model(view)
if candidate has invalid source references:
    return a bounded correction request
save draft and unresolved questions
show draft with publication_status = not_published
```

这段伪代码没有自动审批、网络重试或后台调度。它只是把“模型生成了什么”和“应用确认了什么”分开。后续课程会逐项补齐，避免在第一课就让读者背负所有工程问题。

## 失败也是结果的一部分

假设资料 B 无法读取。助手仍可以概括 A，并说明 B 的比较暂时缺失；它不能把读取失败解释成“B 没有相关能力”。假设用户又发来一句“按最新版本比较”，旧草稿也不能原样改个日期继续交付，需要重新确定资料版本。

我更倾向于把这些缺口直接放进任务结果，而不是藏进日志。这样，用户知道要补什么，后续运行也知道从哪里接手。日志帮助开发者查原因，任务记录帮助系统继续工作，两者面向不同的问题。

小型问答工具未必需要完整状态机。判断依据是任务是否跨请求、是否存在等待、是否触发外部效果，以及用户是否需要恢复。只有一次无副作用的文本转换，简单请求响应仍然很好用。

## 动手写第一份比较草稿

练习：只使用上表两份资料，写出“查询方式、更新信息、待补证据”三个部分。然后假设页面断开，再列出恢复任务所需的最小记录。

预期结果：A 的关键词匹配和批次更新分别引用 source-a@v1；B 的语义检索引用 source-b@v1；不能出现“B 比 A 快”或“B 不支持关键词”的断言。恢复记录应包含目标、范围、资料版本、草稿和缺口，发布状态仍为未发布。我们此时得到的是一次受控资料问答，距离可恢复的完整助手还有清晰可见的几步。
