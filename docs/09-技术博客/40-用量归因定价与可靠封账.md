# 用量归因、定价与可靠封账

前置阅读：[33 Agent Runtime 的微内核与插件边界](33-Agent-Runtime的微内核与插件边界.md)、[38 多租户与服务身份权限范围](38-多租户与服务身份权限范围.md)、[39 全系统时间契约与时区处理](39-全系统时间契约与时区处理.md)。

> 按需进阶：只有报告助手开始面向多个团队实施配额、成本分摊或计费时，才需要本课的封账细节。

研究与报告助手为内部团队比较方案 A/B：A 使用关键词匹配并支持批次更新，B 使用语义检索但缺少更新信息。报告发布前必须审批。一次 Run 可能经历检索、模型生成、重试和导出；报告最终未获发布审批，也不代表外部服务没有产生用量。

本文所有案例、字段、价格和伪代码均为教学示意，不代表任何具体系统的当前行为。

## 先记录事实，再解释价格

原始用量是已经观察到的事实，例如输入与输出 token、检索单位、计算秒数、生成页数和供应商接收时间。预算估算是调用前对未来消耗的预测。两者必须分开：估算可以保守地预留额度，最终结算只能依据确认的用量事实与适用规则，不能把预留额当成真实消费。

Run 是一次任务推进，Action 是“检索 A 资料”或“生成报告”这样的动作，Attempt 是一次具体调用尝试。每条用量应能追溯到租户、Run、Action、Attempt、计量项、服务版本、发生时间和来源。重试产生新的 Attempt；第一次超时且结果未知时，不能因为第二次成功就删除第一次，也不能把未知费用填成零。

供应商可能重复投递同一计量记录，因此需要稳定使用键，而不是依靠“这批消息刚处理过”的内存状态。一个示意键可以由 `tenantId + provider + providerRecordId + meter` 组成；同一回调重放得到同一键并被幂等忽略，不同重试的供应商记录 ID 不同，仍会保留为两条事实。Attempt ID 本身不足以区分一次调用中的 token 与图像等多个计量项。

以下 JSON 是一条用量事实示意，语法有效：

```json
{
  "usageKey": "tenant-a|provider-x|record-771|search_unit",
  "runId": "run-compare-a-b",
  "actionId": "action-search-b",
  "attemptId": "attempt-2",
  "meter": "search_unit",
  "quantity": "8000",
  "observedAt": "2026-09-30T10:15:00Z",
  "status": "CONFIRMED"
}
```

数量和金额宜用十进制定点值。浮点数可能在聚合时制造无法解释的分币差异；不同币种也不能直接相加。

## 定价必须固定版本、币种和期间

定价是对用量事实的解释，可表示为 `quantity × pricePlan@version`。价格版本要说明计量单位、适用起止时间、币种、精度和舍入规则。单价可以小于最小货币单位，因此通常先以足够精度计算明细，再按已定义规则舍入；不能让数据库、后端和页面各自舍入一次。

结算期间应使用明确的半开区间，例如 `[2026-09-01T00:00:00Z, 2026-10-01T00:00:00Z)`。恰好位于右边界的记录进入下一期，避免两个期间重复纳入。若需要汇率换算，汇率来源、时间和版本也属于定价事实；否则应保留原币种分别汇总。

预算控制发生在调用前：模型 Action 预计需要 5 元，可以先预留 5 元；实际确认 3.60 元后结转真实用量并释放差额。若外调结果未知，预留可以继续占用或进入待核实状态，但不能自动记为 0 元。取消 Run 也只阻止后续调用，已经被供应商受理的 Attempt 仍可能收费。

## 封账固定快照，不改写历史

封账应固定租户、结算期间、纳入的稳定使用键、价格版本、币种规则以及未知项清单。对同一快照重复执行必须产生同一结果，重复消息不能再次计费。封账记录应能回答“这笔金额由哪些事实和哪版价格得出”，而不是只留下一个总额。

迟到记录可能在封账后才到达，例如语义检索供应商隔天才确认用量。此时不能重写已封账总额或伪造原记录当时已知。系统应创建引用原期间和原用量键的调整记录，按明确规则进入调整单或后续结算期；原封账快照保持不变。争议、退款也应通过相反方向的调整留痕，而不是删除事实。

纳入封账的用量项还应区分 `CONFIRMED`、`UNKNOWN`、`NON_BILLABLE` 等语义。只有供应商或合同规则明确证明不计费时才能标记 `NON_BILLABLE`；网络超时、回调丢失和字段缺失都属于未知，不能用零值掩盖信息缺口。

报告助手的状态推演如下：A 的关键词检索已确认用量；B 的语义检索返回了内容，却缺少计量回执，因而费用未知；生成报告消耗已确认；审批人拒绝发布，因为 B 缺少更新机制说明。发布被拒不回滚前三项用量，封账也不改变审批结论。

## 计费不是支付闭环

用量归因、定价、封账解决“谁在何时消耗了什么、按哪版规则得到多少金额”。开票、税务、收款、退款到账、坏账和支付渠道对账属于另一套业务闭环。封账成功不能宣称已经收款，支付失败也不应改写原始用量。系统可以把封账结果交给支付域，但要用明确接口和状态衔接。

## 小练习：算出封账与迟到调整

教学设定使用 CNY 价格计划 `plan-v3`：关键词检索每单位 0.01 元，导出每份 0.50 元，语义检索每单位 0.0002 元。期间内有三条记录：A 检索 200 单位且已确认；B 语义检索用量未知；导出 3 份且已确认。同一导出记录又以相同 `usageKey` 投递一次。封账后，B 的 8000 单位用量才确认。

预期结果：重复导出记录只纳入一次；封账时已知小计为 `200 × 0.01 + 3 × 0.50 = 3.50` 元，并保留一个未知项，不能显示为“总费用 3.50 元且已完整确认”；迟到的语义检索形成 1.60 元调整并引用原期间，原封账快照不变；是否已开票或收款无法由这些记录推出。
