# Agent Loop：每一轮都要知道为什么继续

前置阅读：[02 课](02-Session-Run与Execution为什么需要分开.md)、[03 课](03-提示词设计总览分层组装与验证.md)

研究助手读完资料后，发现 B 的更新机制缺失。它可以查资料、询问用户、等待已有流程，也可以交付带缺口的草稿。哪一种才是正确的下一步？

Agent Loop 的难点不是写一个 while 循环，而是让每次继续都有新的依据，让停止也能准确表达任务状态。模型提出候选动作，运行时验证并执行，结果成为下一轮可以消费的 Observation。

## 从候选到观察，中间隔着执行边界

这里把 Observation 理解为动作产生的观察记录，包括状态、数据、来源引用和错误信息。它可以告诉模型“读取失败”，也可以告诉模型“成功读取但没有匹配内容”。两者不能合并为一句空字符串。

一次受控推进的伪代码如下：

```text
while run is eligible to advance:
    view = assemble(committed_observations, current_task, allowed_tools)
    candidate = model_decide(view)
    decision = validate(candidate, permissions, remaining_budget)
    if decision is invalid:
        record_validation_feedback()
        continue only if correction budget remains
    action = record_action(decision)
    outcome = dispatch_or_wait(action)
    commit_observation(action.id, outcome)
    stop, suspend or advance according to committed state
```

记录动作与执行外部请求不可能凭这段伪代码自动获得原子性。遇到发送后无回包，需要后面的未知结果处理。本课先建立一个前提：模型看到的“已完成”，应来自已提交结果，而不是自己上一轮写下的计划。

## 让模型选择不同的出口

接在第 03 课基础模板后，我们增加一段“本轮决策”说明。使用时机是每次选择下一动作前；输入来自当前任务、工具注册表、已提交 Observation 和运行时预算。

```text
[新增：本轮决策]
已有证据足以回答当前范围时，交付结果并结束本次推进。
缺少必要资料且有匹配的可用工具时，提出一次有明确目的的工具动作。
缺少会改变任务范围或结论的用户条件时，提出最少的澄清问题。
已存在等待中的审批或子任务时，引用对应等待目标，不重复创建。
读取 Observation 的 status 后再解释 data：
  success_empty 不等于 failed；unknown 不等于 failed 或 succeeded。
相同查询没有带来新证据时，改变有依据的查询条件、说明缺口或停止。
只能按提供的 schema 输出候选，不自行补造工具名和成功结果。
```

设计这段说明，是为了把“继续工作”拆成可区分的选择。澄清需要用户提供条件，等待需要已有外部任务完成，工具调用需要有获取信息的目的。把它们都写成“继续检索”，容易产生重复工作。

预期行为是：B 的更新机制缺失且存在资料搜索工具时，查询 B 的更新文档；如果工具返回没有匹配，助手可以调整有效关键词或说明缺口。失败对照是机械重发同一查询，然后把多次空结果包装成“已完成全面验证”。

## 非法输出不能靠猜测修好

模型可能引用未注册工具、漏掉必要参数，或给出不完整 JSON。运行时应返回结构化校验反馈，例如“缺少 query”，再按有限纠错预算允许重选。它不能从自然语言里猜出一个 URL 并直接执行。

流式输出更容易诱发抢跑。收到半截参数时，界面可以展示生成进度，执行端必须等完整结构通过校验。若连接中断，半截候选只用于诊断，不能成为一次已经开始的工具调用。

纠错也要消耗预算。模型连续两次输出不存在的工具，并不证明第三次一定会成功。具体上限由系统配置；达到上限后保留失败原因，向用户说明当前无法继续，不把解析失败误报成资料不足。

## 无进展不等于任何重复都错误

显式轮询审批状态可能合理，重复读取一个稳定文档也可能服务于不同片段。无进展判断应结合动作目的、参数、观察变化和等待策略，而非只按字符串相同就取消任务。

研究助手连续查询三次相同条件，拿到同一份资料，却仍声称“继续深入分析”，通常没有新增证据。运行时可以检测这类重复，并要求模型交付现有结果或说明阻塞。对轮询则使用明确间隔和截止条件，避免让模型自己忙等。

达到轮次或时间上限也不必把所有工作丢弃。已有可核验结果可以交付，但应清楚写出未完成部分。运行状态结束，和研究问题得到彻底解决，是两个不同判断。

## 走一遍失败分支

练习：给 Loop 连续输入三个事件：查询 B 返回 success_empty；模型提出不存在的 publish_now 工具；纠正后模型请求用户补充 B 的更新文档。写出每一步系统和模型各自应做什么。

预期结果：空结果作为观察保留，不能推断 B 不支持更新；非法工具在执行前被拒绝，只产生校验反馈；澄清动作进入有明确问题的等待状态，助手说明目前能比较查询方式、尚不能比较更新及时性。没有发布发生，也没有把等待描述为完成整份选型报告。
