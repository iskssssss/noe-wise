# 聊天历史重建：刷新页面后，助手做过的事还在

前置阅读：[19 课](19-持久化状态机与事实源设计.md)、[22 课](22-审批回调与挂起恢复.md)、[27 课](27-从临时文件到正式成果产物生命周期.md)、[29 课](29-REST-SSE-Webhook与断线恢复.md)

研究助手在页面上依次显示“读取资料”“核验引用”“等待审批”。用户刷新后，只剩一条最终回答，待办卡片消失了。另一种错误更隐蔽：页面保留了旧的“正在检索”，而后端早已结束。

聊天界面需要表达任务过程，但过程不应只保存在组件内存里。用户刷新、换设备或离线重连后，应该能够从持久事实重建同一任务，而不是重播一次模型来猜回原来的界面。

## 消息、运行和临时文本分开存放

用户消息表达输入，助手消息表达可交付文本；Run、Action、Execution 和产物记录表达执行事实。它们有关联，却不是同一张“消息表”可以随意替代的东西。

模型流式 token 可以立即展示为临时草稿。只有完整结果通过校验并提交后，才成为历史中的正式回答。工具候选也类似：界面可以显示“正在准备调用”，但不能提前写成“已查询成功”。

可以给界面一个明确的投影规则：

| 事实或信号 | 页面展示 | 刷新后的依据 |
| :-- | :-- | :-- |
| 未提交的文本片段 | 正在生成的草稿 | 可丢弃或按独立策略恢复，不冒充最终消息 |
| 已提交 Observation | 工具结果摘要与证据入口 | 动作及观察记录 |
| 待审批 Execution | 对应版本的待办卡片 | 当前流程与审批状态 |
| 已确认产物 | 成果卡片 | 产物版本与访问状态 |

Run 的终态不能仅靠一条“完成”文本推断。模型也可能在表达未来计划时使用这个词。页面读取结构化状态，文本只负责解释。

## 用快照构建，再应用增量

初次进入页面时读取当前 Session、相关 Run 与快照水位；随后按第 29 课的方法接续事件。事件归并器按稳定 ID 去重，按对象版本判断是否过期，遇到缺口触发重新同步。

以下是投影逻辑伪代码：

```text
apply(event):
    if event.id already seen: ignore
    if event.object_version <= local_version: ignore stale update
    if event depends on an unknown earlier state:
        request snapshot or missing range
    otherwise:
        update the matching object view
        record applied event identity
```

并非所有系统版本都严格连续，也不是所有事件都包含完整对象。具体协议需要说明“跳过某个版本是否安全”。若事件只是差量，漏一条就可能破坏状态；若它携带完整快照，可以按版本替换。前端不能自行猜测。

分页历史还要区分“某页完整”和“整个会话完整”。用户已经展开较早消息后，发送新消息或收到运行完成事件所触发的最新页刷新，不应让这些记录消失。机构调试页按消息身份和版本合并已加载内容，保留最早分页位置；较早页只补消息，不用旧页附带的运行投影覆盖当前待办。真正切换会话时才重新建立集合，当前权限与保留规则仍继续约束披露。单纯不在最新页中，不能证明旧消息已被删除。

聊天顺序也不一定等于网络到达顺序。输入时间、业务因果和展示排序各有用途。子任务结果比父任务卡片更早到达时，可以暂存关联或读取快照，不要把它挂到“当前看起来最近”的运行上。

## 等待卡片应引用对象，而不是一段文案

审批卡片绑定 approval_id 和 D1。用户修订为 D2 后，卡片需要显示过时、已撤回或仍只针对 D1 的状态。按钮发出的命令携带目标与期望版本，后端核对后再更新页面。

如果点击后网络超时，界面可以显示“正在确认”，不能立即假定批准失败并创建新请求。重新查询状态或按命令幂等规则重试，才能避免双击与重连造成重复控制动作。

多 Run 会话中，工具进展、澄清与成果卡片都应保留 Run 归属。否则 R2 的检索失败可能把 R1 已完成的报告标为失败，用户也无法理解自己需要回应哪项待办。

## 重建历史不等于展示所有内部数据

用户需要知道用了哪些资料、什么动作失败、报告为何尚未发布。原始凭据、完整检索敏感正文和不必要的内部调试信息不应直接渲染。模型的隐藏推理也不是聊天重建所需的证据；简短依据和可核验动作已经能解释关键过程。

历史访问还要遵守当前权限。曾经有权读取一个附件，不意味着失去权限后页面仍可从旧缓存无限展示全文。产品可以保留“曾使用某来源”的审计元数据，同时限制内容披露。

持久过程越细，存储和界面复杂度越高。无需把每个 token 都永久保存，但控制决定、稳定结果和交付状态不能只留在动画里。

## 刷新前后核对同一事实

练习：页面先收到 D1 待审批事件，再收到已批准与发布确认；网络重连后重复收到待审批事件。写出最终卡片状态，并说明刷新如何恢复。

预期结果：较旧事件不能让已发布对象倒退成待审批；页面显示已确认的产物及其范围，不重复出现有效批准按钮。刷新从持久快照与事件水位重建，用户无需重新提交研究任务。尚未提交的流式草稿可以消失，但不能因此丢掉已确认的发布事实。
