# 全系统时间契约与时区处理

前置阅读：[38 多租户与服务身份权限范围](38-多租户与服务身份权限范围.md)。

研究与报告助手在周五完成方案 A/B 比较：A 使用关键词匹配并支持批次更新，B 使用语义检索但缺少更新信息。报告只供内部团队使用，发布前必须审批。如果页面、worker 和数据库各自解释“周一 09:00 到期”，同一审批可能在一个节点有效、另一个节点过期。

本文所有案例、字段与代码均为教学示意，不代表任何具体系统的当前行为。

## 四种时间类型解决四类问题

`Instant` 表示时间线上的唯一瞬间，适合记录 Run 创建、Action deadline、回调接收、租约到期和审计时间记录。它通常以 UTC 持久化和交换，例如 `2026-11-01T05:30:00Z`。UTC 是存储与传输约定，不是用户的日历语言。时间戳可以帮助排序，但相同时间或时钟偏差意味着它不能替代事件序号与因果关联。

`LocalDateTime` 只有年月日时分秒，没有时区和偏移。它适合接收“团队当地周一 09:00”这类尚待解释的输入，但不能直接表示全球唯一到期点。`LocalDate` 只表示日历日，例如“资料发布日期”或“结算日”，不能擅自补成服务器默认时区的午夜。

`ZonedDateTime` 把本地日期时间、地区时区及其规则结合起来，适合在系统边界把日历约定解析成 `Instant`，也适合展示。保存长期计划时应保留地区时区标识，如 `America/New_York`，因为 `-05:00` 只是一次偏移，不能表达未来夏令时变化。状态机最终比较解析后的 `Instant`，界面再按团队时区转换。

## 从输入到状态判断只解析一次

假设甲团队在上海查看报告，审批规则却由纽约团队日历定义。受理层收到本地截止时间和 `America/New_York` 后，先按明确规则解析为唯一 `expiresAt`，再以 UTC 写入。随后排队、重启和跨节点执行都传递这个绝对时刻，不能让每个节点用自己的默认时区重新计算。

以下 JSON 是持久化记录示意，语法有效：

```json
{
  "requestedAt": "2026-10-30T08:30:00Z",
  "expiresAt": "2026-11-01T05:30:00Z",
  "scheduleZone": "America/New_York",
  "requestedLocalTime": "2026-11-01T01:30:00",
  "overlapPolicy": "EARLIER_OFFSET",
  "decidedAt": "2026-11-01T01:20:00-04:00",
  "receivedAt": "2026-11-01T05:21:04Z"
}
```

`decidedAt` 是外部系统声称审批发生的业务时间，`receivedAt` 是本系统真正收到回调的事实。两者都要保留；是否接受回调应使用可信接收事实、当前状态和 `expiresAt`，不能让调用方提交一个较早的 `decidedAt` 绕过过期判断。

按案例推演：Run 受理时生成 `requestedAt`，提交审批 Action 时解析并冻结 `expiresAt`；消息排队只改变实际处理时刻，不延长截止点；回调到达时先写 `receivedAt`，再比较当前状态和到期点；通过后启动发布 Action，并为发布结果另记时间。若服务在等待期间重启，它从持久化时间点恢复，而不是用“启动后再等两天”重新计算。这样，方案 B 的更新信息即使后来补齐，也只能形成新的评审或版本，不能倒改原审批在当时是否过期。

## 夏令时必须显式处理

地区时区会产生不存在和重复的本地时间。纽约春季跳时日的 `02:30` 不存在；秋季回拨日的 `01:30` 对应两个 Instant。解析 API 若悄悄顺延或任选一个偏移，审批期限就会随语言库、版本或节点变化。

业务应选定可审计策略。例如：不存在时间直接拒绝并要求重新选择；重复时间必须让规则指定 `EARLIER_OFFSET` 或 `LATER_OFFSET`，同时保存原始输入、时区、采用的偏移和解析结果。上例选择较早偏移 `-04:00`，所以得到 `2026-11-01T05:30:00Z`；选择较晚偏移则会得到 `06:30:00Z`，两者相差一小时。

## 墙上时钟与单调时钟各司其职

单机进程测量一次模型 Attempt 耗时，应使用单调时钟，因为系统校时不会让“已耗时”倒退。单调计数只在当前进程内有意义，不能写进消息后让另一台机器判断分布式租约，也不能跨进程重启比较。

分布式租约、审批到期和跨节点 deadline 必须使用可共享的权威时间语义，例如由一致的服务端时钟生成并持久化为 Instant。节点仍需考虑时钟偏差和数据库精度，采用明确的续租余量与条件更新；不能把本机单调计数冒充全局时间。

外部时间缺少时区、远超允许偏差或格式非法时，应拒绝或标为未验证元数据；未知值不能由服务器默认时区静默补全。定时任务重复触发时，使用稳定计划实例身份去重，而不是比较“是否在同一分钟”。

## 固定时钟让边界测试可重复

测试不应等待真实时间经过。把时钟作为依赖传入，用固定 `Instant` 验证到期前、恰好到期和到期后的状态，再单独测试时区解析器的 DST 策略。若规则是 `now < expiresAt` 才可审批，则 `now == expiresAt` 的预期必须是拒绝。

示意伪代码如下，其中 `clock` 可在测试中固定：

```text
now = clock.instant()
if now >= approval.expiresAt:
    reject("APPROVAL_EXPIRED")
else:
    acceptDecision()
```

## 小练习：解析并判断两个时间

教学设定采用上述策略：DST 缺口拒绝，重叠时间选择较早偏移；审批只在 `now < expiresAt` 时有效。请处理纽约时区的 `2026-03-08T02:30:00` 与 `2026-11-01T01:30:00`，并用固定时钟 `2026-11-01T05:30:00Z` 判断第二个审批是否可接受。

预期结果：三月输入因当地时间不存在而拒绝；十一月输入解析为 `2026-11-01T05:30:00Z`；固定时钟恰好等于 `expiresAt`，因此审批过期。换到任何服务器默认时区，三个结果都不应变化。
