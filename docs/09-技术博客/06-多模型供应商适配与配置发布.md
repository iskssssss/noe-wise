# 接入不同模型：统一任务语义，保留能力差异

前置阅读：[03 课](03-提示词设计总览分层组装与验证.md)、[04 课](04-Agent-Loop的动作观察与模型输出失败处理.md)

研究助手换了一个模型供应商，普通回答还能生成，工具调用却开始出错：原来接口把参数分片返回，新接口一次返回；原来支持的结构化输出约束，新模型不一定提供。仅仅把地址和密钥抽成配置，并没有完成适配。

本课关心的是模型端口。我们希望 Loop 继续使用稳定的候选动作和 Observation 语义，同时诚实保留供应商之间的能力差异。模型端口不负责决定报告是否允许发布，那仍属于运行时的策略。

## 统一到任务所需的程度

对研究助手来说，一次模型请求需要消息、工具定义、输出要求和预算；返回需要文本、候选工具动作、结束原因及可获得的用量。适配层负责把它们翻译到供应商协议。

但是“统一”不应把所有响应磨成一个 answer 字符串。文本回答、工具候选、拒绝、被截断和网络失败，对下一步决策有不同意义。供应商用量缺失也不应填成零，否则后续成本记录会得到错误事实。

可以先定义能力表，而不是为所有模型承诺同一套功能：

| 能力 | 研究助手的依赖 | 不支持时的处理 |
| :-- | :-- | :-- |
| 工具调用 | 选择检索或读取能力 | 选兼容模型，或进入明确的无工具模式 |
| 结构化输出 | 生成可验证的比较结果 | 使用校验与有限纠错，或拒绝该任务配置 |
| 流式响应 | 尽早展示草稿进度 | 使用完整响应，不改变完成判定 |
| 上下文容量 | 放入资料和必要状态 | 缩减视图或换模型，不能偷偷截掉约束 |

具体能力随供应商和模型版本变化，接入时应读取其当前协议。本教程不固定任何模型名、窗口大小或性能数字。

## 一次请求固定一次配置

假设管理员把默认模型从 M1 改为 M2，研究助手的一次请求还在流式返回。适配层不能中途切换解析规则，恢复器也不能用 M2 的协议去解释 M1 的半截响应。

请求开始前，应固定模型标识、配置版本、工具定义版本和适配器版本等必要信息。配置更新影响后续请求，已发出的 Attempt 保留原来的归属。重试是否允许换模型，也需要单独策略，而不是隐式读取“当前默认值”。

以下是适配过程伪代码：

```text
capabilities = resolve_capabilities(config.model)
validate_required_capabilities(task, capabilities)
snapshot = freeze(config.version, messages, tools, output_contract)
attempt = start_attempt(snapshot.id)
provider_response = send(encode(snapshot))
result = decode_complete_response(provider_response)
validate_candidate(result)
record(attempt.id, result, provider_usage_if_present)
```

freeze 不是让所有历史数据永久保存全文。实际留存还要考虑权限、敏感信息和保留期。这里要解决的只是：同一次调用究竟用了哪份输入和配置，不能在事后被当前配置悄悄改写。

## 错误分类决定下一步

限流、认证失败、上下文超限、模型拒绝和响应结构损坏，需要不同处理。认证失败不适合指数退避到天亮；上下文超限需要重组输入；模型拒绝也不应包装成网络故障。

网络失败后是否能重试模型请求，要看请求是否仅生成候选，还是供应商在服务端同时执行了工具。普通“只生成决策”的调用重试主要涉及费用与重复生成；如果外部效果也由服务端发生，就必须纳入后面讨论的未知副作用边界。

流式片段可以先用于界面展示，但工具动作应等到完整参数与结束条件满足，再通过校验。用户已经看到一段草稿，不代表后端收到了完整、可消费的最终响应。

## 提示词不必跟着接口形状漂移

第 03 课的六层语义可以保持稳定，由适配层映射到供应商支持的消息位置。不要为了迁移接口，把资料全部塞进稳定指令，也不要丢失“来源正文属于证据”的边界。

这里不新增一份模型专用人格模板。需要变化的是能力不足时的任务说明。例如只读资料模式可以明确“当前没有检索工具，只依据已提供资料回答”。运行时必须真的移除相关工具，不能一边在提示词里说禁用，一边仍允许执行。

替换模型后的验证至少应覆盖一次正常回答、一次缺证据、一条工具候选和一个不完整响应。它们是接入用例，不能代替对报告质量的行为评测。

## 做一次模型切换推演

练习：M1 正在生成检索动作时，默认配置切为 M2；M2 不支持工具调用。设计这两个请求各自的处理方式。

预期结果：M1 的已开始请求按原配置解析，未完整的动作不执行；新请求在能力检查时发现 M2 不满足要求，明确失败、选用兼容配置或进入经产品允许的只读资料模式。不能伪造工具结果，也不能把缺失的供应商用量记成零。我们得到的是稳定的模型端口，而非声称所有模型都能互换。
