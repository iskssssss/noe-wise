# 知识检索要固定版本，也要能解释证据从哪里来

前置阅读：[03 课](03-提示词设计总览分层组装与验证.md)、[11 课](11-模型上下文视图与冻结请求.md)、[13 课](13-Token预算压缩与历史摘要.md)

研究与报告助手用两份教学构造资料比较检索方案：`source-a@v1` 支持关键词匹配和批次更新，没有延迟测量；`source-b@v1` 支持语义检索，没有更新周期或性能测量。报告供内部技术团队选型，发布前必须得到用户审批。

如果知识库第二天更新，昨天的报告还能复核吗？只在正文末尾写“来自知识库”远远不够。检索时需要固定资料版本和检索集合，命中时需要保留片段身份，写报告时还要记录每个判断引用了哪些命中。

## “查询当前资料”和“重放旧证据”是两种动作

面向新问题，用户可能希望检索当前已发布资料；恢复旧 Run，则通常要继续使用当时固定的版本。两种模式都合理，但必须显式选择。

假设第一个 Run 固定读取 `source-a@v1` 与 `source-b@v1`。后来新增 `source-b@v2`，其内容也是本文为讲解版本变化而构造的教学资料，说明“按批次更新，每周重建语义索引”，仍没有性能测量。恢复第一个 Run 时，不能用 v2 补上 v1 的更新周期；新的 Run 可以明确比较 `source-a@v1` 与 `source-b@v2`，并说明新增结论来自版本变化。

版本固定不能只靠一句提示词。检索 Action 应把集合快照或明确版本作为受控参数，检索适配层拒绝不存在或无权读取的版本。模型只能提出候选；权限、预算、版本可见性、幂等键和审批状态由运行时检查。

来源范围与返回数量是两件事。机构管理页的检索验证在未指定本次条数时沿用知识库的已保存条数，再由运营默认补足；Agent Runtime 的知识调用则使用当次冻结的条目和字符预算，不把管理页默认条数当成运行上限。比较两次召回结果时应同时核对实际来源范围和条数预算，不能把因数量限制未返回的片段解释为固定资料中不存在。

## 查询围绕缺口，而不是围绕预期答案

助手要补的是 B 的更新机制，应查询“更新周期、索引刷新、增量更新”等与缺口相关的概念，而不是只搜“B 实时更新的优势”。后者先假定结论，再挑选支持它的材料。命中后还要核对范围：测试环境的一次试验，不能直接说明生产环境的更新保证。

若同一适用范围内两份文档互相矛盾，按已给出的发布状态、生效时间和替代关系判断。仅看文件名更新或检索得分较高不足以裁定。无法确认时同时保留冲突引用，列出需要核实的条件；权威替代关系明确时则采用有效版本，不必永远停在冲突上。

## 一条可追踪证据包含什么

下面是检索命中的 JSON 示意，不是通用接口：

```json
{
  "query_action_id": "action-query-b-v1",
  "attempt_id": "attempt-1",
  "query": "更新周期 性能测量",
  "retrieval_mode": "pinned",
  "corpus_snapshot": "snapshot-2026-09-30-01",
  "hits": [
    {
      "source_id": "source-b",
      "version": "v1",
      "chunk_id": "chunk-b-07",
      "location": "section:capabilities",
      "text": "支持语义检索。",
      "score": 0.78
    }
  ]
}
```

`score` 只表示检索器对当前查询的排序信号，不证明内容正确，也不能拿来比较 A/B 的性能。`chunk_id` 和 `location` 让系统回读原文，`corpus_snapshot` 说明这次查询在哪个发布集合上运行。最终报告的“B 支持语义检索”可以引用该片段；“B 没有更新周期”则要谨慎表述为“现有 v1 证据未提供更新周期”，不能把未命中当成能力不存在。

证据链还应能回答：用户提出什么目标，模型建议了哪个查询 Action，哪个 Attempt 执行，工具返回哪些命中，报告哪句话使用了哪个片段。无需向读者暴露所有内部事件，但系统必须能从引用回到被冻结的证据。

## 把版本和缺口加入本轮提示词

以下片段在检索 Observation 被加入模型视图时使用。版本、快照和命中元数据来自检索适配层，报告范围与用户要求来自当前 Run。

```text
[新增：版本化证据使用]
查询围绕当前缺口组织，不把待验证结论写成前提；读取后核对环境、范围和生效条件。
同范围来源冲突时核对有效性与替代关系；仍无法裁定则并列引用并说明待确认条件。
仅把明确返回的 source_id、version、chunk_id 与 text 用作资料证据。
retrieval score 是排序信号，不代表事实可信度或方案性能。
未命中只说明本次查询在固定集合中没有返回材料，不等于相关能力不存在。
报告中的重要判断应引用实际命中版本；不得以较新版本替换已固定版本。
若 pinned 版本不可读，报告证据缺失；若任务要求 current，则明确列出本轮实际解析出的版本。
新增版本改变结论时，说明变化来自哪条新增材料，并继续遵守发布审批状态。
```

设计这段增量，是因为模型很容易把“排名更高”误写成“方案更好”，也容易在恢复时自然地采用最新文档。预期行为是先陈述可证实能力，再列出更新周期和性能测量的缺口。失败对照是用 B 的语义命中分数证明 B 性能更快，或把教学构造的 b@v2 周更信息倒填进 b@v1 报告。

## 版本失效时不要静默降级

文件成功上传也不等于已经成为可检索证据。例如空白文本可以完成文档创建，却没有形成分块，来源仍为失败状态。此时应补充原文并保存，确认新来源 ready 后明确选择该版本发布，而不是对空内容反复重试索引。上传回执保留原文档身份，重读回执不会重新上传；具体恢复流程见[知识存储治理](../02-架构与设计/20-知识不可变内容与存储治理.md#1-正文所有者与版本)。

固定版本可能因原文存储异常而暂时不可用，也可能因当前主体权限变化而不可读。前者意味着旧证据暂时无法重新展示，后者意味着当前请求不得访问；两者都不允许自动查询最新版并保留旧引用。当前[知识存储治理](../02-架构与设计/20-知识不可变内容与存储治理.md#4-历史回收)没有知识历史默认 TTL，仍保留的 Runtime 冻结引用会保护来源与正文，正常回收不会删除这些材料。出现不可读情况时，应明确区分证据不可用与访问被拒绝，让模型报告缺口、请求用户选择新 Run，或停止。

索引更新也会制造隐蔽漂移。即使源文件版本号没变，分段算法、过滤规则或嵌入模型变化都可能改变命中集合。需要严格复核时，应固定可解释的语料快照和片段身份；重新构建索引后得到的新命中属于新的检索证据，不应冒充旧 Attempt 的结果。

报告可以在证据缺失时交付草稿，但必须降低主张强度。例如，A/B 查询能力已有直接材料，性能优劣则没有。是否允许发布一份带缺口的报告是用户决策；模型只能提出发布 Action，运行时依据当前审批事实决定是否执行。

## 练习：旧 Run 遇到 B 的新版本

旧 Run 已引用 `source-b@v1`，随后知识库发布了上述教学构造的 `source-b@v2`，同时模拟原文存储异常导致 v1 暂时无法回读。请分别设计“恢复旧报告”和“重新比较当前资料”的行为。该故障情境不代表正常保留策略会删除已冻结来源。

预期结果：恢复路径保留 v1 引用并标记原文不可用，不用 v2 替换；重新比较路径创建新的 Run 和检索 Action，明确使用 b@v2，并把“按批次更新，每周重建索引”标成新版新增信息。两条路径都不得虚构性能测量，任何发布仍等待用户审批。
