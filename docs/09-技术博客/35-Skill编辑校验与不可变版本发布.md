# Skill 编辑校验与不可变版本发布

前置阅读：[33 Agent Runtime 的微内核与插件边界](33-Agent-Runtime的微内核与插件边界.md)。

报告助手最初只会检索和写草稿。技术团队随后希望加一项“方案比较”Skill：它教助手如何列出证据、指出缺口、按团队模板组织报告。把一段说明文字直接覆盖到线上配置，短期很快，遇到争议就会失去回答“这份报告依据了哪一版规则”的能力。

统一案例中的资料仍是教学构造：`source-a@v1` 只证明关键词匹配和批次更新，没有延迟测量；`source-b@v1` 只证明语义检索，没有更新周期或性能测量。Skill 可以要求把这些缺口单列，却不能把缺失信息补成选型结论，也不能取得报告发布权限。

## 编辑阶段先拒绝坏定义

Skill 编辑器应校验名称、入口说明、资源路径、依赖能力、冲突组和估计 token。引用的工具必须在声明范围内，资源不能越出包目录，脚本资源也只是内容，不能因为存在就获得执行权限。校验的目标不是限制写作者，而是让错误在发布前暴露。

例如“方案比较”Skill 依赖资料检索和报告草稿工具，却不需要发布权限。若定义里混入发布工具，编辑器应要求明确声明并进入更严格审核。权限不是从提示词措辞推断出来的。

## 校验结果必须绑定到被校验的修订

草稿不是一个会被原地覆盖的字符串。每次保存都产生递增修订或内容指纹，校验记录同时固定草稿修订、解析后的资源引用、工具 schema、依赖版本和校验器版本。下面是教学结构示意：

```json
{
  "draft_id": "skill-compare",
  "revision": 8,
  "content_digest": "sha256:8f2...",
  "resolved_refs": ["resource:report-layout@3", "tool:evidence-search@2"],
  "validator_version": "validator@5",
  "status": "passed"
}
```

如果作者在校验后把“缺失性能测量”改成“默认推荐 B”，内容指纹已经变化，修订 8 的通过结果不能用于修订 9。资源别名也不能到发布时再次解析为最新版；校验所见的精确引用必须进入发布候选，否则同一份校验报告会为不同内容背书。

失败路径常出现在异步校验：校验任务开始时读取修订 8，返回时草稿已到修订 10。编辑器可以展示“修订 8 曾通过”，但发布按钮只能接受与当前内容指纹一致的结果。把最近一次绿色状态贴到整个草稿上，会制造典型的检查与使用时序漏洞。

## 发布生成不可变版本

发布时固定 Skill 正文、资源摘要、提示词、工具定义与依赖解析结果，计算内容指纹。报告 Run 在准备时引用这个版本；之后即使编辑者修正文案，已开始的比较任务也继续使用原版本，新 Run 才能采用更新版。

这条冻结规则同样适用于工具定义。若检索工具参数从 `query` 改为 `queryText`，旧 Run 不能在恢复时悄悄适配新 schema。要么继续使用旧定义完成，要么明确失败并让用户新建任务。严重安全问题可以阻止旧版本继续产生新 Attempt，但不能删除版本引用或改写已发生的事实。

并发编辑与发布也需要明确结果。草稿携带修订号或内容指纹；作者 A 基于修订 8 发布时，作者 B 若已先把修订 9 发布，A 必须得到冲突、分支草稿或已存在版本，而不是静默覆盖。发布以草稿修订为前置条件：同一修订的重复请求返回同一制品，两个竞争者不能生成相同版本号而内容不同的 Skill。

这里还需要原子可见性。一次发布至少要同时固定制品正文、内容指纹、精确依赖、资源引用和版本状态，再把“当前可选版本”指针推进到新制品。实现可以使用单个事务，也可以先写不可见制品、全部落定后再以一次条件更新激活；关键是发现列表永远不能看见缺少资源或依赖锁的半个版本。

具体推演如下：作者甲和乙都从修订 8 开始。甲保存修订 9 并通过绑定校验，乙仍拿修订 8 请求发布。若策略允许发布任意已校验修订，乙可以得到独立的 `skill@1.0`，甲之后发布 `skill@1.1`；若策略规定只能发布草稿头部，乙得到修订冲突。无论采用哪种产品选择，同一幂等请求不能生成两个版本，版本号分配与制品写入也不能分离提交。

发布通知和索引更新可以在制品提交后异步投递，但投递失败不能让制品内容回到可变状态。相反，如果制品写入失败，不能先向订阅者宣布新版本。运行时从不可变版本读取 Skill；一次 Run 冻结 `skill@1.0` 后，即使 `1.1` 成为默认，也不会在恢复时换用新规则。

## 激活并非把全文塞进上下文

Skill 可以常驻，也可以按需激活。两种模式都检查冻结版本、依赖能力、冲突组和挂载预算；入口估算超过上限时返回 `BUDGET_EXCEEDED`，不截断入口正文来伪装激活成功。挂载和 Agent 发布成功不代表入口必然已被加载；机构挂载页展示精确发布版本的入口估算，并提示预算不足，仍保留维护者选择额度的权利。

激活成功才把完整入口说明加入模型视图，附加资源按需读取并单独对照同一挂载上限；这不是 Loop 累计 Skill 额度，也不是供应商实际用量。最终模型消息仍按实际 tokenizer 检查整体上下文预算。Skill 的文字可引导模型组织证据，却不能从提示词中获得发布、读取或状态迁移权；执行端仍以当前授权和已注册 Action 为准。

在 A/B 报告中，`skill@1.0` 可能只要求列证据，`skill@1.1` 新增“证据不足必须单列”。使用 1.0 的待审批 Run 继续按 1.0 生成草稿；新 Run 采用 1.1 后，应明确写出 A 缺少延迟测量、B 缺少更新周期和性能测量。两版都只能提出发布 Action，实际审批状态仍由运行时强制。

练习：为“方案比较”Skill 设计两次发布。第二版新增“证据不足必须单列”的规则，两位作者同时从同一草稿修订尝试发布，且一份比较说明正在等待审批。

预期结果：校验结果带有草稿修订、内容指纹和精确引用；内容变化后旧校验失效。同一修订的重复发布得到同一制品，竞争修订按既定策略产生冲突或不同版本，发现列表看不到半发布制品。正在执行的 Run 保持第一版并能恢复，新 Run 可采用第二版；引用不存在的检索工具时，定义在发布前被拒绝而不是降级执行。
