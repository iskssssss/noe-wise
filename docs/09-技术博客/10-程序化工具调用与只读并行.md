# 程序化工具调用：只把真正独立的读取并行起来

前置阅读：[04 课](04-Agent-Loop的动作观察与模型输出失败处理.md)、[07 课](07-Skill按需加载与工具发现.md)、[08 课](08-HTTP工具的受控出网与执行边界.md)、[09 课](09-通用代码执行沙箱的隔离设计.md)

研究助手需要读取 A、B 两份资料，再整理对比表。两次读取互不依赖，串行等待没有必要。可“先搜索 B 的资料，再读取搜索返回的来源”具有明确依赖，不能一股脑并行。

程序化工具调用把一段编排交给受控程序描述：组合调用、汇总结构化结果，再把需要模型判断的部分交回来。它能减少来回传递的大块中间文本，但也会扩大一次动作的工作量，必须保留逐项权限和预算控制。

## 并行资格来自依赖与效果

判断是否适合并行，可以从两个问题入手：一项调用是否需要另一项的结果？调用之间是否会争夺或改变同一资源？

读取固定版本的 A、B 通常可以并行；先发布 D1 再通知读者不可以并行，因为通知依赖发布结果。两个名义上的“查询”如果会触发远端状态改变，也不能仅凭名称判断安全。

并行还不保证得到同一时刻的数据。两个实时来源在不同瞬间被读取，可能呈现不一致的视图。需要严格比较时，应固定资料版本或清楚记录读取时间与限制。

## 编排程序也只能走工具端口

不要让程序化调用成为绕过 HTTP 策略、身份检查或沙箱限制的第二条通道。编排器应只暴露受控工具代理，每次子调用都经过原来的验证，并建立可关联的动作或子调用记录。

以下是教学伪代码：

```text
targets = [source_a_at_v1, source_b_at_v1]
results = bounded_parallel_map(targets, configured_concurrency, item ->
    tool_proxy.read_material(item)
)
for each result:
    retain status, source, version and evidence_reference
return compact_result_set(results)
```

bounded_parallel_map 的并发数由运行时配置，模型不能把它调成任意大。预算应在派发前预留或检查，不能等全部请求发出后才发现已经超限。工具失败也应该作为结果收集，避免一次异常让其他已经完成的读取证据消失。

## 并行部分失败，报告仍然可以推进

A 成功、B 超时，是一个有用的部分结果。助手可以交付 A 的已知信息并说明比较缺口，也可以在规则允许时只重试 B。若简单重跑整个批次，既浪费资源，又可能让原本成功的结果被新版本覆盖。

当用户取消任务时，编排器应停止派发尚未开始的调用，并尝试取消进行中的调用；已经返回或无法撤回的请求仍需记录结果。并行取消是收敛动作集合，不是让此前所有效果消失。

读取数量很少时，普通 Loop 分别调用工具更容易观察和调试。只有确有批量操作、依赖处理或中间数据整理需求时，程序编排才值得增加复杂度。

## 让模型说明为什么能并行

使用时机是准备一个批次前。输入来自已知来源、工具效果类型、依赖关系及运行时给出的并发和预算限制。增量提示词可以这样写：

```text
[新增：并行与依赖]
互不依赖且效果类型允许的读取可以组成一个批次。
需要前一步返回值的动作保留顺序，不提前猜测参数。
只通过提供的工具代理调用能力，遵守运行时给出的批次限制。
消费每项结果的状态；部分失败不抹去其他成功证据。
只重试符合策略的失败项，不把 unknown 写入当成普通读取重试。
汇总时区分已完成项、失败项、未开始项和仍在等待项。
```

设计理由是把“更快”转成清晰的依赖判断。预期行为是 A/B 精读并行，读取完成后再构造比较表。失败对照是把检索和依赖检索结果的精读同时发出，或者任何一项失败就谎称整个批次未执行。

这一片段也适用于后面的团队协作，但工具并发与 Agent 委派不同。前者通常有明确输入和调用契约，后者让子 Agent 自己展开多轮决策，需要更完整的任务与生命周期管理。

## 给动作画一张依赖表

练习：安排“读取 A”“搜索 B”“读取找到的 B”“计算样本统计”“汇总草稿”五项工作。假设样本 CSV 已上传且授权，B 的搜索返回空结果。

预期结果：读取 A、搜索 B、计算统计可以独立启动；读取 B 依赖搜索命中，本次不应执行；汇总等待已启动的必要分支收敛，并明确 B 的证据缺失。草稿可以包含 A 和样本统计，但不能宣称完成 A/B 的完整比较。下一阶段会处理这些观察如何进入模型上下文，避免批量工具结果把输入窗口塞满。
