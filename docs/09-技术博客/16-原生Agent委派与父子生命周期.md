# 原生 Agent 委派：父任务不必亲自完成每一步

前置阅读：[03 课](03-提示词设计总览分层组装与验证.md)、[04 课](04-Agent-Loop的动作观察与模型输出失败处理.md)、[15 课](15-长期记忆提取治理与按需使用.md)

研究助手要为内部技术团队比较两份虚构资料。资料 A 描述关键词匹配和批次更新，却没有更新延迟数据；资料 B 描述语义检索，却没有更新周期或性能测量。最终成果是选型报告，发布前必须审批。这个任务很适合拆成“核对 A”“核对 B”“综合写作”，但拆分不等于让三个模型共享一段聊天记录后各写各的。

原生委派的关键，是父 Run 用一个明确 Action 创建独立子 Run。Session 仍代表长期会话，父 Run 和子 Run 则分别保存自己的目标、状态、预算与终态。子任务不是父任务的一次普通工具调用，也不是一段隐藏的内部推理；它有可追踪的身份，可以等待、失败、取消和恢复。

## 先把分工写成可验收合同

父任务负责决定为什么拆分、子任务之间如何组合，以及什么条件下可以交付。子任务只负责自己的封闭问题。以资料核验为例，父任务可以创建两个子任务：A 子任务提取查询方式、更新机制及缺失测量；B 子任务提取查询方式、更新信息及性能证据。它们都不得直接发布报告，也不能把自己的局部结论包装成最终选型。

下面是委派请求的示意数据，不是某个产品的固定接口：

```json
{
  "delegation_key": "compare-ab/audit-source-a",
  "objective": "核验资料 A 的查询与更新事实",
  "inputs": [{"source_id": "source-a", "version": "v1"}],
  "deliverable": {
    "facts": "带来源定位的事实",
    "missing": "资料未提供的信息",
    "status": "completed | blocked | failed"
  },
  "forbidden": ["访问资料 B", "决定最终选型", "发布报告"]
}
```

目标说明必须能让子任务独立完成，结果合同则让父任务知道怎样消费终态。只写“研究一下 A”会留下三个漏洞：完成标准不明确，子任务可能扩展范围，父任务也无法区分“没有证据”和“忘了检查”。合同要求 `facts` 与 `missing` 分开，正好能表达“A 有批次更新说明，但没有延迟数据”。

## 一次父子时序怎样推进

时间点 t0，父 Run 记录拆分计划；t1，它提交两个委派 Action，运行时为每个 Action 建立稳定的委派身份和子 Run；t2，父 Run 进入等待集合，而不是持续轮询。A 子 Run 在 t3 返回“关键词匹配、批次更新、无延迟数据”，B 子 Run 在 t4 返回“语义检索、无更新周期、无性能测量”。每个结果都先成为持久终态，再以一次可去重的 Observation 唤醒父 Run。

t5，父任务发现两个合同都已满足，生成草稿 D1：它可以比较检索机制，却不能宣称 B 更快，也不能比较更新及时性。审阅者补充受众要求后，父 Run 可在同一任务目标下形成 D2，但 D2 仍是草稿。t6 的发布必须等待审批；子任务完成从未隐含发布授权。

父任务若在 t3 收到 A 的终态，不能把“部分到齐”误写成“全部完成”。它可以展示进度，也可以先做不依赖 B 的整理，但正式汇总应读取等待集合中的实际状态。重复到达的 A 终态只确认同一个子结果，不能触发第二次汇总或创建第二个 A 子任务。

## 在第 03 课模板后追加委派规则

下面的增量提示词用于父模型准备拆分和消费子结果时。任务目标来自用户输入，候选分工由父模型提出；可委派 Agent、预算、已创建子 Run 与终态结果由运行时提供。

```text
[新增：委派决策]
只有当子问题可独立说明目标、输入边界和结果合同时，才提出委派。
为每个子任务写明：要回答的问题、允许使用的材料、不得执行的动作、完成与阻塞条件。
子任务终态只能作为带来源的结果输入；不要把子任务仍在运行或等待描述为已经完成。
汇总前核对全部必要子任务的状态；允许交付部分结果时，逐项标出已完成内容和缺口。
不得要求子任务发布最终报告，也不得把子任务的内部推理当作交付物。
```

这段提示词解决的是模型怎样提出合理分工，不负责真正创建子 Run。预期行为是父模型把 A/B 核验拆成两个独立合同，并在两个结果到齐后写 D1。失败对照是只说“并行研究 A/B”，随后看到 A 先返回就自行补写 B 的性能结论。即使提示词写得再严密，运行时仍要校验子任务类型、权限和预算，并持久化父子关系。

子 Agent 也需要自己的短指令。创建子 Run 时，运行时将已批准的任务说明和允许材料填入下面的片段；它只规定子任务职责，不继承父任务的整份聊天和工具权限。

```text
[新增：子任务职责]
只回答 delegation.objective，依据 delegation.inputs 中可访问的指定版本。
返回带来源定位的 facts、缺失信息 missing 和真实 status。
缺少必要材料或调用失败时返回原因及已有结果，不编造补全。
完成核验后结束本子任务；最终选型、审批与发布由父任务及对应流程处理。
```

预期结果是可独立核对的一份资料核验记录；失败对照是子 Agent 擅自生成最终推荐或公开报告。父任务还要验证返回结构与引用，不能把子模型的自我评价当作质量证明。

## 生命周期传播需要显式语义

父 Run 取消时，运行时可以向尚未开始或正在运行的子 Run 发出取消请求，但取消不是时间倒流。子任务已经发出的外部效果不会因此撤销，已经提交的核验结果也应保留审计记录。反过来，一个子 Run 失败通常不应自动把整个父 Run 标成失败；父任务应根据结果合同判断能否重试无副作用步骤、请求补料，或交付带缺口的草稿。

子 Run 等待用户输入时也不能偷偷把问题转给整个 Session。运行时应把“等待什么、由谁回答、截止条件是什么”带回父任务，由父任务决定统一提问还是终止该分支。这样用户只面对一份清楚的问题，而不是多个子 Agent 争抢会话。

委派的代价是额外上下文、调度与汇总复杂度。两个高度耦合、反复交换中间稿的子任务往往不值得拆；一个父任务直接完成会更可靠。适合委派的是输入边界稳定、结果可验收、彼此可以真正并行的工作。

## 小练习

父 Run 已创建 A、B 两个子 Run。A 返回终态后，相同结果事件又到达一次；B 进入等待，要求提供其更新周期文档。请写出父 Run 下一步。

预期结果：A 的终态只消费一次；父 Run 不重复创建 A 子任务，也不宣称比较已完成。它向用户提出一个具体缺口：需要 B 的更新周期资料；同时可交付 D1 的已有部分，明确 A 没有延迟数据、B 没有性能测量，报告仍是草稿且未提交发布审批。
