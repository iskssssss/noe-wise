# 单 Session 多执行：一句“继续”应该交给谁

前置阅读：[02 课](02-Session-Run与Execution为什么需要分开.md)、[16 课](16-原生Agent委派与父子生命周期.md)、[22 课](22-审批回调与挂起恢复.md)

同一个研究会话里，Run R1 正在等待用户批准 D1，Run R2 正在等待补充方案 B 的资料。用户发来一句“继续”。如果系统总把新消息交给最近的任务，这句话可能被当成批准；如果广播给所有等待者，又可能同时唤醒两个流程。

输入路由的职责，是确定一条输入针对哪个对象、表达什么意图。它与自然语言理解有关，却不能完全依赖模型猜测，尤其是审批、取消和其他控制动作。

## 区分新任务、补充内容和控制输入

同一聊天框可以承载多类输入，后端仍需保存明确的类别和目标：

| 输入 | 目标示例 | 需要核对的关系 |
| :-- | :-- | :-- |
| 新任务 | Session S 下新建 Run | 用户可以在此 Session 发起任务 |
| 补充资料 | R2 的资料等待项 | 等待项属于该 Run，仍接受这种输入 |
| 审批决定 | 指定审批对象与 D1 | 审批身份、内容版本与当前状态 |
| 取消 | R1 或指定 Execution | 当前主体可以控制该目标 |

界面可以在待办卡片里携带目标标识，用户点击“补充资料”时，不必自己输入一长串 ID。后端不能只相信前端传来的 target_id，还要验证它属于当前主体可访问的会话与任务。

自然语言消息没有显式目标时，可以结合当前焦点和等待项提出候选。低风险补充可按已声明的产品规则处理；高影响控制出现歧义时，应澄清或要求选择，不能把猜测落成授权事实。

## 路由结果也要持久化

接收端先生成或接受稳定的 input_id，再决定它对应新 Run、已有等待项，还是待澄清输入。路由后保留 input_id、目标、意图、依据和受理结果，重投时复用这个决定，而不是重新按“当前最近任务”分类。

下面是补充资料的示意输入：

```json
{
  "input_id": "input-material-7",
  "session_id": "S",
  "target_run_id": "R2",
  "target_wait_id": "need-source-b",
  "intent": "provide_material",
  "attachment_ref": "authorized-material-B2"
}
```

附件引用仍需资源校验。路由成功只说明资料被交给正确任务，不说明文件内容可信，也不自动把它变成长期记忆。

如果重复提交 input-material-7，接收端返回原受理结果。若相同 ID 对应不同附件，不能悄悄覆盖原输入；可以按冲突处理，要求新的输入身份。

## 目标消失时，不要偷偷改投

用户打开页面时 R2 还在等待，提交附件时 R2 已结束。系统应返回明确的过期或不再接受输入的状态，并提供“作为新任务继续”的选项。不能因为 R1 还活着，就把附件塞给 R1。

类似地，一个等待项可能由版本变化失效。输入携带 wait_id 与期望版本，可以让条件更新识别这种竞态。处理失败后，用户知道需要重新选择，而不是在几分钟后发现材料用错了地方。

对于只允许一个活动 Run 的简单助手，路由规则可以很小，但也应拒绝过期目标。支持多执行时，显式目标的价值会迅速增加。复杂度应该来自实际并存任务，而不是预先设计无限灵活的广播总线。

## 模型可以帮助消除歧义，但不能批准自己

若路由层使用模型分类，给它的输入只应包含当前用户有权看到的候选等待项及其简述。模型返回候选 intent 和 target，不直接修改审批或运行状态。

可以给分类器一个很窄的示意约束：

```text
[路由辅助片段]
从提供的候选等待项中判断这条消息可能针对谁。
多个目标都合理或缺少目标时，返回 needs_clarification。
“继续”不自动等于对某个报告版本的发布批准。
只能返回候选标识与简短依据，不创建任务、不改变审批状态。
```

使用时机是普通文本无法明确匹配目标时，候选来自可信等待记录，消息来自用户输入。预期行为是面对 R1 审批和 R2 补材料两个等待项，询问用户指哪一项。失败对照是因为 R1 更新更近就推断用户已同意发布。路由后的权限与状态校验仍由程序完成。

## 给三条消息找位置

练习：R1 等待审批 D1，R2 等待资料 B。依次收到带 R2 待办标识的附件、没有目标的“继续”、重复投递的第一条附件。

预期结果：附件只交给 R2；“继续”不能批准 R1，应先明确目标与意图；重复附件返回原受理结果，不新建 Run、不再次消费等待项。若 R2 已关闭，重复输入仍可返回历史受理结果，新内容则需要新输入与有效目标。这样，Session 能容纳多条进展，却不会把它们混成一个隐含控制通道。
