# 动态插件与 Marketplace 供应链设计

前置阅读：[33 Agent Runtime 的微内核与插件边界](33-Agent-Runtime的微内核与插件边界.md)、[36 模板安装](36-Agent模板发布与机构安装.md)。

> 本课是通用设计推演。灵知的动态插件安装、热更新及 Marketplace 供应链治理仍属[未闭环主题](../02-架构与设计/11-未实现功能清单.md#2-其他平台缺口)，本文不代表这些功能已经实现或完成验收。

当报告助手被多个团队使用后，团队会提出自己的连接器、报告格式和检索算子。动态插件能满足这些需求，也会带来供应链问题：这份包从哪里来，依赖了什么，能访问什么，发现漏洞后怎样撤回？“上传一个压缩包即可运行”并不是平台能力，而是风险的起点。

统一教学案例中，助手比较 `source-a@v1` 与 `source-b@v1`，为内部技术团队写选型报告。A 的教学资料只证明关键词匹配和批次更新，没有延迟测量；B 只证明语义检索，没有更新周期或性能测量。一个外部资料抓取插件可以补充证据，却不能凭安装本身获得任意出网、跨团队读取或报告发布权限。

## 静态插件和动态 Marketplace 的风险面不同

静态插件随应用构建、测试和部署，变更进入主发布流程；回滚通常意味着回滚整个应用版本。动态插件则在应用运行期间独立分发、安装和撤回，Marketplace 还增加了搜索、作者身份、版本选择和跨团队复用。它缩短了能力交付路径，也把依赖解析、制品验证、隔离加载、权限批准和紧急撤回变成运行平台的责任。

若连接器只服务一个受控部署，静态集成通常更简单。只有确实需要独立版本节奏、多作者分发或租户自选能力时，动态插件才值得承担额外治理成本。把已有类放进可下载压缩包，并没有完成从静态到动态的架构转换。

## 制品必须有可验证身份

一个插件发布包至少应包含清单、内容摘要、版本、依赖范围、许可证、作者、签名或来源证明、权限声明和扫描结果。下载后先验证摘要与签名，再解析清单和依赖；任一步失败，插件不能进入可加载目录。

报告格式化插件可以声明需要读取报告草稿、生成附件，却不能默认申请网络和资料库权限。权限声明只是安装前的审查材料，真正执行时仍由运行时依据当前团队、Run 和 Action 复核。

签名只回答“当前字节是否由某个密钥签发且未被改动”。一个作者完全可以签署会把报告上传到自己服务器的插件；作者密钥也可能被盗。假设“证据增强器”具有有效签名和干净的已知漏洞扫描，却在格式化 A/B 报告时尝试连接未声明域名，运行时网络策略仍必须拒绝该 Action。不能因为签名通过，就把行为可信、依赖安全和业务合理合并成一个绿色标记。

## 依赖解析要可重复

插件依赖应使用明确版本范围，并在安装时形成锁定清单。若“引用格式化”依赖某个文档生成库，后续安装和恢复应使用已解析版本，而不是重新查询当下最新版本。否则同一个报告在下周重跑，排版规则可能已经改变。

撤回也需要分层处理。发现恶意版本后，平台可以停止新安装和新 Run 使用；已经启动的 Run 则按冻结能力与安全策略处理，不能把历史事实抹掉。高风险漏洞可能需要终止后续 Action，但这应留下明确原因，而不是静默换包。

## 市场不替代治理

摘要与签名只能说明内容未在传输中改变、或制品来自可识别的签名者；它们不自动证明作者可信、依赖无漏洞、权限合理或业务语义安全。可信度来自来源治理、审查、扫描、权限策略与运行时限制的组合。插件也不应获得长期万能凭据：运行时按当前团队和 Action 注入最小身份，声明的网络范围不能扩大为任意出网。

安装必须在插件可发现前完成。制品先进入隔离区域，依次核对摘要、签名、清单、依赖锁、扫描和权限批准，全部满足后才一次性标记为可用。中途失败的内容不得出现在发现列表；并发安装同一版本应复用同一已验证制品或等待，不能留下两份状态不同的安装记录。

隔离激活可以推演为四步：`downloaded` 制品只允许读取元数据；`verified` 表示摘要、签名和依赖锁可复核；`approved` 表示某团队接受声明的权限；`active` 才允许该团队的新 Action 选择插件。制品验证可以跨团队复用，权限批准和密钥绑定不能复用。若扫描完成后权限审批被拒绝，插件留在隔离区或按策略清理，但绝不能出现在该团队的工具发现结果中。

运行插件时还要管理类加载、文件路径、网络和资源配额。类加载隔离只解决依赖与命名空间问题，不能把不可信代码安全地关在宿主进程里；不可信可执行插件需要独立进程或更强沙箱，并通过受控端口访问资源。插件返回“已抓取性能基准”只是 Observation 候选，报告助手仍需看到来源版本与实际内容。若插件只找到了 B 支持语义检索，模型不能借插件名“证据增强器”推断 B 更快；发布报告依然等待用户审批。

回滚插件版本只影响未来加载和新 Action 的代码选择，不能回滚已写入报告、已发送外部请求或账本中的 Attempt。若旧插件已产出不可信附件，应单独记录附件的处置状态；删除运行记录会破坏审计，继续公开附件又可能扩大影响。

撤回、停用和数据回滚也要分开。Marketplace 撤回版本可以阻止新安装；团队停用可以阻止本团队新 Action；安全隔离可以中止尚未开始的调用。它们都不会自动撤销插件已经写入的外部数据。若插件向外部系统创建了一条记录，只能在目标系统支持且当前授权允许时执行显式补偿；发送邮件、下载后泄露的信息通常不可逆。

本地派生数据也不能一删了之。插件生成的附件可以被标为隔离、禁止下载，并在保留策略允许时删除内容；Attempt、来源插件版本、处置动作和审批记录应保留必要审计元数据。审计留存不等于永久保存敏感附件，更不等于继续向原接收者披露。

Marketplace 解决分发和发现，不能替团队批准插件。团队仍需要评估数据范围、网络访问、预算与维护责任。自动扫描能发现已知风险，却不能证明一个插件的业务语义安全。

练习：为一个“外部资料抓取”插件写一份最小清单，列出它的网络范围、输入输出和撤回策略。设定该插件签名有效，但运行时请求访问未声明域名；它此前还为一份待审批的 A/B 报告生成了附件。

预期结果：未声明域名在 Action 执行前被拒绝，签名有效不改变结论；同一版本内容摘要和依赖锁固定。撤回后不能新安装或为新 Action 激活该版本，旧报告引用的附件进入隔离或禁用状态，Attempt 与处置记录仍可审计；系统不会声称撤回已经逆转外部副作用，报告也不会绕过用户审批发布。
