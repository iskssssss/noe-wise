## 2. 通用约定

固定路径、严格输入、字段错误路径、查询分页、批量及通用 HTTP 错误分类归[工程规范](../../.agents/skills/nw-engineering/references/engineering-standards.md#api-与错误契约)；身份与对象授权归[授权规则](../../.agents/skills/nw-engineering/references/engineering-standards.md#身份权限与租户)。本文维护具体领域协议和传输形式，不复制通用规则。规范已定义而代码尚未统一的差异见[实施索引](11-未实现功能清单.md#22-工程通用契约实施差异)。

字段命名、宿主 ID 字符串传输、长度与精度及部分更新的目标要求见[数据库模型与字段规范](../../.agents/skills/nw-database/references/database-modeling-standards.md)，其中[更新语义](../../.agents/skills/nw-database/references/database-modeling-standards.md#6-部分更新的字段语义)同时约束 DTO、SQL 和客户端。存量接口尚未统一的范围见[实施状态索引](11-未实现功能清单.md#21-宿主数据库模型与字段契约统一)，不能把当前的空字符串或空对象哨兵当作目标例外。

`/admin/api-docs` 仅展示可通过外部凭证调用的接口，不以管理端登录凭证作为接入前提。智能体管理、终端用户、会话管理与诊断、请求用量和 Webhook 订阅使用 OpenAPI 渠道 API Key + HMAC；这些管理类开放路径拒绝终端渠道令牌，机构身份只取已认证的渠道记录。精确开放路径由 `ExternalAuthPaths.SIGNED_OPENAPI_PATHS` 维护，不向所有管理 API 扩散。后台登录使用权威安全会话和当前正式角色/动作/对象权限，外部凭据不替代后台身份。

聊天与知识接口接受渠道令牌或 OpenAPI 渠道签名；`/api/v1/open-platform/**` 使用 ServicePrincipal 凭证及 scope；Runtime 回调使用注册凭证与 callback-v1 签名。各类外部凭证不能互相替代。

管理基础 API 采用平台 `/api/v1/admin/foundation/<area>` 与机构 `/api/v1/tenant/foundation/<area>`，area 为 access、security、catalog、messaging、files、jobs、operations。动作、组织范围、资源共享和商业授权的组合见 [SaaS 基础底座](19-SaaS基础底座设计.md)，请求不提供可替代当前主体的角色或租户。登录、刷新及 `me` 返回当前 `roles/permissions/authorization_version`、安全会话 ID 和认证状态；MFA 默认关闭，自愿启用或显式策略后使用受限会话完成证明。未完成 MFA 的凭据不能进入普通业务 API，具体登录及恢复字段由双宿主 auth Controller 与生成 OpenAPI 定义。

### 2.1 独立聊天入口

- `GET /api/v1/chat/agents` 从已认证的机构、渠道读取已绑定且已发布的智能体，返回 `channel_id` 和 `items[{id,name,is_default,role_description,capabilities,delegation_config}]`；`delegation_config` 为 `{enabled,target_agent_ids}`，其中 `target_agent_ids` 只保留仍在当前授权目录内的目标。能力摘要仅包含 `type/name/description`，由服务端从有效挂载及对应发布版本提取，不返回系统提示词、模型配置或凭据。
- `GET /api/v1/chat/commands` 接收互斥的 `agent_id` 或 `team_id`，返回 `{items:[{command,title,description}]}`；字段均为字符串，`command` 是可填入输入框的完整命令。复用渠道令牌或渠道 OpenAPI HMAC 认证，并校验当前机构、渠道的目标绑定与发布状态；不要求已有 Session，不创建会话、提交输入或改变模式。单智能体和工作室都由普通 Chat Run 提供 Plan、Goal 和送达控制命令（见下文 §3）。两个目标均缺失、同时出现或为空返回 422，缺少合法身份返回 401，目标不可用或未绑定返回 403。
- `POST /api/v1/chat/client-profile` 接收 `client_ref`（UUID）与 `display_name`（1–128 字符），按机构、渠道、本机引用事务登记，返回 `channel_id`、`end_user_id`、首次登记昵称及 `identity_token`。凭证由服务端签名，绑定机构、渠道、终端用户、本机引用和 30 天有效期。已有引用的恢复必须通过 `X-Chat-User-Token` 携带原有效凭证；验证通过后返回同一用户及新有效期凭证，不改变首次昵称。仅提供引用、凭证过期、签名无效或身份不匹配均拒绝恢复。同一引用的并发首次登记只允许一次创建，其他无原凭证的请求被拒绝。
- 上述入口使用渠道令牌或 OpenAPI 渠道签名，不借用管理端身份。`client_ref` 是可由用户输入的本机引用，不构成授权。公开渠道的后续聊天请求必须同时发送 `X-Channel-Token` 与 `X-Chat-User-Token`；每次请求重新检查凭证期限、映射、渠道和终端用户状态。客户端按服务地址及渠道持久保存本机引用和身份凭证，旧裸 UUID 不恢复原用户；丢失或失效凭证后不能凭引用重新取得原身份。
- 外部聊天创建、输入、历史和回放均校验渠道目标授权；显式目标或用户不能改变已有会话归属。会话列表指定 `agentId` 或 `team_id`，两者互斥；团队必须同时指定 `end_user_id` 并匹配当前渠道内的个人团队归属。
- `GET /api/v1/chat/teams?client_ref=…` 查询本机身份创建的工作室；`PUT /api/v1/chat/teams` 接收 `client_ref`、可选 `id`、`revision`、名称/说明、成员 `[{agent_id}]` 和 `primary_agent_id`。不接收成员职责、工作室容量、Token 预算或客户端提供的委派范围；成员名称、版本、`role_description` 和 `capabilities` 是只读响应字段，不能由客户端覆盖。工作室只接受当前渠道授权且已发布的成员，所有协作者必须属于主 Agent 当前已启用的 `target_agent_ids`，主助手必须属于成员集合。服务端使用当前授权 Agent 目录中的 `delegation_config` 校验，不把完整委派名单复制进公开工作室成员快照。成员提示词、挂载和版本由服务端决定。保存与发布原子完成，旧 revision 返回 409。`POST /api/v1/chat/teams/disable` 接收 `client_ref/id/revision`，停用保留历史及维护入口。公开渠道请求的本机引用必须匹配已认证终端用户凭证，不授予机构工作室管理权限。
- 机构端工作室创建、编辑采用相同成员输入、主 Agent 委派名单约束和只读摘要边界；不设置职责、容量或 Token 预算。Agent 原生委派、通用 Run scope 与工作室收窄规则归 [Harness 08 §20](../../harness-design/08-Agent委派与多智能体运行时.md#20-agent-原生委派与结构化计划首期基线)。
- 工作室公开答复始终来自固定 `primary_agent_id` 的普通 Chat Run；成员子 Run 的进度和结果只进入协作投影，不能直接写用户消息。历史消息和 SSE 持久化主助手的真实来源标识，不能用最近一次成员执行者覆盖。
- 用户工作室复用现有 Team 定义、发布版本和 Runtime。成员能力调用继续核对其来源渠道当前授权；会话、协作历史和产物披露验证工作室的渠道/用户归属及相关成员当前授权，不能仅凭主助手绑定放行整个工作室。
- 工作室命令目录使用 `GET /api/v1/chat/commands?team_id=…` 并提供普通 Chat 的 Plan、Goal 和送达控制命令。普通 AGENT 与 TEAM 会话都通过现有 `GET /api/v1/chat/work?session_id=…` 查询最新协作工作，可选 `work_id=…` 精确查询一项，并通过现有 `GET /api/v1/chat/work/history?session_id=…` 返回按历史顺序排列的 `{items:[TeamWorkSnapshot]}`；不新增 Agent 专用协作路径。`POST /api/v1/chat/work/controls` 的请求体带 `session_id`、卡片自身 `work_id` 与对应任务/工作/pending 控制字段；补充不推定为批准，不接受成员选择或重路由操作。
- 会话正文按用户消息 `metadata.input_id` 显示对应协作摘要，右侧“本次协作”在协作与产物间切换。`TeamWorkSnapshot` 的 `input_id/run_id` 指向原主助手轮次；`revision/status` 表示工作事实，`run_revision/run_status` 表示父 Run 事实（记录暂不可读时为 null），不得用成员完成替代主助手答复完成。两类修订分别防回退，`stage` 是据此派生的显示阶段。客户端默认选择历史最后一项；用户选中旧工作后，最新投影刷新不得覆盖选择，控制响应按 `work_id` 替换对应项，结果卡通过自身 `artifact_id` 打开受控产物。
- 聊天前端将验证成功的渠道凭证保存到当前浏览器 localStorage，下次打开自动恢复并重新验证；支持主动清除，认证失效时自动清除。本机另存服务地址、认证方式、渠道对应的本机引用、昵称与最近智能体，聊天正文从服务端恢复。

- JSON 字段使用项目统一序列化命名，不在同一契约混用两套字段。
- 自有业务日期时间使用 ISO-8601，并以北京时间 `+08:00` 输出；标识符按字符串传输。绝对时间输入必须携带偏移，本地日期时间按北京时间解析；纯日期使用 `YYYY-MM-DD`。协议例外和存储语义见[全系统时间契约](13-全系统时间契约.md)。
- Session 输入携带或由服务端生成 inputId；资源发布、知识摄取和批量同步生成 operationId，并以 rootOperationId 关联子操作。两者都传播 W3C traceId/spanId，但控制请求不能伪造 inputId。
- tenantId、入口 `end_user_id`、agentId 和 sessionId 必须通过身份边界绑定，不能信任未验证的客户端元数据；
  个人分支的 `end_user_id` 缺失或非法时直接拒绝；群分支使用经过授权的 GroupBinding 和独立 requester，字段判别见 §2.7，不创建群 EndUser。
- Open Platform 凭证解析为 tenant + integration + ServicePrincipal + scopes；创建个人 Session 时必须显式
  传入属于当前租户的 `end_user_id`。`externalUserRef` 只用于审计、幂等和外部关联，不能解析、创建
  或覆盖内部终端用户身份。
- 三方资源使用 `integrationId + resourceType + externalRef` 映射，externalRef 不替代平台内部 id、租户隔离或权限检查。
- 错误使用稳定 errorCode、message、retryable 和 traceId。
- 对外 schema 以生成 OpenAPI 为机械校验对象，本文不维护重复字段副本。

### 2.2 JSON 响应与传输例外

所有普通 JSON 响应使用统一 `ApiResponse<T>` envelope：`code`、`message`、`data`、`trace_id` 为固定字段，成功固定为 `code: "OK"`、`message: "成功"`，业务结果放在 `data` 内。失败响应的 `data` 必须为 `null`，并按实际情况返回 `retryable` 与 `field_errors`；HTTP 状态码仍表达传输和授权结果，不能用 200 伪装失败。`trace_id` 来自请求上下文，必须是非空字符串，不得改名或从错误响应中省略。

网关沿用当前 exchange 的追踪上下文向宿主传递 `X-Trace-Id`，原样转发宿主响应。网关自身在提交响应前发生的 `/api/v1/**` 代理错误使用相同字段：连接失败为 502 `UPSTREAM_UNAVAILABLE`，超时为 504 `UPSTREAM_TIMEOUT`，其他错误保留实际 HTTP 状态并返回 `GATEWAY_ERROR`。代理失败不证明上游未受理，`retryable` 为 false；客户端读取已有回执或恢复事件，不自动重发业务 POST。已提交的 SSE 或二进制不追加 JSON。

204 和 304 不带响应 body，因此不包 envelope。SSE（`text/event-stream`）、二进制下载（包括 `application/octet-stream` 和文件响应）及 WebSocket 使用各自的传输协议，也不包 envelope；这类例外必须在 OpenAPI 的响应 content 或协议章节中明确标记。Open Platform v1 的普通 JSON 成功和错误响应都遵循该规则；本文同时覆盖宿主 API 的传输语义，Open Platform YAML 只作为 Open Platform 版本契约，不替代宿主全部 API 的 springdoc 权威来源。

### 2.3 平台治理与机构执行身份

已确认采用平台直管独立机构，目标移除 Application 和应用 HMAC 治理身份。平台人员 JWT 及受限管理机器身份经平台动作/对象授权维护机构和公共定义；机构 Open Platform 继续使用固定 Tenant/integration 的 ServicePrincipal，管理凭证不能代理任意 Tenant 的聊天、群历史或工具执行。目标和退役范围见[相关设计](01-技术架构.md)。

外部机构按部署内“命名空间＋机构标识”幂等开通，Tenant/默认策略/外部映射事务创建，同键异参冲突；已有机构需平台明确绑定。机构执行凭证另行一次签发/轮换/撤销。平台管理机器身份的凭证、scope、固定路径及错误以[GI-00 公开协议基线](#27-多机构接入公开协议基线目标)为准，不把平台人员 JWT 或默认应用作为自动化凭据。机构 API Key/HMAC 继续使用 `X-Api-Key/X-Timestamp/X-Signature`，canonical 为 `timestamp + "\n" + METHOD + "\n" + requestTarget + "\n" + sha256(rawBody)`，requestTarget 保留实际 query；正文不能改变主体和 Tenant。

开放平台 `POST /open-platform/sessions/attachments` 与 `/media` 使用 `application/octet-stream` 原始文件正文，分别以必需 query `sessionId/uploadId/filename` 和 `sessionId/uploadId` 指定会话及稳定上传身份；这些 query 与文件原字节共同被上述 HMAC 保护。附件复用现有类型、大小、摘要与同键异参校验，图片按实际内容解码和登记。该二进制上传元数据是写参数进入 query 的限定例外，不能扩展到普通 JSON 写命令；不支持以空正文摘要签 multipart 上传。上传与后续引用、成果生成及正式发布分别授权和验收。

公共定义在平台端按创建/编辑/校验/发布/下架权限维护，精确草稿 revision CAS、幂等不可变发布、影响视图、下架当前授权及恢复新发布与机构直接部署共同组成生命周期。目标部署校验平台有效发布、目标 Tenant、部署权限和本地资源；不经应用 grant，不使用 applicationManaged 兜底。FOLLOW_PUBLISHED 与独立安装保持明确模式，机构不能因有部署权编辑平台定义。

当前宿主不提供 `/api/v1/platform/applications` 与旧应用 `/api/v1/integration/**` 入口；管理、固定机构执行、直接部署与用量入口按所属契约分别授权。群和总部操作须按各自契约验证，不能仅凭入口存在推定完整交付。机构 `/api/v1/open-platform/**` 保留正式职责，不提供旧应用 API 代理或默认应用。

`POST /open-platform/end-users/ensure` 的 `end_user_id` 保留十进制字符串精度。消息/action/callback/command/steering 的 `Idempotency-Key` 接受最多 256 字符的稳定外部键，同参复用原回执、异参返回 409；服务端 input_id/run_id 是不透明身份，不从外部键推导。群作者/请求者、服务 Agent、记录与触发、成员版本及控制/记忆目标 schema 见[公开协议基线](#27-多机构接入公开协议基线目标)，所属 Runtime 类型见 Harness 03 §5.1.1 与 Harness 02 §5.8.1。

### 2.4 管理写入回执的持久字段

团队草稿通过 `POST /api/v1/teams/save-with-receipt` 接收原 `request_id`、可选团队 ID 和草稿；按新建或更新分别校验对应权限，草稿与仅含请求身份、成员、团队 ID 和修订号的窄回执同事务提交。`GET /api/v1/teams/save-with-receipt/result?request_id=...` 要求当前机构成员及团队读取权限，只读取该成员的原回执；204 不证明写入未受理，调用方保留原请求身份并继续核对，不重发原 POST。回执不复制草稿正文，目前未设置自动过期清理。

工作流安装通过 `POST /api/v1/builder/workflows/install-with-receipt` 接收原 `request_id`、`workflow_id` 和安装配置，校验创建权限及对象管理权限后，安装修订与只含请求、成员、工作流、实例和修订的窄回执同事务提交。`GET /api/v1/builder/workflows/install-with-receipt/result?workflow_id=...&request_id=...` 复验工作流读取权限与对象范围，只返回同一机构成员的原回执；204 不证明未受理，不可用当前实例推断原请求结果。该 POST 不提供重放契约；重复请求身份冲突时整个安装事务回滚。回执不复制配置或绑定，目前没有自动过期清理。

知识发布范围可通过 `GET /api/v1/knowledge/bases/documents/latest-ready-sources?kbId=...` 一次读取最多 2000 个未删除文档的当前就绪来源版本，按文档创建时间及 ID 倒序；该读取要求知识读取权限和知识库对象读取权，只返回来源标识。选择结果是读取时的范围，不自动发布，提交发布时仍校验来源版本与完整性。

已准备知识修订通过 `POST /api/v1/knowledge/bases/revisions/publish-with-receipt` 提交固定的 `request_id`、`kb_id` 和 `revision`；只要求知识发布操作权限及知识库对象管理权，不重复准备修订，也不额外要求创建、编辑权限。独立发布与组合准备发布共用原请求身份空间，同一机构 UUID 绑定不同命令、参数或操作者返回 409。成功回执 `{request_id,status,revision}` 与修订、能力版本和活动指针同事务提交，后续发布不会改写原回执；受理后业务拒绝持久返回 `REJECTED` 及 `error_message`，技术失败不伪造终态，仍保留 `PROCESSING`。同键重发只返回原进度或回执，不重新执行。

`GET /api/v1/knowledge/bases/revisions/publish-with-receipt/result?request_id=...` 只读原回执，要求知识读取权限、当前知识库对象读取权及原操作者；204 只表示没有可见回执，`PROCESSING` 也不证明原操作失败。既有组合发布结果查询继续使用 `prepare-and-publish/result?requestId=...`。界面必须保留原请求身份，不以当前修订状态或 active 指针冒充原操作回执；原修订被后续发布归档时仍返回当时的原发布成功结果。

ServicePrincipal 签发、Webhook 订阅创建、Connector 更新、平台机构开通／外部映射维护／签发凭证及 AgentTemplate 生命周期管理接口，以本次操作的权威持久记录生成安全回执。公开的 `created_at`、`updated_at` 与所属 `published_at` 取持久字段；同资源、同版本没有后续业务修改时，写响应中的安全持久字段与对应读取结果精确相等。日期时间沿用 ISO 8601／`+08:00`，不另规定固定小数位；一次性秘密仅首次交付，安全读取不再次返回或重新签发秘密。

普通机构创建使用 `POST /api/v1/admin/tenants/create-with-receipt` 提交原 `request_id` 与创建内容，页面通过 `GET /api/v1/admin/tenants/create-with-receipt/result?request_id=...` 查询原请求回执；写入不自动重发。`PROCESSING`、未查询到或回执不完整均不能证明原操作未发生。仅历史会话记录缺少请求 ID 时，工作台保留按原 slug 查找并由用户确认使用机构的入口；该查询不证明管理员账号已按原请求创建。具体授权与回执状态见 [PlatformTenantCreationController](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/controller/PlatformTenantCreationController.java) 和 [PlatformTenantCreationService](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/controller/PlatformTenantCreationService.java)。

团队已保存修订可通过 `POST /api/v1/teams/publish-with-receipt` 提交 `request_id`、团队 `id` 与 `expected_revision` 发布；服务端在锁定草稿后核对修订，成功结果与原请求回执同事务提交。`GET /api/v1/teams/save-and-publish/result?requestId=...` 可由原机构成员读取回执；`PROCESSING` 或未查到回执不代表原请求失败，页面不会自动重发。权限或参数在受理前被拒绝时，按实际错误反馈处理。

机构智能体部署可通过 `POST /api/v1/tenant/agent-deployments/receipt/query`，使用原 `Idempotency-Key` 和原创建内容只读核对结果。查询要求当前机构部署读取权限；代直属机构查询还要求该目标的读取许可，且仅返回原操作者对应的创建回执。`NOT_FOUND` 不证明原请求失败或未完成。原生部署未提供外部标识时由服务端生成；指定接入时须提供外部系统的真实标识。机构页面在当前标签页保存待核对请求，关闭标签页可能丢失该记录。

机构工具部署可通过 `POST /api/v1/capabilities/deployments/create-with-receipt` 提交 `{request_id,payload}`，创建结果与原请求回执关联；`GET /api/v1/capabilities/deployments/create-with-receipt/result?request_id=...` 要求当前机构成员和能力读取权限，仅返回原操作者可见回执。`SUCCEEDED` 表示原请求创建成功，`REJECTED` 表示原请求明确拒绝；204 不证明未受理。回执只保存请求身份、摘要、部署 ID 和标识等必要信息，不保存提供方凭据；同一请求身份的不同内容或操作者冲突不能解释为原请求失败。当前部署状态仍需单独读取，原无回执创建接口保留给已有调用方。

`GET /api/v1/capabilities/deployments` 的每项同时返回 `tool_name` 与 `tool_version_key`，供部署列表展示和本地筛选；服务端按 `tool_version_id` 批量读取必要字段，前端无需逐项请求版本详情。字段沿用版本读取的可见性：本机构版本可见，平台版本仅在已发布时可见；版本不可见时两字段为 `null`，部署记录仍保留。名称对应部署锚定版本，不替换为当前默认发布版本，也不改变运行时跟随当前发布的行为。部署详情、直接创建及启停返回的部署对象采用同一字段语义；原请求回执继续仅表达原操作结果。

机构工具部署启停可通过 `POST /api/v1/capabilities/deployments/state-with-receipt` 提交 `{request_id,deployment_key,expected_revision,active}`，分别要求启用或停用权限。状态 CAS 与成功回执同事务提交；确定的修订冲突记录拒绝回执，相同请求返回原结果，不同参数或操作者冲突。`GET /api/v1/capabilities/deployments/state-with-receipt/result?request_id=...` 要求能力读取权限且仅原操作者可见；204 不证明未受理。页面保留未知请求身份，可显式以相同身份及参数继续，不自动重发；原回执记录提交时结果，当前状态另行读取。

机构服务身份暂停与吊销使用 `POST /api/v1/service-principals/status-with-receipt`，提交 `request_id`、`principal_id` 和 `action`（`suspend` 或 `revoke`）。操作与回执同事务提交，`changed` 记录原操作是否实际变更；同请求的重放返回原结果，不同身份或操作冲突。暂停仅作用于启用身份，吊销可作用于启用或已暂停身份；未发生变更不能报告成功。原机构成员具备服务身份读取权限时，可用 `GET /api/v1/service-principals/status-with-receipt/result?request_id=...` 核对；204 不代表原操作失败，回执描述原操作，当前状态须重新读取。

机构服务身份可核对签发使用 `POST /api/v1/service-principals/issue-with-receipt`，提交 `request_id`、`integration_id` 和 `scopes`。签发与不含明文的回执同事务提交；首次响应返回 API Key 和签名密钥明文，同请求同输入的重复提交只返回原身份标识，输入不一致返回冲突。原机构成员具备服务身份读取权限时可用 `GET /api/v1/service-principals/issue-with-receipt/result?request_id=...` 核对；204 不代表签发失败，回执不能恢复明文。事务内明确拒绝并回滚的业务错误返回 `PRINCIPAL_ISSUE_REJECTED`；其他错误不能单凭状态码判断原操作未发生。

机构服务身份可核对轮换使用 `POST /api/v1/service-principals/rotate-with-receipt`，提交 `request_id` 和 `principal_id`。凭据更新与不含明文的成功回执同事务提交；首次响应返回 API Key 和签名密钥明文，重复请求不返回明文。原机构成员具备服务身份读取权限时可用 `GET /api/v1/service-principals/rotate-with-receipt/result?request_id=...` 核对；204 不代表轮换失败，回执不能恢复明文。事务内明确拒绝并回滚的业务错误返回 `PRINCIPAL_ROTATION_REJECTED`；其他错误不能单凭状态码判断原操作未发生。

AgentTemplate 管理元数据以对应持久管理行为权威，发布内容以精确 `(template_id, version)` 的不可变快照为权威。新发布的管理行与对应冻结表示复用一个持久权威发布时间；已发布的历史快照保持原样，读取旧版本不能替换为当前版本内容。

### 2.5 机构层级与 Agent 授权（目标）

本节定义 GI-15 机构关系/直属目录与 GI-16 机构共享定义、授权链及目标部署管理的契约；机构关系、字段和幂等边界见[§2.7.5](#275-机构关系与直属开通gi-15)，共享定义和完整授权协议见 §2.7.1–§2.7.2。固定 HTTP 路径与动作总表见[GI-00 公开协议基线](#27-多机构接入公开协议基线目标)。身份边界见[SaaS 基础底座](19-SaaS基础底座设计.md#24-机构层级与跨机构管理目标)，所有权与关系见[数据模型](03-数据模型设计.md#45-机构共享定义与授权目标)。

| 操作 | 权限、并发及可观察结果 |
|---|---|
| 查询机构树/下级目录 | 保留真实主体，按明确管理目标及当前关系过滤后分页/计数；总部不能借目录读取下级业务正文。 |
| 创建直属下级 | 平台机构创建权或总部专门创建权＋容量；机构/默认策略/映射/关系/幂等同事务，同键异参冲突；创建不签发凭证、不将总部加入下级成员。 |
| 挂接/迁移/解除关系 | 平台明确动作及目标授权，预期关系 revision/CAS；事务中校验父存在、单父、自指/环及并发反向挂接，失败不改关系；失效依赖旧关系的授权/范围并保留审计。仍有下级时拒绝删除机构。 |
| 机构共享定义维护 | 可信机构所有者；创建/编辑/校验/发布/下架/恢复分权，精确 revision、不可变幂等发布、影响预览沿用平台机制；私有挂载不能外泄，普通发布不自动共享。 |
| 授予/转授 | 校验定义/所有者或父许可、当前直属目标及动作/范围/期限/剩余层数；源所有者未允许转授时拒绝。同一稳定 actor 的创建键固定一个 grant_id，同参重试读取该 ID 的当前事实，换源/换目标冲突；授权不部署实例。 |
| 收窄/撤销/重新授权 | 预期 grant revision/CAS，保存权威回执；按收窄后的完整许可链即时判定，仍满足新动作/期限/转授深度的派生链继续可用，超出范围的派生授权不可用；撤销使全部依赖链不可用于新受理/派发，不能依赖投影刷新。旧创建重试读回已撤销事实，重新授权必须显式新操作，重新挂回旧关系不复活。 |
| 下级部署与绑定 | 目标机构部署权，或总部对目标的独立部署管理权；有效源发布＋完整当前授权/关系链＋目标资源/配额，在受理事务内防止与撤销/迁移竞争。稳定实例幂等，外部键换源冲突；本地绑定 CAS，不接收父机构私有资源或凭据。 |
| 同源实例切换授权依据 | 调用方明确指定当前实例与目标授权，检查目标机构部署管理权、相同源所有者/定义、目标 Tenant、完整当前授权/关系链及资源范围；以预期部署 revision CAS 原子保存新修订、审计及幂等回执。旧授权可以已失效，不能要求其仍有效才允许修复；新依据必须有效。相同命令同参返回原回执，异参冲突；旧命令重试不覆盖后续修订。 |
| 目录/影响/就绪 | 所有者维护视图与受让方发布消费视图分开；下级无源草稿/私有挂载，影响视图无业务正文，缺槽位或撤权返回明确未就绪原因。 |

目录、详情、历史版本、独立安装和部署统一核验[定义分发策略](03-数据模型设计.md#41-agent-模板与安装)。受控源仅按 AUTHORIZED_DEPLOY 消费，旧快照或调用方 mode 不授予独立复制权；GI-14 与旧标记移除同时落实，机构来源由 GI-16 扩展。

FOLLOW_PUBLISHED 对平台/机构源共用 Chat、Team、委派解析，实例在目标 Tenant 执行；版本与绑定冻结不覆盖当前授权检查。撤权/迁移/上级停用阻止后续受限动作，已派发或未知结果、历史和真实费用保留；独立平台直授及本机构自有 Agent 按自身授权继续判断。治理请求可见性和管理权不会授予群服务资格、会话读取或任意 Tenant 执行权。

首次部署必须确定所采用的授权依据，多条许可并存不形成隐式优先级；运行时只核验实例/Run 明确引用的依据，不自动换链。重新授权与实例切换是两个独立操作，普通部署幂等重试不能偷偷更新已有绑定。切换与撤销/迁移、新 Run 受理在权威事务边界串行化：新 Run 取得完整旧修订或完整新修订，不能混用；新依据先失效则切换拒绝，切换先成功也不能阻止随后撤权生效。实例保持稳定身份与本地配置，旧 Run 及其后续子任务沿用原冻结依据，旧链失效后不借新链恢复。切换成功不自动启动 Run、重放输入或发送积压；公开响应与影响视图区分当前实例依据、旧 Run 依据及各自有效性。

### 2.6 暂停与接管跨服务生效（目标）

本节是共享群控制的宿主契约；复用 Runtime 既有控制、调度和调用账本，不建立第二执行引擎。公开路径、字段、错误及 SDK 以[GI-00 公开协议基线](#27-多机构接入公开协议基线目标)为准；GI-04 实现 SkillForge 与示例发送服务的协议。以下状态名表达目标语义，不声明现有 API 已提供。

**状态归属与命令。** SkillForge 持有 Tenant/integration/GroupBinding 下的权威期望状态和单调 control_revision；若限定 Run，必须同时绑定原群与 Run。范围明确区分自动执行/模型与任务派发、自动业务写入、自动外发；人工接管展开为明确范围集合，后台记忆提取是否暂停按群策略单独配置。人工操作仍需自己的业务权限，聊天或记忆中的“继续/同意”不能改变控制。

控制命令使用认证上下文、稳定 command_id、内容指纹及 expected_revision CAS。同键同内容返回原回执，异参冲突；并发旧 revision 不覆盖新意图。期望状态、审计、命令回执及可靠待传播记录同事务持久化。控制和 ACK 接口分别复验当前主体、动作及对象范围，不能以普通聊天权限或正文伪造发送参与方。

**参与方与生效回执。** 服务端按控制范围确定必需参与方：SkillForge 调度/业务写派发及 Outbox 资格门禁，和实际自动发送端点。端点注册绑定当前 integration、群及端点世代；调用方不能删减必需参与方。无有效发送参与方时自动发送不可用，不以空 ACK 集合宣称发送控制已同步。参与方先持久化本地门禁及已应用 revision，再返回经过身份校验的 ACK，包含命令、群、revision、端点世代及拦截边界。它证明已落实拦截规则，不表示在途外调已撤回。

| 回执 | 对调用方的含义 |
|---|---|
| `ACCEPTED / APPLYING` | 权威命令已受理，全部或部分门禁尚待确认；返回当前 revision、必需/已确认/待确认参与方及可见在途引用，界面显示待同步或部分生效。 |
| `APPLIED` | 当前命令要求的全部参与方均已持久应用同一 revision 并确认；暂停生效只指未取得派发资格的后续动作被阻止，恢复生效只解除对应门禁；均不改变在途事实或自动放行积压。 |
| `SUPERSEDED / REJECTED` | 命令已被更新意图取代，或未通过当前授权/CAS；旧命令回执不能充当当前状态。查询同时返回当前期望和实际应用版本。 |

**跨服务失败与恢复。** 由业务侧发起暂停时，发送服务先持久设置本地安全阻止，再向 SkillForge 提交命令；本地阻止不另造权威 revision，未确认结果保留阻止并展示待同步，明确拒绝转为待对账；处理规则见下文。由 SkillForge 发起时，外部参与方尚未确认前只能报告部分生效。断网、超时或 ACK 丢失通过可靠记录重试原命令/查询原回执，不改 ID、不回滚为运行、不把超时当成功。控制传播按 revision 去重，旧版本忽略、缺口对齐当前权威快照；新端点、端点换代和进程重启先阻止自动派发，取得并持久应用当前状态，并在存在旧代时完成派发隔离且接续本地阻止/发送账本后才重新参与。过去的 APPLIED 不能授权新端点或失联重启端点继续发送。参与方失联时如实返回最后确认版本及失联状态；未来暂停仍须其确认，不能承诺网络分区中的即时全局生效。

**派发竞争。** 队列领取、Outbox 读取或预约发送不等于实际派发资格。发送端最终检查当前控制版本、当前有效端点世代、根触发的自动发送资格及未解除阻止、群/凭证/对象权限、原 Run 已完成且 final 已获正式采纳，并将稳定 delivery_id 的账本转入 `DISPATCHING`；该转移与本地暂停门禁串行化。暂停先赢则尚未取得资格的消息一律阻止；派发先赢的项列为在途，即使网络发送尚未完成，也不能宣称已被撤回。SkillForge 模型/任务和业务写派发采用同样的边界，与既有调用账本衔接。数据库提交和外部网络调用不声称原子，响应丢失记 UNKNOWN；仅在外部接口具备稳定幂等保证或可查询回执时按原身份恢复，否则不盲目重发。

本节“旧代/新代”均指满足同一目标协议、使用目标格式持久账本的运行进程世代，不表示支持历史实现与新实现混跑。历史协议、字段或账本格式不通过兼容适配接入本协议；不符合目标契约的入口明确拒绝，旧实现及直接消费者按所属批次替换。新版本配置、历史发布追溯和当前格式下的进程恢复继续遵守各自契约。

**旧发送端点退出与换代。** 端点的逻辑身份与进程世代分开；首版同一逻辑端点的各代共用可恢复的持久门禁与派发账本。每次取得新的 DISPATCHING 资格，必须在该权威账本事务中核对当前有效世代；世代停用/推进与派发资格转移串行化，不使用进程缓存、注册成功或 ACK 有效性代替派发校验。无法访问权威门禁时不得取得新资格。端点换代不改变 delivery_id 或重复发送判断范围。

换代先将旧代标为退役待确认并禁止它取得新资格，保留旧代已经取得资格的在途/UNKNOWN 项；可信控制参与方从持久门禁取得并上报可核验的退役回执，记录逻辑端点、旧/新世代、隔离边界和原在途引用。SkillForge 验证退役依据后，才可将旧代从必需参与方集合移出；新代还须接续本地阻止和账本、应用当前控制版本并确认。仅新代 ACK 或旧代失联超时不足以满足整体生效条件。隔离前赢得资格的调用仍属原在途，隔离后旧代即使仍存活、重新联网或持有旧凭证，也不能取得新资格。

首版不支持通过另建空账本、清空本地状态或变更逻辑端点 ID 绕过交接。未能读取旧账本或证明旧代被隔离时，旧代保留待确认、替代端保持停发，不宣告整体 APPLIED；旧代最终结果按原派发身份入账，由当前获准主体核验收口，不重新授予退役进程发送权。端点换代是当前授权的独立管理动作，不扩大群控制或机构执行权限。

**恢复与积压。** 恢复是新的、单独授权且带 expected_revision 的命令；旧 ACK、旧恢复或延迟暂停不能降低已应用版本。只解除对应控制阻止，其他人工阻止仍有效；整体恢复仍等待所需参与方确认，不因收到一个 ACK 就显示全局恢复。恢复仅允许后续合格触发，不自动放行旧版本积压输出，也不重启已取消/失败/未知 Run。积压需显式逐项或明确集合放行，沿用原 delivery_id，重新验证当前控制、授权、Run/final 及发送账本；已发送和未知结果不重新生成身份绕过去重。所有状态、失败、在途项及解除操作可审计；已发生用量保留。

**迟到结果与触发归属。** 在适用的群或定向 Run 范围持久保存发送暂停边界，以及根触发的可信顺序/发送资格代；资格登记与暂停边界由所属权威服务串行化，不能用客户端时间、final 生成时间或 Outbox 入队时间判断先后。跨服务尚不能确认归属时保留待核验并停止自动发送。GI-03 的稳定来源/根输入与 Run 关联由 GI-04 补齐该资格判断，委派、延迟工具结果和多段输出继承同一根来源；定向 Run 的阻止不扩大到其他 Run。

涉及自动发送的暂停一旦形成边界，其前已有触发的输出（已取得 DISPATCHING 资格的项除外），以及暂停期间登记的触发所产生的输出，均不得因恢复自动获得发送权；不要求当时已有 final 或 delivery 行。恢复只为其后新登记且满足当前授权的触发开放新的自动发送资格。旧 Run 可以按执行控制范围继续运行，但其恢复后才生成的 final、恢复后才补拉的旧 Outbox、暂停期间排队后启动的结果，仍需明确放行；历史查询和公开展示不因此被当作自动外发。

明确放行只针对已知的原根输入/Run 与已正式发布的具体消息版本或确定集合，记录其覆盖的阻止边界；它不覆盖尚未产生的任意后续消息，也不解除更晚暂停或其他独立阻止。创建或复用原消息对应的稳定 delivery_id，重新核验当前权限、final 和账本；没有正式结果时不提供通配预授权，也不重提原输入。端点换代和本地暂停意图解除均不能清除这些来源与阻止依据。

**本地暂停意图的对账与解除。** 业务发送端先验证本地操作者当前控制权限，再以稳定 local_intent_id 持久保存本地阻止、适用范围、来源/发送边界和本地 revision；可靠提交记录关联原 command_id、内容指纹、expected_revision、提交结果及远端受理 revision。该意图是本地安全依据，不另造远端权威控制版本；重启、换代或重复请求复用原记录，多个独立意图分别保存。

| 对账结果 | 后续动作与解除边界 |
|---|---|
| 远端结果未知 | 查询或重试原命令及原内容，保持本地阻止；暂时查不到、超时或重试收到权限拒绝，不证明先前未知投递未受理。无法查证时由当前获准管理主体对账，不自动解除。 |
| 原命令已受理 | 绑定原远端命令/revision，继续传播及确认；即使后来被更新意图取代，也先读取当前状态。解除远端暂停需独立授权的恢复命令，不能仅删除本地记录；相关恢复确认后以 CAS 解除对应本地阻止，其他阻止仍生效。 |
| 可核验的原命令明确未受理 | 保存 CAS/权限等拒绝依据，进入“远端拒绝、待对账”，不无限重试固定冲突内容。当前获准主体可在读回最新状态后明确重新提交，使用新 command_id/指纹/expected_revision，并关联原意图与被拒绝尝试；或者明确放弃该本地意图。两种操作均需本地 revision CAS 与审计。 |
| 放弃仅在本地存在的意图 | 必须已证明此前关联尝试均未受理或已完成必要的远端解除；重新核验当前远端控制状态与管理权限，仅解除指定 local_intent_id。远端仍暂停、其他意图未解除、存在端点隔离问题或状态无法核验时，实际发送继续阻止。已留存的旧触发/迟到结果仍按明确放行规则处理。 |

明确拒绝必须对应同一可信命令身份下持久终结的未受理回执，或由获准主体对账终结该未受理命令的回执；终结与命令受理竞争同一权威边界，已受理的命令不能被改判未受理。终结后迟到请求、可靠提交重试和旧队列副本均不得再次受理该 command_id；本地停掉重试或单次 HTTP 错误都不构成此证明，也不能抹去此前结果未知的投递。失去权限的原操作者不能自行解除；获准管理者可接续对账，保留原操作者及接续者审计。对账、重新提交、放弃和本地解除均幂等，竞争以当前 revision 为准；解除中崩溃由原回执恢复，不批量清除其他接管。远端命令状态与本地有效阻止分别展示，不能将“远端恢复 APPLIED”显示成所有本地阻止已解除。

公开消息的 final 门槛见 [Harness 核心对象模型](../../harness-design/03-核心对象模型与状态机.md) 的原生回答采纳契约，不能以 Outbox 中出现文本代替自动外发资格。群控制的存储职责见[数据模型 §3.7](03-数据模型设计.md#37-群控制与跨服务回执目标)，跨服务控制与恢复组合需按当前候选单独验收。

### 2.7 多机构接入公开协议基线（目标）

本节是 2026-10-22 GI-00 的目标传输契约，后继批次同步 Controller、版本化 OpenAPI、SDK 和消费者后才能宣称接口可用；GI-14 候选已同步接入、部署、范围与用量的直接消费者，其余操作按所属批次实施，ABI 的群/记忆扩展仍未开始。这里固定操作、关键字段及拒绝分支，未列的正文内容、资源绑定和消息内容结构复用其所属契约，不新增自由 Map 协议。机构、定义、部署和群等宿主 ID 均为十进制字符串，Runtime input/run/message/cursor 为不透明字符串，revision/sequence 为非负整数，需要 CAS 的写入 expected_revision 必填；首次创建不伪造既有对象 revision，ensure 的已提交同参重试返回原回执。

GI-14 的部署读取辅助路径为 `GET /{platform|tenant|open-platform}/agent-deployments/detail`、`/definitions`、`/grants`，分别返回本闭包的实例、可消费定义和许可目录，沿相同 read/resources.read 动作。平台部署管理入口在机构宿主复用单一部署事务，网关按这些精确路径路由；平台人员在这些路径沿用 `X-Platform-Token` 认证头及平台 JWT realm，机构其他路径沿用 `Authorization` 及机构 realm，并继续检查当前数据库安全会话和平台动作/对象范围。管理机器按独立 HMAC 验证，不从平台角色、请求 tenant_id 或已建立部署获得机构执行权。

机构后台本机构用量使用 `GET /admin/usage/{events,summary,details}` 和当前 `foundation.usage.read`，固定可信当前 Tenant；与未来 `/tenant/usage/summary` 总部汇总分开，后者仍由 GI-09 实施。平台用量的三个动作独立授权，页面可按分别获准的事件、汇总或明细读取进入。

授权 actions 固定为 `deploy`、`execute` 的非空集合；部署创建逐跳要求两者，绑定修改/切换授权要求 deploy，新 Run/恢复及后续派发要求 execute；转授须为父许可子集。allow_regrant=false 时 remaining_depth=0；允许转授则深度为正，每跳至少减一，父有期限时子期限不得为空或更晚。源维护动作不进入这组消费许可。普通独立安装沿用现有正式模板安装入口，仅消费 OPEN_INSTALL；受控部署只消费 AUTHORIZED_DEPLOY 和当前有效 grant。创建机构/授权不自动部署或签发凭证。上述写操作使用 Idempotency-Key，作用域为主体的稳定 ID＋操作种类＋对象范围，不含 credential_version；除 Agent 授权创建的当前事实读取外，同参返回原持久回执；异参 409，轮换不制造第二次业务操作。首次成功普通写入返回 200；排队触发/异步控制为 202；幂等重读保留原业务结果和状态，不把受理改称完成。

Agent 授权创建的稳定请求身份为 actor＋创建键；definition_id、target_tenant_id、parent_grant_id 和完整授予范围进入指纹，同键换源或换目标均为 409，不能因目标不同形成第二次创建。重投仍检查当前管理动作；同参读取原 grant_id 的当前 GrantView，包括收窄后的 actions/revision 和 revoked 状态，不回显已失效的宽范围或激活旧 ID。narrow/revoke 保存首次命令安全回执；部署创建、绑定与换授权保存首次成功的 View，旧命令重投不以当前定义、绑定或新链重组原响应。

总部部署管理许可独立于来源 grant：平台通过上表固定 API 为可信总部 Tenant、精确直属目标和单项部署动作创建许可。总部人员还须拥有自身当前同名动作，许可的 relation_ref/relation_revision 必须等于当前直属关系，双方停用、迁移或撤销后立即失效；重新授权使用新 ID。机构 `/agent-deployments` 的写入目标只取类型化正文 tenant_id，本机构可省略；GET 可用 tenant_id 查询参数明确目标。平台写入使用 `{tenant_id,payload}`，payload 中如提供 tenant_id 必须与外层一致。固定机构 ServicePrincipal 仅管理自身 Tenant/integration，不能借这些字段跨机构；来源授权、目录 read grant 或源维护权均不替代目标部署许可。

平台定义创建的对象范围为新对象，编辑/发布/下架/恢复为稳定 definition_id。每次重读仍先检查当前动作及目标权；同参命中原回执后返回首次成功时保存的安全响应，再次编辑、发布或恢复不能改变旧键的结果，也不把旧 expected_revision 当成一条新 CAS 命令。新操作才检查精确 revision，业务变更、不可变发布、原回执及审计同事务提交。指纹按类型化命令规范化，保留有序数组语义，参数 Map 键排序；不以当前可变定义重组历史回执，不迁移旧实现的指纹或伪造不可重建的原结果。

机构共享定义的 `POST /api/v1/tenant/agent-definitions/preview` 接收 `{definition_id,expected_revision}`，要求可信当前机构源所有者及当前 `tenant.agent_definitions.read`、`tenant.agent_definitions.validate` 权限。在同一只读可重复读快照中返回 `{draft,validation,impact}`：`draft` 为完整已保存草稿详情，`validation` 校验该精确修订，合法时 `impact` 返回同修订的发布影响，否则为 null；修订已变化返回 409，不改用其他草稿。目标影响仍只覆盖当前明确管理许可允许读取的部署，不返回目标业务或绑定实际值。`POST /api/v1/tenant/agent-definitions/preview-content` 另接收 `definition`，仅预览当前编辑内容，返回 `{validation,impact}`，不返回或保存草稿，也不能作为已保存修订的发布依据。

机构页面“保存并校验”在保存回执确认后，直接用回执的定义 ID 和草稿修订调用上述保存态预览，由返回的 `draft` 同步服务端规范化内容，无需先单独读取详情。预览读取失败时保留已保存身份和修订，只重试只读预览；校验不通过时展示问题，不自动发布。原保存结果仍为 UNKNOWN 时，先按原请求身份核对或封存原保存，不自动重发保存，也不自动校验或发布。

群历史或事件身份不能按当前公开规则披露时，`history` / `events` 返回 `GROUP_EVENT_ID_UNDISCLOSABLE`，`retryable=false`；调用方保留原游标，联系机构管理员人工核对原事件，不跳过或重派。已建立的 `stream` 发送无事件 ID 的同码错误帧后关闭；同游标再次订阅若首条事件仍不可披露，返回 HTTP 204，原生 EventSource 应停止重连。首次遇到 204 的调用方可通过 `events` 读取原因；事件和原执行事实保持不变。

群的四项写操作均使用 Idempotency-Key，原命令指纹含精确对象、CAS、来源事件/版本及变更内容；同键同参重读首次持久成功回执，不按当前成员状态、Agent 名单或群状态重组响应，同键异参为 409。命令重读仍验证当前主体、动作与 Tenant/integration；新建绑定、加入/恢复 active 投影另验当前有效业务范围，范围停用不阻止 detail、关闭、退出/撤下或原回执读取。成员和 Agent 各自维护对象 revision 与来源回执，更新不能借另一对象或群的 revision 绕过 CAS；来源去重范围为 Tenant/integration/group＋成员或 Agent 操作＋具体对象＋source_event_id/source_revision。来源指纹包含对象、role/status 和来源标识/版本，排除 expected_revision、actor 和命令键；同一来源同业务内容即使换命令键或 CAS 仍读原回执，改变内容为 409，同版本换来源事件也因来源版本不前进而冲突。关闭群后仍允许有权读取原命令/来源成功回执，但不接受新状态变更，迟到事件不能覆盖较新的退出/撤下事实。

群服务授权明确落在当前 Tenant/integration/GroupBinding 下。本机构原生 Agent、integration_id 为 null 的受控部署可以经过该群的显式服务授权加入；部署固定了非空 integration_id 时必须与当前执行域精确匹配。允许加入不改变实例的原部署或来源授权，也不把 null integration 解释为任意外部主体的执行权。GI-03 的群触发、新 Run 和后续派发必须从当前群服务资格进入统一执行解析并复验原完整来源链，不能沿个人 Session 的旧 integration=null 匹配方式推导群执行资格。

个人 Session 创建和既有 actions/commands/steering、正式成果/附件/媒体接口保留职责；GI-02 不开放群运行，个人通道拒绝群 Session。后继群定向操作增加 group_binding_id 与具体 session_id/run_id 并进入原 Runtime，不得接受请求每轮改写 Session owner/固定 target。所有操作检查当前 Tenant/integration、群、读取者/操作者及适用业务范围；新执行、Agent 检索/恢复和派发另验当前服务 Agent 及该 Run 冻结的完整源授权链。当前成员读取已公开历史/群事实只依自身当前群读取权，不依历史回复 Agent 仍在服务名单或原源授权仍有效；治理另验自身治理权及来源。成果/未公开业务材料按各自对象披露权限，不因群成员身份放宽。群完整公开历史不包含私有推理、密钥、未公开工具正文或待审候选。

#### 2.7.3 HTTP 错误与消费者替换

使用现有 [ApiErrors](../../backend-java/skillforge-core-shared/src/main/java/com/skillforge/core/shared/web/ApiErrors.java) 字面量；不在 GI-00 假造已存在的领域错误枚举。每项拒绝遵循 §2.2 的失败 envelope，field_errors 使用具体字段路径；CAS/幂等原回执从有权读取的安全查询获得，不把冲突对象/旧秘密放入失败 data。

| HTTP / code | 固定分支与副作用 |
|---|---|
| 400 `VALIDATION_ERROR` | 缺字段/非法 union、未知字段、策略缺失或非法、转授权扩大、必需槽位不满足；不发布、不建实例、不派发。 |
| 401 `UNAUTHORIZED` | 无效签名、凭证撤销/过期或错误认证域；不建立业务身份。 |
| 403 `FORBIDDEN` | 当前 scope/目标/成员/群服务/来源链不允许，或管理身份试图执行；不以冻结事实或 JWT 旧角色放行，不产生非法副作用。 |
| 404 `NOT_FOUND` | 当前授权闭包内对象不存在；未获准目标不能借详情探测。 |
| 409 `CONFLICT` | 同键异参、revision 竞争、机构环/多父、外部键换源、首次发布后切策略、触发已占用、游标范围变化或终结命令再受理；不覆盖原事实。 |
| 429 `RATE_LIMITED` | 配额/容量不足，受理前拒绝；月配额仍按 §9 的渠道例外。 |
| 503 `SERVICE_UNAVAILABLE` | 权威授权/存储暂不可核验而未受理；不能据网络失败推断原副作用不存在，已派发/未知按原回执查询。 |

认证、校验、授权、冲突默认 retryable=false，429/503 也不能绕过幂等、前序对账和副作用安全重放；确定待前序/部分 ACK/UNKNOWN 是持久业务状态，不能用通用重试标志改写为失败或零成本。后继生成契约必须覆盖上述 HTTP、字段存在性、ID 精度和正反分支。

SDK/生成物替换：Open Platform 的版本化 YAML、springdoc、[生成类型](../../frontend-shared/src/open-platform/generated/v1-contract.ts)、[客户端](../../frontend-shared/src/open-platform/v1.ts)、契约生成校验工具和 integration-demo 同批更新；平台/机构管理接口由各自 springdoc 覆盖，不塞进仅 Open Platform 的 YAML。Runtime subject/requester/MemoryOwner 变化同步 API、core/session/memory、JDBC/inmemory、宿主装配、ABI 与 published-consumer，删除只维持旧 owner/应用格式的序列化和测试分支。

#### 2.7.4 发送端本地意图协议

独立示例发送服务提供 `POST /api/v1/local-control-intents`、`GET /api/v1/local-control-intents/detail`、`POST /api/v1/local-control-intents/reconcile` 和 `/release`。创建含 local_intent_id、group_binding_id、范围及本地 expected_revision，先原子写阻止/根边界和待发命令；后两项含 intent_id、expected_revision、明确 action（resubmit/abandon/release）和对应原命令/终结/恢复回执引用，各有独立 Idempotency-Key。身份必须具有当前 `groups.controls.reconcile` 或 `groups.controls.release` 及该群对象权，由受控认证边界核验，不接受正文自报权限。

resubmit 只在原命令已确定未受理终结时新建 command_id 并关联原尝试；UNKNOWN 只能查询/同参接续原命令。abandon 需要可核验 terminal_not_accepted 回执，受理竞争已由 SkillForge 的 terminalize 串行终结；已受理先执行相应远端恢复，再 release 对应本地阻止。CAS 竞争失败返回 409，远端/本地回执丢失不自动解除；权限撤销后原操作者不能继续，获准接替者保留双方审计。远端控制状态、本地有效阻止、迟到结果待放行和在途结果分别读取，不能合成一个 paused 状态。

#### 2.7.5 机构关系与直属开通（GI-15）

实际传输类型由 [InstitutionRelationContracts](../../backend-java/skillforge-core-foundation/src/main/java/com/skillforge/core/foundation/institution/InstitutionRelationContracts.java) 定义，平台和机构分别经 [PlatformInstitutionRelationController](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/controller/PlatformInstitutionRelationController.java) 与 [SubInstitutionController](../../backend-java/skillforge-institution-service/src/main/java/com/skillforge/institution/controller/SubInstitutionController.java) 调用同一关系服务。关系响应为 `{tenant_id,parent_tenant_id,name,status,revision,tree_revision}`，parent 为 null 表示独立根；列表为 `{items,total,page,page_size,tree_revision}`，page 默认 1，page_size 默认 20、范围 1–200。两个列表都先按有权目标过滤再分页/计数，只返回安全目录字段。

`GET /platform/institution-relations` 可用 `parent_tenant_id` 筛选直属子节点；无此筛选时列出当前平台范围中可见的关系，child 和非空 parent 均须在范围内。attach/move 的 JSON 为 `{child_tenant_id,parent_tenant_id,expected_revision}`，detach 的 parent 必须为 null 或不提供；ID 严格接受 `[1-9][0-9]*` 且不超过 signed bigint 的 JSON 字符串，拒绝 JSON 数字、前导零及溢出；expected_revision 只接受正 JSON 整数，拒绝字符串或浮点数。attach 仅适用于当前无父机构，move/detach 要求当前有父；目标不变、失效 revision、自指/成环或竞争失败返回 409。首次变更在树写锁内同时复核 child、当前原父及目标父的管理范围，不搬移业务数据或改变机构身份。revision 是该 child 直属关系的 CAS 修订，tree_revision 是全树拓扑修订，不能互相替代，也不代表业务权限版本。

`GET /tenant/sub-institutions` 只返回可信当前 Tenant 的直属机构，并同时要求当前 `tenant.sub_institutions.read`、该目标的 active 目录 grant，以及 grant.relation_ref 所指父/child/revision 与当前关系完全一致。`POST /tenant/sub-institutions/provision` 沿用 `ProvisionInstitution` 的 namespace、external_institution_ref、name、default_plan_code 和可选资源覆盖；父机构来自可信主体，正文不指定 parent 或认领已有 Tenant。外部键已有绑定即 409；成功同事务创建机构、默认策略/固定 integration 映射、初始关系、该关系的明确目录 read grant、原回执及审计，仅返回 Relation，不签发成员、凭据或 Agent 使用授权。直属容量见 [SaaS 基础底座 §2.3](19-SaaS基础底座设计.md#23-租户功能和资源配额)。

平台路径接受当前平台人员身份或 `X-Management-Key/X-Timestamp/X-Signature` 管理机器，机器须有与路径对应的精确 `platform.institution_relations.read/attach/move/detach` 动作及明确 Tenant 目标，不接受通配符 scope。机构上述两个精确路径接受当前机构人员 IAM，或 `X-Api-Key/X-Timestamp/X-Signature` 认证的本 Tenant/integration ServicePrincipal；后者须独立显式授予 `tenant.sub_institutions.read` 或 `.provision`，并复验当前状态、credential_version、scope、Tenant 与 integration，不能用 `resources.write`、平台管理机器或渠道令牌替代。普通机构管理员角色不自动获得这两个机构动作；正文、祖先位置及外部编号都不能签发管理身份或扩张业务权限。

三个关系变更及直属开通均要求 `Idempotency-Key`，稳定 actor＋操作＋key 唯一，参数指纹包含完整类型化请求（关系变更含 expected_revision）。当前身份、动作及请求目标检查先于原回执读取；同参返回首次成功的完整 Relation，包含当时的 revision/tree_revision，异参 409。原关系后来迁移、解除或重新挂接后，晚到重试仍读原响应，不重新写关系、授权、审计或消耗直属容量；回执不是当前目录或当前授权的证明。首次业务变更、回执和审计同事务提交，失败不消费成功键。数据约束见[数据模型 §12.1](03-数据模型设计.md#121-管理关系定义与部署)，设计取舍见[SaaS 基础底座 §2.4](19-SaaS基础底座设计.md#24-机构层级与跨机构管理目标)。

### 2.8 业务与媒体示例交付边界（目标）

GI-08 的业务系统和媒体 Connector 为可替换外部适配器，SkillForge 不新增预约、患者或企微专用 Runtime API。工具输入仅包含业务对象/筛选、计划参数和显式授权引用；Tenant/integration、执行主体、当前群/Session/Run、可信 BusinessScope、调用和确认身份由服务端签发的调用上下文绑定，模型参数不得覆盖。查询/评估与写入是不同声明的 ToolEffect；所有写入经过现行确认、策略、预算和外部调用账本。

待确认记录固定 proposal_id、目标对象、关键参数指纹、有效期、允许 actor/业务范围、所属 session/run/action 及 revision。确认 action 定向原 Run/Action 且当前有权，参数/对象/有效期变化或批准已消费均不得作为一次新的写许可；执行沿原稳定 invocation/operation 身份，成功而答复中断只读原回执，UNKNOWN 不重放。患者查询对象和本次时间约束/候选方案不改变私聊主体，不写成记忆授权。

媒体 ToolVersion 冻结供应商服务、输入/输出 schema、计量单位、确认/幂等及回执查询能力；Connector 凭证不进模型/源定义。长任务由原调用回调/查询收口，附件和 workspace 中间文件不直接成为可发成果；正式成果保存 artifact/message/run/来源引用，上传、下载、跨范围引用和发送均重新授权。预约/随访和媒体示例的业务状态由模拟系统持有，Runtime/模型/用量及正式产物必须按实际使用的真实入口采证，不能由模拟回执宣称真实生产业务完成。

## 3. 对话入口

代码执行产生的文件通过宿主受控产物 API 查询与下载，不嵌入 SSE 正文或原始 Trace。接口与票据使用见[代码执行与产物运行指南](../04-指南与运维/09-代码执行与产物运行指南.md#执行与下载)，归属、保留与预览隔离契约见[产物设计](12-代码执行沙箱与产物交付.md)。

对话提交入口为 `POST /api/v1/chat`（普通 JSON）与 `POST /api/v1/chat/sync`（JSON 受理入口，不表示 Run 已完成）；事件订阅使用 `GET /api/v1/chat/events`，历史回放使用 `GET /api/v1/chat/replay`，二者才返回 SSE。客户端必须先创建或复用稳定 Session（普通入口为 `POST /api/v1/chat/sessions`），后续消息携带稳定的 `client_message_id`；服务端将其映射为统一 inputId，重试不能生成新的业务输入。`POST /api/v1/chat` 的普通异步受理以 202 和 `ApiResponse<ChatResult>` 表达；纯控制命令没有 execution 时可用 200 返回已完成的 `ApiResponse`，不能把命令完成快照伪装成执行结果。SSE 响应本身保持事件流格式，不包 JSON envelope。

机构调试页使用 `POST /api/v1/chat/sessions/create-with-receipt`，请求为 `{request_id, payload}`，其中 `request_id` 是 UUID，`payload` 为原会话创建参数；成功返回 `{request_id, session_id}`。请求身份与 Session 同事务保存，不提供 POST 重放契约。响应未知时，以相同身份调用 `GET /api/v1/chat/sessions/create-with-receipt/result?request_id=...` 只读核对；读取要求当前成员是原创建主体且仍有该 Session 的读取权。204 表示当前没有可见回执，不能证明原请求未受理；会话被清理后回执也随之消失。核对不自动发送消息或上传文件，不授予会话写权。

`ChatCommandController` 的 `GET /api/v1/chat/commands` 是两个聊天入口的统一命令目录，接收互斥 `agent_id` 或 `team_id`，返回 `items[{command,title,description}]`，无需先创建 Session。机构登录必须访问当前租户已发布的目标；渠道请求还须校验绑定。目录包含 `/plan`、`/plan off`、`/goal`、`/goal status`、`/goal pause`、`/goal resume` 和 `/delivery`。选择菜单只填入输入草稿，不执行命令；工作室在没有 Session 时执行 `/goal`，先以 `{end_user_id,team_id}` 创建工作室 Session。

Goal 与送达属于客户端显式控制命令：两个聊天入口使用同一解析与反馈组件，将 `/goal [--rounds N] <目标>` 转为现有 `POST /chat/goals/create`，默认后续最多 3 轮，N 限定为 1 至 20；status、pause、resume 分别复用 `/chat/goals`、`/chat/goals/pause`、`/chat/goals/resume`。缺少目标或参数无效只在聊天输入框内提示，不创建会话或模型 Run；普通聊天不推定持续目标。控制命令不作为模型正文提交，写入失败重试保留 command_id 与初次取得的 expected_revision。无目标时不展示独立表单，已有目标只显示紧凑状态行，服务重启后仍须显式恢复。

`/delivery` 按当前会话选中的 Run 调用已有 `/chat/runs/delivery`，每次读取最新事实；无可定位的 Run 时只提示，不猜测运行。默认聊天不展开送达诊断，显式查询才在输入框内反馈；SSE 可重放不代表用户已读，Webhook unknown 不代表送达。以上控制 API 继续使用原租户、渠道、会话和 Runtime 权限边界，命令目录不授予执行权限。

`GET /api/v1/chat/events` 的订阅绑定受理时的真实租户、会话和主体。每个非空 Outbox 页面及首次 `history.retired` 在发送前重新验证当前会话访问权；空闲轮询只读取固定归属的候选页面，按单调时间每五秒复验访问权。五秒是检查调度间隔，不包括数据库检查自身的耗时。拒绝后关闭订阅且不发布候选内容，不缓存权限；心跳仅为无业务内容的 SSE comment。

页面取消通过 `POST /api/v1/chat/runs/cancel` 提交 `{session_id, run_id}`，进入 Runtime 持久取消协议；断开 SSE、切换会话或离开页面只释放连接。`cancelling` 表示取消意图已接受，页面通过 `GET /api/v1/chat/runs/status?session_id=…&run_id=…` 或 SSE 核验该 Run 终态后才允许继续发送。`waiting_hitl` 是挂起，不能作为取消完成。两接口均先验证当前租户的 Session 归属，再核对 Run 的受控访问与会话归属。取消请求的追踪上下文沿当前请求和后台继续处理传递；仅 Open Platform 的 `cancel_execution` 命令在重放时必须带原始 revision、receivedAt 与 trace，缺少原始回执时返回 409 `CANCEL_REPLAY_UNAVAILABLE`，客户端只能读取状态，不能自动重新提交取消。

取消过程中允许已提交工具动作继续收敛；`unknown` 表示服务端无法确认外部工具结果，不能当作成功或失败，也不能因取消把已执行的外部副作用撤销。产物只有在持久化完成、归属和内容摘要可核验后才进入 `ready`，客户端只能通过受控 artifact 引用读取。未完成发布的产物不得展示为 ready；Run 取消或另一个工具结果未知不抹除已经可靠发布的产物事实。

代码执行可以出现执行成功但交付失败：Sandbox 返回 `state: "completed"` 且 `exitCode: 0` 时，Tool 结果的 `success` 为 `true`；若随后产物文件传输或发布失败，结果仍保留 `success: true`，同时返回 `delivery_status: "failed"`、`delivery_error: "artifact_delivery_failed"` 和空 `artifacts`，客户端必须按交付状态阻止 ready 展示。

对话入口、历史、回放、协作状态、Plan 模式、取消执行与执行状态查询端点属于开放聊天面。公开终端请求使用当前已激活渠道的 `X-Channel-Token` 及上述终端用户凭证；签名 OpenAPI 使用绑定该渠道的 `X-Api-Key` + `X-Timestamp` + `X-Signature`，作为可信集成服务保留其渠道授权范围，不把正文中的 `client_ref` 或 `end_user_id` 当作独立登录身份。机构管理端 JWT 仍可按既有权限访问全机构会话。外部认证写入的租户与渠道身份不接受请求体覆盖，`ChatChannelAccess` 强制校验目标 Session 属于当前渠道且其 Agent 仍绑定并已发布；公开终端请求还须匹配已认证 `end_user_id`，列表及创建请求必须显式提供该用户，跨渠道或跨用户读写返回 403。历史、SSE、回放、成果、附件和文件票据沿用同一归属检查；仅供管理签名的 trace 等端点继续拒绝公开渠道凭证。渠道签发的成果文件票据绑定终端用户，消费时重查会话当前归属，缺少该绑定的旧渠道票据无效。`/api/v1/chat/runs/collaboration`、`/api/v1/chat/runs/plan-mode`、`/api/v1/chat/runs/cancel` 与 `/api/v1/chat/runs/status` 不属于仅 OpenAPI 的管理签名路径，也不接受 Tenant Open Platform ServicePrincipal 作为替代凭证。取消和状态查询继续由 Runtime 核对目标 Run 的租户与会话归属，不因开放渠道认证而放宽访问范围。

运行中补充使用 `POST /api/v1/chat/runs/steer`，请求 `{session_id,run_id,command_id,text}`；正文非空且最多 8192 字符，命令身份最多 200 字符。`GET /api/v1/chat/runs/steering?session_id=…&run_id=…` 查询同一快照：`{run_id,accepting,items:[{command_id,text,status}]}`。`status` 为 `PENDING|INCLUDED|CONSUMED`，分别表示等待纳入、进入已提交冻结请求、对应模型结果已被 Session 采用；不表示用户要求已经完成。相同 command_id 必须保持 Run 和原文相同，网络失败重试复用命令；终态拒绝新命令并保留原未消费内容，客户端可显式带入下一轮。两接口沿用上述渠道、租户、Session 与 Runtime owner/Agent 权限，返回前再次核验读取授权。

产物差异使用 `POST /api/v1/chat/artifacts/diff`，请求 `{base:{artifact_id,path},target:{artifact_id,path}}`，服务端分别授权并验证两份文件。`POST /api/v1/chat/artifacts/recovery-inputs` 以 `{session_id,artifact_inputs:[{artifact_id,path}]}` 校验后返回 `validated` 及真实 size/sha256；客户端仅生成下一轮请求草稿，不自动执行旧 invocation。范围、限制与来源关系见[产物设计](12-代码执行沙箱与产物交付.md)。

### 3.1 Plan 命令与协作端点

`POST /api/v1/chat` 和 `POST /api/v1/chat/sync` 的 `message` 支持精确的 Plan 命令解析：去除首尾空白后，`/plan` 选择 active，`/plan off` 选择 inactive，`/plan <文本>` 选择 active 并把 `<文本>` 作为本次模型输入；`/planner` 等没有空白边界的前缀按普通消息处理。Plan 选择与权限、审批、沙箱及工具目录独立；带文本的命令继续提交一次普通 Runtime 输入，纯模式命令不创建 Model Run。

纯模式命令的 POST JSON 信封中，`data.status` 为 `collaboration_updated`，`data.execution_id` 为 null，`data.collaboration` 包含 `active`、`pending`、`selected_active` 和完整 `todos[{content,status}]` 快照；`/api/v1/chat/sync` 返回同一业务 DTO。该命令不创建 Model Run，客户端不为它等待 SSE 订阅，也不能把协作快照本身当作 Run 终态或执行结果。`command_completed` 仅属于既有临时 `collaboration.updated` 通知，不是 ChatResult 字段。

宿主 `ChatConversationDirector` 将无 `execution_id` 的 `collaboration_updated` 识别为协作命令：不写入用户消息，不增加 Session 消息计数，不更新时间或提交闲聊摘要，也不记录普通请求用量；带文本的 `/plan <文本>` 具有普通对话输入的持久化和计量语义。

`GET /api/v1/chat/runs/collaboration?session_id={session_id}` 读取当前会话的规划模式选择状态，包括 `active`、`pending` 和 `selected_active`；任务步骤使用同一用户轮次下的通用计划快照。`active` 是当前运行实际使用的模式，`selected_active` 是最近选择的目标，`pending` 表示该选择等待下一次已接受的准备阶段生效。

`POST /api/v1/chat/runs/plan-mode` 选择协作模式，请求体为 `{session_id, command_id, active}`，三个字段均必填；`command_id` 是该控制命令的稳定输入身份，重复命令按 Runtime 幂等语义处理。端点返回与上述协作查询相同的快照。Controller 只验证当前租户的 Session 归属并转交 `SessionAgentRuntime` façade；owner、Agent、终端用户、渠道和 Runtime ServicePrincipal 身份在 façade 与 Runtime 边界重新校验。

### 3.2 Plan 评审恢复

历史接口以 `pending_interactions` 数组返回所有等待人工输入的执行（无待办为空数组），每项保留完整的执行与检查点身份。客户端按 `execution_id` 展示和提交，结束一个执行只移除对应项；普通消息可以启动独立任务，不能代替待办恢复。

模型调用 `exit_plan_mode` 后，`pending_interactions` 中的单项只有在 `interaction_type: "plan_review"` 且 `card.type: "plan_review"` 时才进入 Plan 评审展示。评审载荷必须保留完整 Markdown `plan` 与 `title`，并携带同一挂起交互的 `execution_id`、`run_revision`、`checkpoint_revision`、`action_id`、`invocation_id`、`pending_id`、`wake_id` 和 `wait_revision`；客户端恢复时逐字段原样提交，不能用普通 HITL 的部分身份或前端生成的替代值。

评审通过 `POST /api/v1/chat` 的 `hitl_response` 恢复，结构为上述完整身份字段加 `plan_review: {decision, feedback}`，其中 `decision` 仅为 `approve` 或 `keep_planning`。`approve` 选择退出并使 Plan 进入 pending inactive，`keep_planning` 只提交反馈并保持 active；身份缺失、版本漂移、计划不完整、取消或通道不可用均拒绝恢复且不改变 Plan 选择。评审卡展示与普通消息输入互斥，普通文本不能绕过该精确恢复身份。
普通工具补参使用同一个 `POST /api/v1/chat` 的 `hitl_response`。`interaction_type: "tool_input"` 与 `card.type: "tool_input"` 同时成立时展示表单；提交完整的 execution/run/checkpoint/action/invocation/pending/wake/wait revision 身份以及 `tool_input.responses`。响应以请求 ID 为键，每项为 `method` 和 `result: {schema_id, canonical_json}`；当前公开表单只接受 `elicitation/create`，其结果 schema 为 `application/json`，正文为 `{action:"accept",content:{...}}` 或不带草稿内容的 `{action:"decline"}`。服务端精确匹配当前等待的请求集合与方法，拒绝混合 PlanReview、过期卡片和其他 owner 的响应。公开卡片仅包含问题与表单 schema，不公开 Tool requestState。回复进入原 Run 的 ACTION 入站，不另建 Run；再次挂起必须使用新的等待身份。

人工协助采用独立 Handoff 管理端契约：详情从原产品 Session 读取公开历史、过程摘要和成果引用；回复只提交工单、期望 revision、稳定 command ID 与正文，租户、Session 和坐席身份由服务端确定。回复请求先持久受理，再以 `AppendHumanAssistanceCommand` 向 Session 提交唯一 `human.assistance` 事实。SessionLog 同时供历史、Outbox 和后续模型准备读取，受理表不是第二份消息正文权威。该命令不创建 Run、不主动调用模型、不冒充终端用户输入；既有冻结准备保持不变。关闭会话拒绝新回复，已提交事实仍可幂等取得原回执。人工协助不改变工具权限、目标授权或任务完成状态。

目标语义统一映射为 InboundEnvelope：

| 输入 | 要求 |
| :--- | :--- |
| message | 用户文本或结构化输入 |
| session_id | 必填且必须指向调用者已有、可访问的 Session；`/api/v1/chat` 与 `/api/v1/chat/sync` 都不得自动创建 Session，必须先通过 Session API 创建或复用 |
| agent_id | 必须与已有 Session 的绑定一致；不能借请求体改写 Session 的 Agent 身份 |
| client_message_id / idempotency key | 必填且稳定，最长 64 字符，映射为 inputId；重试必须复用同一值；超长输入在 Runtime 受理前返回 HTTP 400 |
| action | 点选或结构化恢复动作，必须包含可验证目标 |
| scope | 只作身份与可见性上下文，不能覆盖 Session 固定绑定 |

用户入口不得接受 Workflow 作为会话目标。旧 `workflow_id` 直连字段和“Agent/Workflow 二选一”语义应随 M2/M6 删除，不保留兼容分支。

同步与 SSE 入口共享同一 Inbound、Session 和决策链，仅传输方式不同，不允许形成两套业务语义。

Tenant Open Platform 的 Session API 覆盖以下语义，具体路径由生成 OpenAPI 定义：

| 操作 | 约束 |
| :--- | :--- |
| 创建 Session | 指定已部署 Agent、入口 `end_user_id`、externalUserRef、externalConversationRef 和允许的初始化参数；服务端校验 end_user_id 归属后返回 sessionId 与 eventCursor |
| 提交输入 | message、action、callback、command 统一转换为 InboundEnvelope，并使用 inputId 幂等 |
| 查询摘要 | 返回 Session、Agent deployment、活动 Execution 摘要和最新 cursor，不返回 checkpoint 或记忆原文 |
| 读取事件 | 按 sessionSequence/cursor 获取与 SSE、Webhook 相同的 Outbox 投影 |
| 关闭 Session | 产生受审计的关闭命令；不隐式删除 Execution Ledger 或费用事实 |

业务服务先调用 `POST /api/v1/open-platform/end-users/ensure`，在凭证固定的 Tenant/integration 中取得用户映射，再创建私聊 Session；业务范围必须符合机构接入绑定及资源权限。共享群目标改为一个 GroupBinding 对应一个共享 Session，真实作者、请求者和本次 Agent 分开记录，不能沿用按成员/Agent 拆群会话；其正式输入/owner 类型以 [Harness 03 §5.1.1](../../harness-design/03-核心对象模型与状态机.md#511-群归属与执行身份目标契约)为准。Session、Run 和委派的可信来源独立于消息 context，去除 Application 后继续检查 Tenant/integration 和对象授权。

`/sessions/messages` 接受有序 `content`、业务 `context` 和授权材料 `references`，复用聊天内容及公开材料契约；消息受理响应包含稳定输入与 Run 身份，幂等重试复用原受理。`GET /sessions/history`、`/status`、`/events` 和 `/stream` 分别提供公开历史、真实 Run 状态、游标补拉与 SSE；所有读写统一复验 Tenant、integration、Session 和 scope，群操作同时检查当前成员及服务资格。`/sessions/steering` 和既有 actions/commands 进入原 Runtime 控制链。`/sessions/attachments` 与 `/media` 复用会话授权上传；`/sessions/deliverables` 和 `/deliverables/file` 只访问正式发布成果，不公开工作区中间文件。精确请求和响应结构见版本化 OpenAPI。

`GET /open-platform/sessions/messages/receipt?sessionId=...` 用于原 `/messages` 受理响应丢失后的只读核对，携带首次请求的 `Idempotency-Key`（1–256 字符），要求当前 `sessions.read`、同一 tenant/integration/Session 归属及 Runtime 读取授权。服务端复用原键身份工厂；凭证轮换不改变原输入身份。HTTP 200 的 `data.observation=FOUND` 携带原准确 `accepted` 回执（`receipt`），其中原 input/rootInput/event/Run 身份保持一致，`replayed=false` 表示本次只是查询；FOUND 不代表执行完成，取得 runId 后继续读取 `/status` 或原事件流。`data.observation=NOT_OBSERVED` 的 `receipt` 为空，仅表示本次尚未观察到已提交受理事实，不能证明未发送、清除 UNKNOWN 或授权重试；原请求仍可能正在受理。查询不创建 Session/Run、不重提消息、不唤醒执行，也不支持 actions、commands 或其他 operation。跨 integration、当前撤权及存储故障是错误，不能转换成 NOT_OBSERVED。


`POST /api/v1/open-platform/sessions/workflow-invocations` 提供明确调用正式 Workflow 的入口，要求当前服务主体拥有 `sessions.write`，请求头 `Idempotency-Key` 非空且最多 256 字符。请求体为 `{ "session_id": "...", "mount_id": "...", "capability_id": "...", "version_id": "...", "parameters": {} }`；能力与版本 ID 使用正整数十进制字符串，`mount_id` 指向会话当前 Agent 的精确挂载，`parameters` 为 Workflow 输入 schema 定义的业务 JSON 对象。身份、Tenant、integration、EndUser 与业务范围均从当前凭证及冻结 Session 取得，参数不授予任何身份或调用资格。

该入口运行在已按正式 Agent 契约配置模型的 Session 上，保留当前模型配置就绪检查，不提供无模型 Agent 或无模型 Session 能力。明确的初始 Workflow intent 及确定性节点执行完成链不准备 MODEL 请求；Workflow 自身显式配置的模型节点仍按其原节点契约执行。

该入口只允许当前有效、`user_invocable=true` 的正式发布 Workflow 挂载，按同一正式版本 descriptor 的 `input_schema` 校验参数，缺失必填、类型或范围不符以 `workflow_invocation_input_invalid` 返回 422，拒绝前不受理 Run；随后精确冻结原实例、定义版本、安装 revision 和参数，通过原 `AgentRuntimeExecutionGateway` 与 `ExecutionStore.admit` 受理。测试会话、已关闭会话、未挂载、非正式版本、版本或挂载不匹配均拒绝；派发及恢复继续复验当前正式目标和 IAM。入口不调用模型选择 Workflow，不新建执行引擎。幂等命名空间包含 Tenant、integration、Session 和操作类别；相同键及相同参数返回原 Run 回执，相同键更换挂载、能力版本或参数返回 409。JSON 对象键顺序不影响参数身份，数组顺序与所有值保持原样；重复请求仍复验当前凭证和会话授权。

响应复用 `OpenPlatformInboundReceiptResponse`（`inputId`、`rootInputId`、`eventId`、`runId`、`status`、`replayed`）；受理不代表执行成功。后续使用原 `/sessions/status`、`/events`、`/stream`、`/actions` 和 `/commands` 查询、等待响应与取消。超时或断连后保留原键核对原受理，不生成新的业务操作。


SSE 与游标补拉消费同一冻结 Outbox 投影。最终正文由已校验并完成的 Run 结果产生，接入端按 message_id 去重，保留 `phase=final/state=completed`；执行过程使用独立 process 事件，`execution.completed` 的 `waiting_hitl` 表示挂起。断线只释放订阅，不取消任务，不重发输入或重新生成已发布正文。

action 可以携带 sessionId + executionId + actionKey 和受 schema 校验的值，但 API 只提交 Inbound，不开放 Workflow run/resume。command 只包含平台声明的会话或任务命令，不能用自由 Map 调用内部服务。

### 3.3 持续目标控制

`GET /api/v1/chat/goals?session_id=…` 返回明确 GoalStatus 实体 `{goal, continuation_enabled, completion_pending, publication}`，无目标时 `goal=null`。Goal 包含 `goal_id`、`revision`、`objective`、`state`、`max_rounds`、`rounds_started`，以及可空的 `last_run_id`、`pending_round_input_id`、`reason`；状态使用大写 `ACTIVE|PAUSED|COMPLETE|BLOCKED`。关联标识只供程序恢复与控制，界面显示目标正文和可读状态。读取不启用自动续行。

`POST /api/v1/chat/goals/create` 接受 `{session_id, command_id, objective, max_rounds}`，目标非空且最多 8000 字符，轮次 1–20；API 校验与 Runtime 复用 SessionGoal 所属限制。`POST /api/v1/chat/goals/pause` 与 `/resume` 接受 `{session_id, command_id, expected_revision}`。命令身份最多 200 字符；同命令幂等，版本竞争不隐式重试。端点先验证租户、渠道、Session 与 Runtime owner 权限，恢复不接受模型自行提出的授权。

页面对已有 Session 提供目标创建、暂停、继续和手动刷新，默认 3 轮，无自动轮询。关闭页面不取消后台执行；服务重启后需要用户显式恢复。执行轮次和取消规则由 [Harness Goal 契约](../../harness-design/03-上下文视图与执行优化.md#23-持续-goal)定义。

### 3.4 执行与送达状态

`GET /api/v1/chat/runs/delivery?session_id=…&run_id=…` 在 Session 与 Run 授权后读取同一租户、会话和 Run 的 Outbox 聚合，返回 `run_id`、`runtime_status`、`sse`、`webhook` 与最多 10 条失败尾部。事件通过显式 `runtime_run_id` 关联，不从正文或 trace 猜测归属。

SSE 状态为 `replay_available|unknown`，存在已提交输出时返回 `replay_available` 及 `replay_available_count`，不维护待发布数量；它只证明服务端可重放。Webhook 状态为 `pending|delivered|failed|unknown`，`delivered` 只证明订阅端确认传输。两者均不表示终端用户已阅读，也不改写 Runtime 的执行成败。多个 Webhook 订阅分别计数，不能使 SSE 事件数重复。以上 Goal 与送达端点适用同一开放聊天渠道认证与 Session 归属检查。

### 3.5 公开材料引用

普通对话的 `ChatRequest.references` 是顶层类型化选择器列表，最多 64 个不同选择器；客户端只提交身份与版本，不能提交材料名称、正文、路径摘要或服务器冻结快照。四类选择器如下：

| `kind` | 选择字段 | 首次受理校验 |
| :--- | :--- | :--- |
| `artifact_files` | `files[{artifact_id,path}]` | 当前 Session 归属、文件清单、真实 size/sha256 与当前读权 |
| `deliverable_revision` | `revision_id`、`purpose=input\|revision_base` | 指定已发布成果版本；`revision_base` 必须仍为当前版本，单消息只能选择一个基础版本 |
| `message` | `source`、`message_id`、`message_version` | 公开消息仍可见且版本精确匹配 |
| `process` | `source`、`process_id`、`updated_sequence` | 公开过程仍可见且更新序号精确匹配 |

`source` 是 `{kind:"session"}` 或 `{kind:"work_task",work_id,task_kind:"plan"|"direct",task_id}`。Session 指当前产品会话；成员来源由服务端从父工作/任务绑定解析实际独立 Session 与 Run，不接受客户端指定 child Session 或 child Run。展开后最多 2,048 个不同文件，首次受理将已授权材料与名称冻结到现有 input ledger；缺失材料或版本过期不得先受理再补齐。`context.attachment_ids` 保持既有上传附件契约；客户端不能用 `context.artifact_inputs`、`context.base_revision_id` 或 `context.input_references` 绕过顶层引用。

普通消息允许 `content=[]` 且 `context.attachment_ids` 非空。Runtime 受理后仍持久化该用户消息，历史 `metadata.attachment_ids` 保存相同的附件选择器，`metadata.attachments` 保留首次受理时已授权并冻结的附件摘要（`id/name/input_path/size/sha256/expires_at`），用于显示资料名称；公开消息不携带 `attachment_readings` 正文，附件摘要不授予新的读取权限。图片继续通过有序 `metadata.content_parts` 保存选择器；同一 `client_message_id` 重试也必须保持附件列表一致。长文本粘贴可先作为本地草稿附件，发送时再走现有 UTF-8 文本上传入口；本地预览不解析 HTML，还原原文只适用于粘贴来源，使用粘贴时保存的输入选区。草稿已改变时只在原位置插入，不覆盖后续编辑。纯附件输入首次冻结时按[附件文本准备预算](12-代码执行沙箱与产物交付.md#用户上传的会话附件)准备已授权小文本的读取事实，先基于真实内容概述再询问目标；超出预算或需文档解析的类型仍走正式读取能力。带文字目标的附件输入沿用受控文件读取流程，不额外进行模型预调用；客户端不能提交 `context.attachment_readings` 伪造读取事实。

同一 `client_message_id` 重试必须带相同选择器与业务正文；同键异体返回 409。合法重放只重新确认当前父/成员读权、原材料仍可访问和不可变文件来源，不重新读取消息/过程的新内容版本，不改写原冻结标题、正文、引用、版本或 Runtime 目标。引用展示使用 `ChatReferenceView{label,source}`；label 来自服务端并通过公开检查，source 保留类型化身份，程序标识不拼入普通文字。

机构成员可通过 `GET /api/v1/chat/citations/content?session_id=…&message_id=…&citation_id=…` 读取知识依据片段。三个参数均为必填，`citation_id` 是已公开完成消息中的精确引用身份；成功返回 `ApiResponse` 的 `data: {label,source_version,text}`，响应设置 `Cache-Control: no-store`。`label` 是展示标签，不保证为知识库或文档名称；`source_version` 和 `text` 来自原执行实际采用的冻结来源版本与结果，不跟随当前版本替换。

读取要求当前机构成员具备 `foundation.sessions.read`、目标会话访问权和对应知识来源的当前读取权限。服务端核验已公开的助手完成消息、原完成事件引用、原知识调用和结果的归属及版本，再检查片段可公开性；引用 ID 本身不授予读取权。身份、引用或原结果不匹配及片段不可用时拒绝读取，权限不足按对应授权边界拒绝；成功读取记录安全审计。该接口不授予渠道凭证或 Tenant Open Platform ServicePrincipal 读取能力，也不执行新的知识检索。

机构调试对话与独立会话端在派发前固定完整消息请求，包括会话、目标、`client_message_id`、正文、图片及附件身份。结果未知时保留原请求，阻止改稿重建或切换会话丢失身份；受理状态核对仅 GET 当前会话历史，必须匹配用户消息的精确消息 ID 或 `metadata.client_message_id`。同文案、助手消息或其他 Run 终态都不是原输入受理证明。显式重试仍发送原请求；已有 UNKNOWN 不因后续 403、404、409 或预算前置拒绝解除。首次明确派发前拒绝才恢复编辑并保留草稿，成功只清理原请求所含草稿资源；不把消息正文持久化到浏览器。该保护面向已确认 Session 内的输入，不为 Session 创建新增恢复协议。

`POST /api/v1/chat/deliverables/recovery-inputs` 返回类型化 `RecoveryResponse`，包含服务端 `references`；客户端把其中 `source` 加入下一轮输入草稿，仍须用户提交。版本恢复不依赖前端拼装内部 `artifact_inputs/base_revision_id` 上下文。

`GET /api/v1/chat/work/tasks/detail` 使用 `session_id/work_id/task_kind/task_id` 与绑定该来源的不透明 `cursor` 读取成员任务详情。返回任务、Run 状态、公开过程页、Pending 和报告；查询扫描成员自己的 SessionLog，过程页与主助手共用公开投影。成员读权撤销或来源绑定不成立时拒绝返回，父 Session 历史不能作为成员详情的替代来源。

### 3.6 会话容量读取

`GET /api/v1/chat/limits?session_id=...` 在当前产品会话授权后返回明确的附件、引用及文件选择容量。两端共享读取，不从提示词、模型窗口或错误文案推算容量。附件默认单文件 50 MiB、每条 16 个、合计 200 MiB；引用最多 64 项，文件选择器合计 2,048 个。服务端仍执行最终去重、权限、版本、SHA 和容量校验。会话切换取消旧请求并拒绝迟到结果，不能用旧会话限额覆盖新会话。

`GET /api/v1/chat/runs/budget?session_id=…&run_id=…` 需要 `foundation.sessions.read`，按当前租户及会话读取权限验证后，继续核对 Run 的完整会话和终端用户归属，再读取原预算账本与 registration。当前平台入口只投影 Enforced 有限策略；ObserveOnly 明确以 `budget_policy_not_supported` 拒绝，不补造限额或增加可空限额的另一套响应。响应提供 `run_id/root_run_id/scenario/role/phase/source_version`、Root 与 Run 的冻结限额/已消耗/未结算预留/已确认活跃时间，以及收尾保护；资源区分业务模型、辅助模型、工具、知识、输入、输出及总 Tokens，全部计数和秒/毫秒值用十进制字符串传输，精确 DTO 归[只读预算入口](../../backend-java/skillforge-institution-service/src/main/java/com/skillforge/institution/controller/ChatRunBudgetController.java)。查询不唤醒执行、不读取当前策略、不推算余额或阶段已用量，也不将未知用量预留归零；不公开租户、Attempt 或内部执行材料。

### 3.7 个人浏览器连接控制

`/api/v1/chat/browser` 使用当前认证机构及个人身份。机构端提供已授权 `session_id`；渠道端提供已登记 `client_ref`，两者必须且只能提供一项，继续执行现有渠道与终端用户凭证检查。客户端不指定 `tenant_id` 或 `end_user_id`。连接请求还须属于当前个人及其可读来源 Run；机构端的所选会话必须命中原产品会话。

| 端点 | 请求与返回 |
| :--- | :--- |
| `GET /devices` | 身份查询参数；返回当前个人设备目录和默认浏览器 |
| `POST /pair` | 身份字段，可选 `connection_request_id`、`make_default`；返回一次性受控交付的 `pairing_url`，不能保存到连接请求、日志或聊天消息 |
| `POST /select` | 身份字段、准确 `device_id`，可选 `connection_request_id`、`make_default`；返回设备目录 |
| `GET /connection-requests/detail` | 身份查询参数和 `request_id`；返回 `BrowserConnectionView`，只读查询，不签发凭据或代替恢复提交 |
| `POST /connection-requests/cancel` | 身份字段和 `connection_request_id`；取消准确连接等待，成功响应无业务正文，不撤销独立设备授权 |

`pair/select` 省略 `connection_request_id` 时继续作为独立设备配置：配对不创建原工具等待，选择直接保存个人默认设备。有该字段时，动作只作用于准确连接请求；`make_default=true` 表示用户明确要求在恢复时保存默认设备，未提供或为 false 不改变个人默认配置。配对先持久化已派发事实，清除该请求原离线设备目标，再发起一次官方控制调用；重复点击或未知结果不能再次签发。选择校验本人准确设备及有效授权，设备可在之后上线；目标冻结后只能幂等重复同一选择，不能改选。

`BrowserConnectionView` 包含 `connection_request_id/status/reason/device_id/browser_id/make_default/devices/error`，不含配对串、设备密钥或 Runtime 恢复载荷。`status` 取 `WAITING / READY / RESUMING / RESUMED / CANCELLING / CANCELLED / FAILED`，`reason` 是首次等待原因 `NO_SELECTION / OFFLINE / AUTHORIZATION_REQUIRED`；`RESUMED` 仅表示原工具等待的恢复输入已受理，不代表浏览器任务成功。只有 `WAITING` 可以发起新配对、改选或取消，迟到的竞争操作返回 409；不存在和不属于当前来源的请求分别拒绝为 404 或 403。

真实在线与准确配对关联由服务端后台观察，页面关闭不终止该观察。等待、稳定输入去重及授权边界见[BrowserSkill 连接续跑](18-BrowserSkill远程浏览器接入.md#8-按需连接与自动续跑)，数据归属见[连接请求模型](03-数据模型设计.md#36-个人浏览器连接请求)。原浏览器任务的 `/tasks`、`/cancel` 与连接等待查询、取消是不同资源；连接取消不冒充上游任务清理回执。

## 4. 外部输入

### 图片上传与有序内容

通用图片输入采用[多模态内容与媒体引用](../../harness-design/03-多模态内容与媒体引用.md)的内容与材料契约。宿主提供鉴权图片上传入口，验证当前机构和终端用户归属，持久化文件与材料身份后返回可提交的受管引用；上传不自行创建 Run，也不允许请求指定其他用户的 owner。普通聊天 HTTP 请求统一使用 `content` 列表，服务端与两个聊天客户端同步更新；`message` 只作为 Java 内部文字投影，不再是请求字段。实际运行结果应针对当前候选单独验证。

用户提交内容是保留顺序的文本与图片项，支持纯图及图文混合；适配器不能将图片 URL 拼成文字、按类型重排内容或强制补一个虚构文本正文。受管图片引用按会话用户授权核验，浏览器截图使用相同材料机制。BrowserSkill 设备管理与任务查询属于用户控制面，内部浏览器命令接口不直接开放给聊天客户端，具体宿主边界见[浏览器接入专题](18-BrowserSkill远程浏览器接入.md)。

图片上传原请求返回 `SESSION_MEDIA_UPLOAD_REJECTED` 表示图片大小或内容在任何图片写入前被拒绝；客户端可显示原因并允许用户重新选择。仅该原请求的明确回执可解除对应待核对记录；其他错误以及原上传查询未找到均不能证明上传失败。

图片与普通聊天采用以下固定端点与类型化正文：

| 端点 | 请求与返回 |
| :--- | :--- |
| `POST /api/v1/chat/sessions/media/upload` | multipart `session_id`、稳定 UUID `upload_id`、`file`；返回 `{media_id,mime_type,byte_length,width,height}` |
| `GET /api/v1/chat/sessions/media/limits` | 返回 `{max_file_bytes,max_pixels,mime_types}`；首版 PNG/JPEG/WebP，50 MiB、4,000 万像素 |
| `GET /api/v1/chat/sessions/media/content?session_id=...&media_id=...` | 当前产品会话鉴权后的图片字节，`Cache-Control: no-store`；委派图额外核验来源 Agent 的当前可读权 |
| `POST /api/v1/chat` | `content` 中每项为 `{type:"text",text:"..."}` 或 `{type:"image",media_id:"UUID"}`；沿用 `session_id`、`client_message_id`、目标和身份上下文 |

例如 `content=[{type:"image",media_id:"..."},{type:"text",text:"比较第一张与第二张"},{type:"image",media_id:"..."}]` 保留三项顺序。纯图无需补空文字。客户端只能提交已上传到当前 Runtime 会话的 `media_id`，服务器解析摘要、实际尺寸、MIME 和归属；重放依据完整图文指纹判断同键同体。历史 `metadata.content_parts` 保留这些有序选择器，不能只保存文字正文或将图片统一移到末尾。

浏览器截图可以来自委派子会话：模型引用仍绑定该子 Runtime 会话；用户界面以产品会话身份请求显示。产品展示权限不赋予父 Agent 对子会话媒体的自动读取权。

### 4.1 回调

Runtime 回调投递使用固定路径 `POST /api/v1/runtime/callbacks/deliveries`，`tenantId`、`callbackId`、`deliveryId` 分别通过 `X-Tenant-Id`、`X-Callback-Id`、`X-Delivery-Id` 请求头传递；callback-v1 签名仍绑定三个标识、时间戳与原始请求体摘要。

`async_task` 的生产注册入口为 `POST /api/v1/open-platform/sessions/workflow-callbacks`，请求体 `{session_id,run_id}`。调用者需要 `sessions.write`，并且必须是该 Open Platform 会话所属 integration 和原 Run 使用的同一 ServicePrincipal、同一凭据版本。服务端从持久等待读取 Execution、actionKey、两个 revision 与截止时间，只接受尚未取消或到期的 `async_task`；同一等待重复注册返回同一个 `callback_id`。响应包含投递路径、精确目标、载荷 schema 和签名策略，不返回密钥。回调仍使用调用者原签发的 signing secret；凭据轮换后旧版本不能继续投递。机构聊天身份不能借此创建外部集成的回调。

投递正文使用工作流规范的七项数组，内层响应必须携带注册时返回的 `suspend_ref`、`action_key`、`execution_revision` 与 `checkpoint_revision`。注册不执行节点；投递后的确定结果由原恢复链处理。等待已结束时注册返回 409；回调与超时竞争同一等待 revision，不能重复执行后继节点。

渠道和 ServicePrincipal 的 HTTP HMAC 签名输入绑定完整请求目标：路径后有查询串时追加 `?` 与原始查询串，签名和发送使用相同的参数顺序及编码，不解码或重排。

外部回调必须完成签名、租户归属、重放保护和 inputId 幂等，然后转换为 callback Inbound。投递 Controller 不得直接读取 checkpoint 或调用 Workflow 恢复方法；注册入口只核验持久等待来源。

### 4.2 定时触发

Scheduler 只产生 scheduled Inbound。超时动作由 Recovery 定位 Pending，并经 WorkflowPortal 执行 CAS 恢复。

### 4.3 后台完成

Execution 终态经 durable outbox 投影为带稳定 `source` 判别值的 recovery Inbound，由 Agent 决定是否通知、总结或继续任务。消费者按 eventId 与 inputId 幂等。

### 4.4 出站事件订阅

出站 Webhook 只消费持久 Outbox/ControlOperation 事件。订阅声明允许事件、资源范围、端点、签名版本和停用状态；每次投递具有 eventId、deliveryId、attempt、状态和下一次重试时间。

入站回调与出站订阅使用不同端点、签名方向和幂等账本。出站至少一次投递，三方按 eventId 去重；投递失败后可按 cursor 拉取同一事件，不能重新生成业务结果。

## 5. 管理与控制 API

机构后台新建 MCP 连接器使用 `POST /api/v1/connectors/instances/create-with-receipt`，请求包含 UUID `request_id` 和连接器 `payload`。MCP 发现成功后，创建身份与连接器行一并保存，回执仅返回请求和连接器标识；不保存请求正文或明文凭据。响应未知时使用 `GET /api/v1/connectors/instances/create-with-receipt/result?request_id=...` 只读核对，要求当前成员是原创建人且具有连接器读取权限；204 不证明原请求未受理。回执随连接器删除而消失，不提供 POST 重放契约。服务端在插入前明确识别的 MCP 发现失败返回 `CONNECTOR_CREATE_REJECTED`；发现结果未知或其他未证实的写入结果不能盲目重建。

机构后台更新 MCP 连接器使用 `POST /api/v1/connectors/instances/update-with-receipt`，请求包含 UUID `request_id`、`instance_id` 和更新 `payload`。更新与成功回执在同一事务提交；回执仅返回请求及实例标识，包含凭据的请求摘要使用业务加密密钥封存，不保存明文凭据。同一租户、成员、请求号和相同内容的重复提交返回原回执；不同内容或成员使用同一请求号时返回冲突。`GET /api/v1/connectors/instances/update-with-receipt/result?request_id=...` 要求原成员及连接器读取权限，204 不证明原请求失败；回执随连接器删除而消失。确认在事务内被拒绝且已回滚的业务错误返回 `CONNECTOR_UPDATE_REJECTED`，其余未知结果只查询原回执，不自动重发。密钥轮换后，历史摘要的解密沿用已配置的业务历史解密密钥。

机构后台删除连接器使用 `POST /api/v1/connectors/instances/delete-with-receipt`，提交 UUID `request_id` 和 `instance_id`。删除和成功回执同事务提交；回执独立于连接器保存。同一租户、成员及实例的相同请求号返回原回执，请求号与其他内容或成员冲突时不能据此认定原操作失败。`GET /api/v1/connectors/instances/delete-with-receipt/result?request_id=...` 仅允许具有读取权限的原成员核对；204 不代表原请求失败。事务回滚的明确业务拒绝返回 `CONNECTOR_DELETE_REJECTED`，未知结果只查询原回执，不自动重发。


管理与知识内容 API 分为以下语义组，具体路径与字段由同版本 OpenAPI 定义：

| 语义组 | 最小约束 |
| :--- | :--- |
| Agent 管理 | 直接创建机构草稿 Agent，或安装已发布 Agent 模板；模板校验、不可变发布版本、Deployment、Persona/Preset/Scope、能力绑定和运行预算可追溯 |
| Workflow 管理 | 草稿定义、发布前能力校验、不可变 DefinitionVersion 和 Agent binding |
| Skill 管理 | 接受以 `SKILL.md` 为入口的目录或 ZIP，校验标准 metadata、引用和包预算，创建不可变版本并支持内容读取与 default/latest 指针；`ALWAYS/ON_DEMAND`、依赖/冲突和 Agent mount 是宿主治理元数据，包内脚本不获得执行权限，凭证或 Provider 配置一律不进入包 |
| Tool 管理 | ToolDefinition/Version 与 ToolDeployment 分离；schema、风险、幂等、确认策略和受管 Provider 绑定可追溯 |
| Knowledge 管理 | KnowledgeBase、来源授权、文档版本、异步摄取任务、审核、ready revision 和 active 发布 |
| Session 查询 | 只返回会话摘要、消息投影和活动 Execution 摘要 |
| Execution 查询 | 从 Registry/Ledger 投影读取，不暴露内部 checkpoint |
| Execution 取消 | 校验权限并经 WorkflowPortal CAS |
| 记忆管理 | 支持查看、纠正、删除和来源解释 |
| 连接器管理 | 凭证只存 ConnectorInstance，响应不返回明文 |
| Builder/Marketplace | 只创建、校验、发布、安装和升级版本化资源；不暴露执行端点 |
| Handoff/运营 | 只操作受控任务和投影；不返回 checkpoint、内部变量或原始 Provider 载荷 |
| Billing/Compliance | 只消费 Usage/Audit 等权威账本；调整通过追加事件，不改写调用事实 |
| 平台管理 | 平台账号与租户账号身份域分离；模型目录和运营配置的写入要求平台主体具备相应动作权限 |

已发布 Agent、Agent 模板、Workflow、Skill、Tool、Knowledge Source、Persona 和 Policy 不允许原地修改；更新必须创建新 draft/version。ChannelBinding 只指向已部署 Agent revision，CapabilityMount 引用已发布能力并使用类型化配置。机构 Agent 的技能挂载请求须提供正数 Token 预算，激活方式由服务端按当前发布版本确定；请求可省略 `activation_mode`，即使提供该字段也不覆盖发布配置。底层知识绑定类型包含 FOLLOW_ACTIVE 和 PINNED_REVISION；当前机构 Agent 挂载管理入口构造 FOLLOW_ACTIVE，不能据此认为页面支持选择固定修订，见 [Harness 挂载契约](../../harness-design/03-核心对象模型与状态机.md#54-类型化-capability-契约与挂载快照)。Agent 委派和产品运营权限使用独立授权，不伪装成 CapabilityMount。模板在稳定定义下编辑工作草稿，发布追加不可变快照并切换当前指针；下架是独立动作，历史快照保留。安装或部署是否跟随当前发布依具体模式判断。

普通 `POST /api/v1/agents` 只创建机构直接草稿 Agent，不接受 `template_id` 分支。模板安装使用独立端点，避免把模板版本选择和普通草稿创建混为一条语义。

Agent 与共享定义的创建、更新及模板安装名称最多 128 个 Unicode 码点，按原始输入校验，不截断超长名称；更新名称缺失或 null 的既有不修改语义保持。普通创建的名称错误路径为 `name`，更新、保存并发布及创建回执的嵌套路径为 `payload.name`。越界在进入应用服务前返回 400 和 `field_errors`；创建回执与模板安装分别返回 `AGENT_CREATE_REJECTED`、`AGENT_INSTALL_REJECTED`，普通创建、更新及保存发布返回 `VALIDATION_ERROR`。首次明确字段拒绝允许修正输入，已有未知操作仍需按原回执核对，不因后续校验失败解锁。

机构知识检索验证使用 `POST /api/v1/knowledge/search`，要求 `foundation.knowledge.run` 和目标知识库 execute 对象权。返回条数上限按本次请求显式 `top_k`、知识库已保存的 `top_k`、当前运营默认条数依次取值；请求省略或传 null 均表示继承，不由 Controller 补入固定条数。本次覆盖不保存知识库设置，关闭覆盖后恢复该默认顺序。`source_version` 另行确定精确来源版本，不改变条数优先级。该管理检索默认不替代 Agent Runtime 知识调用的冻结 `KnowledgeBudget.maxItems`；Runtime 仍按其已授权来源、条目与字符预算取证，恢复不重选预算或重跑查询。

管理检索响应的 `rerank_status` 记录本次实际重排阶段：`DISABLED` 为有效设置未启用，`NO_CANDIDATES` 为启用但无候选，`APPLIED` 为重排已返回结果，`DEGRADED` 为重排不可用而保留原检索顺序。该状态不通过得分推断，也不改变 Runtime 的知识调用契约。

检索结果项携带命中的 `source_version`。机构成员可使用 `GET /api/v1/knowledge/documents/version?docId=…&sourceVersion=…`，在知识读取及目标文档读取权限下只读核验对应版本的标题和正文；指定版本不存在或不可用时返回错误，不替换为当前文档。当前文档的编辑入口独立于该只读核验。

机构工作台通过 `POST /api/v1/agents/create-with-receipt` 提交 `{request_id,payload}`，一次创建草稿并同事务保存原请求回执；同一主体、请求号及内容重放返回原 `{request_id,agent_id}`，不同内容或操作者冲突。`GET /api/v1/agents/create-with-receipt/result?request_id=…` 仅供原主体在当前仍有 Agent 和该资源读取权限时核对；204 表示暂未查到，不证明原请求失败，也不触发创建。回执不保存提示词或配置正文。

渠道列表、详情和更新结果以 `api_key_issued` 表示 OpenAPI 凭据签发状态；`config` 不包含哈希或密文，提交凭据字段返回参数错误。`POST /api/v1/channels/api-keys` 与 `/api-keys/rotate` 原子替换凭据并仅在当前响应返回明文，`DELETE /api/v1/channels/api-keys` 原子吊销；通用配置修改不能覆盖并发轮换的凭据。

渠道 API Key 的可核对签发使用 `POST /api/v1/channels/api-keys/issue-with-receipt`，提交 `request_id` 和 `channel_id`。凭据更新与不含明文的回执在同一事务提交；首次成功响应才返回 API Key 和 Secret 明文，重复请求只返回请求及渠道标识。原机构成员具备渠道读取权限时，可通过 `GET /api/v1/channels/api-keys/issue-with-receipt/result?request_id=...` 核对；204 不代表签发失败，回执不能恢复明文。事务内明确拒绝并回滚的业务错误返回 `CHANNEL_KEY_REJECTED`；其他错误不能单凭状态码判断原操作未发生，未确认时不能自动重发。

渠道令牌的可核对轮换使用 `POST /api/v1/channels/tokens/rotate-with-receipt`，提交 `request_id` 和 `channel_id`。令牌更新与不含明文的回执在同一事务提交，首次成功响应才返回令牌明文；重复请求只返回请求及渠道标识。原机构成员具备渠道读取权限时，可通过 `GET /api/v1/channels/tokens/rotate-with-receipt/result?request_id=...` 核对；204 不代表轮换失败，回执不能恢复明文。事务内明确拒绝并回滚的业务错误返回 `CHANNEL_TOKEN_REJECTED`；其他错误不能单凭状态码判断原操作未发生，未确认时不能自动重发。

渠道创建及可选智能体绑定使用 `POST /api/v1/channels/onboarding`，以 `request_id` 标识原操作；渠道、绑定与不含明文令牌的成功回执在同一事务中提交。原成员在具备渠道读取权限时可通过 `GET /api/v1/channels/onboarding/result?request_id=...` 只读核对，204 不代表创建失败。首次令牌只在首次成功响应中返回，回执不能恢复明文。已占用新请求身份后、事务内明确拒绝并回滚的业务错误返回 `CHANNEL_ONBOARDING_REJECTED`；其他 HTTP 错误或请求号冲突不能单凭状态码判断原操作未发生。

`PUT /api/v1/channels/agents {channel_id,payload:[{agent_id,priority,is_default,traffic_percentage}]}` 完整替换当前渠道的 Agent 路由集合，空数组清空集合。目标必须是本机构已发布 Agent，不能重复目标、配置多个默认 Agent 或使用范围外流量值。绑定服务锁定当前机构渠道行，在同一事务内校验目标、移除原集合并批量写入新集合；任何失败保留完整原集合，数据库默认与重复绑定唯一约束继续生效。解绑同样使用该渠道行锁。管理端添加绑定时必须保留最新现有集合的路由参数，再提交完整集合；该接口不再提供追加语义。

普通 Agent 的 `id` 是稳定身份，`(tenant_id, agent_key)` 唯一。`POST /api/v1/agents/revise {agent_id}` 打开同一身份的工作草稿；配置和能力挂载的修改不替换当前发布快照。发布在身份锁内追加不可变修订并更新当前发布指针，ChannelBinding、Session 和工作室继续绑定同一 Agent ID；下一主 Run 采用当前发布，进行中的 Run 与恢复使用原快照。`GET /api/v1/agents/revisions` 和 `/revisions/detail` 读取发布历史，`POST /api/v1/agents/restore-revision` 将指定历史内容恢复到工作草稿，仍需发布才生效。身份与快照归属见[数据模型](03-数据模型设计.md#43-普通-agent-身份与发布历史)。

`GET /api/v1/agents/detail` 的 Agent 详情返回 `icon_url`、独立运行预算摘要和 `delegation_config:{enabled,target_agent_ids}`；`PATCH /api/v1/agents/update` 可提交同一字段，省略表示不修改。普通 Agent 的定义、预算、委派和挂载修改进入工作草稿；状态更新独立生效，`disabled` 和 `archived` 限制执行，不能通过通用更新设置 `published`，曾发布身份也不能退回 `draft` 或直接删除。停用后恢复运行须重新通过发布校验和发布权限；`POST /api/v1/agents/publish-with-receipt` 保留原请求回执，无须先制造草稿修改。公共部署实例的定义由所属部署管理，普通发布接口拒绝覆盖。

Agent 列表、详情及更新结果以 `definition_managed` 表示定义是否由公共部署管理，依据服务端部署关系得出，不根据来源模板推断。机构页面仅为独立 Agent 提供停用和重新发布操作；停用只提交目标身份与状态，不附带或覆盖工作草稿。公共部署实例显示所属管理入口，不经过普通 Agent 的发布流程。

启用委派时目标必须是同租户当前已发布的 Agent；关闭时允许保留已有 `target_agent_ids`，不因旧目标已停用而阻止关闭；关闭状态下新增目标仍须通过同租户已发布校验。两种状态均要求目标为有效正整数 ID，且不能包含自身或重复项。授权 Agent 目录返回服务端裁剪后的同一结构，`target_agent_ids` 只含调用者当前可见且授权的目录交集；工作室成员快照只返回冻结的公开人设、能力摘要和同一运行预算配置，不复制 Agent 委派配置。Runtime 内部的 `AgentRunBinding`、target snapshot 与通用 `PlanCommand/DagPlan` 契约归 [Harness 08](../../harness-design/08-Agent委派与多智能体运行时.md)，不在对外 DTO 中复制。

机构配置页可在委派字段就地刷新可选 Agent，读取目录不会保存表单或移除已选目标；目录显示不替代发布和执行时的授权及状态校验。

知识摄取、批量同步和期望状态对账等异步 ControlOperation 的同步响应只确认受理和 operationId；查询结果必须展示当前状态、逐项成功/失败、最终资源引用和 retryable，不承诺跨服务长事务。普通 Agent 发布在本地事务完成后返回发布结果或原请求回执，不套用异步受理响应。

三方显式知识写入进入机构知识摄取、校验、审核和发布链。Agent Runtime 产生的 KnowledgeWriteProposal 仍只是候选，不能借 Open Platform 权限自动激活。

现有 Agent、Workflow、Knowledge、Channel、Connector、Billing 和平台运营端点继续由生成 OpenAPI 校验，但在依赖的 Runtime 主干有有效验收证据前只描述为现有基础或内部预览。开放平台、Builder 和 Marketplace 不提供 Skill execute、Tool invoke、Workflow run/resume 或 checkpoint 端点；业务交互只能进入 Session Runtime。目标 Runtime 接管后，旧恢复和直连能力端点直接删除。

### 5.1 平台模型、运营配置与运营查询

| API | 契约要求 |
| :--- | :--- |
| `/api/v1/admin/models` | 具备相应权限的平台主体读取、创建模型；模型详情固定使用 `GET /api/v1/admin/models/detail?id=MODEL_ID`，详情和列表只返回安全投影，密钥不回显，仅返回 `credential_configured`。`/update` 以请求体 `{id,payload}` CAS 更新模型；`/history?id=MODEL_ID` 读取不可变历史，`/rollback` 以请求体 `{id,payload}` 把目标 revision 复制为新 revision，`/providers`、`/discover` 和 `/test` 分别提供受控目录、发现与连接探测；`/test` 要求 `foundation.models.run`，可选传入 `id` 和模型配置 `payload`：不带 payload 时测试已保存草稿，带 payload 时测试当前输入，id 用于复用已有连接凭据。历史和探测响应都不回显明文或密文。 |
| `/api/v1/admin/system-settings` | 具备读取权限的平台主体读取注册分组；`/update`（请求体 `{group,payload}`）更新必须提交 `expectedRevision` 和完整 `values`，`/history?group=GROUP` 读取不可变历史，`/rollback`（请求体 `{group,payload}`）必须提交 `expectedRevision` 与 `targetRevision` 并追加新版本。CAS 冲突不得覆盖当前值，敏感字段不进入管理视图或历史响应。 |
| `/api/v1/settings/available-models` | 机构只读取已启用模型的选择摘要，包括引用、类型、模型名、能力摘要与 revision；响应不含 endpoint、Provider 连接、认证方式或凭据。 |
| `/api/v1/settings/model-selections` | 机构读取或保存 LLM、Embedding、Rerank 的平台模型引用；写入校验模型存在、已启用且类型匹配，不接受连接或凭据字段。 |
| `/api/v1/platform/audit/logs` | 平台审计查询支持 `action`、`tenantId`、`page`、`limit`、`actorId`、`resourceType`、`from` 和 `to` 查询参数；`from` 含边界、`to` 不含边界，时间范围必须满足 `from < to`。缺省页码为 1，缺省服务端条数为 50，条数归一化到 1–200；响应为 `{total,page,limit,items}`，按 `created_at DESC, id DESC` 返回。 |
| `/api/v1/marketplace/reviews` | 平台审核列表只使用 `/reviews` 路径；`status` 缺省为 `pending`、`search` 缺省为空、`page` 缺省为 1、`limit` 缺省为 20，响应为 `{total,page,limit,items}`。对外状态只有 `pending`、`approved`、`rejected`，`status=all` 表示不按状态过滤；`pending` 来自待审核模板，后两者来自已保存的审核决定。 |
| `/api/v1/marketplace/reviews/approve`、`/api/v1/marketplace/reviews/reject` | 两个决定端点都要求请求体中的 `workflow_id` 与 `expected_updated_at`；服务端锁定审核对象并校验其仍为 `review` 状态且时间戳未变化，竞争失败返回 409。驳回还要求非空 `reason`，长度为 1–1000 个 UTF-16 code unit；通过前执行安全扫描，驳回后回到 draft，通过后进入 published。不存在旧 `/workflows` 审核别名。 |

平台机构开通与账单状态扫描属于平台管理员管理 API。机构请求定义见 [CreateTenantRequest](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/dto/tenant/CreateTenantRequest.java)，入口见 [PlatformTenantController](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/controller/PlatformTenantController.java)。`POST /api/v1/admin/tenants` 接收 `{tenant_name,tenant_slug,plan_code?,admin_username,admin_password,admin_email?}`，成功返回 201 与 `TenantDetail`；`plan_code` 可省略并按服务端默认套餐解析，不能由客户端提交配额或密码哈希。名称最多 128 个、slug 最多 64 个、管理员用户名最多 128 个、邮箱最多 255 个 UTF-16 code unit；密码必须非空、至少 12 个 Unicode 码点，包含 ASCII 字母（`A-Z` 或 `a-z`）和数字（`0-9`），且 UTF-8 编码最多 72 bytes。名称、slug、用户名和邮箱在请求对象中去除首尾空白，密码保持原样，不 trim 或做 Unicode 规范化。400 的 `field_errors` 使用 snake_case 字段名和约束文案，不返回 `rejectedValue` 或密码内容；重复 slug 返回 409，数据库唯一约束负责并发创建裁定。

当前机构工作台使用[原请求回执](#24-管理写入回执的持久字段)创建和核对，不在查询不到结果后自动重发。旧无回执接口仍提供 `POST /api/v1/admin/tenants` 和按 slug 查找；查找只证明对象存在，不证明特定请求已成功或管理员账号已按原请求创建。创建与读取分别检查平台主体的当前 `foundation.tenants.create/read` 动作，成员治理传输正式角色数组，不接收旧单角色声明作为授权。

平台账单扫描由 [PlatformBillingController](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/controller/PlatformBillingController.java) 和 [PlatformBillingScanService](../../backend-java/skillforge-platform-service/src/main/java/com/skillforge/platform/billing/PlatformBillingScanService.java) 提供。`POST /api/v1/platform/billing/process-states` 执行扫描，请求体为 `{operation_id: UUID}`，操作者从平台登录主体取得，不能由请求体指定；检查平台主体当前 `foundation.billing.run`，回执读取检查 `foundation.billing.read`。扫描范围固定为状态为 `active` 或 `warning` 的机构，状态切换与回执在同一事务内完成，使用所见状态 CAS，不会把并发停用的机构重新激活或预警。响应为 `{operation_id,scanned,warning,active,completed_at}`，其中 `completed_at` 使用后端时间。

扫描结果查证使用 `GET /api/v1/platform/billing/result?operationId=…`；200 返回已提交回执，204 表示当前尚无已提交回执，不能据此推断请求未执行。服务端按“同一平台操作者 + 同一 operation_id”幂等；网络失败或结果未知时先查证，重试必须复用同一操作键，已完成对象不会再次处理。回执永久保留以阻止旧键重新执行；平台非租户表的 RLS 只允许平台策略访问。

平台模型更新、运营配置更新和回滚只改变当前指针并追加不可变 revision。Agent 的五项运行预算覆盖在 NewRun 时与平台 task_budget 场景根额度及代码角色比例统一装配并冻结，后续动作和恢复保持同一预算。所有新格式 Run 保存不可变准备 Profile 的精确引用与预算登记；后续动作和恢复不按当前代码策略或部署配置重新派生。已经发出的调用及其重试、结果处理和恢复读取原调用快照，不在中途换版本。配置变更不删除 UsageEvent 或重置累计用量。

运营配置历史条目显式返回必需的 `contract_status=SUPPORTED|RETIRED`。精确识别到已停用的旧知识11键契约时，列表保留原 revision、时间与 actor 元数据，`values={}`，客户端显示只读并禁止回滚；原数据库正文不删除。直接读取该旧修订正文或回滚返回 HTTP409、`knowledge_settings_revision_retired`、`retryable=false`，不访问新类型读取器恢复其执行。其他未知损坏保持严格失败，不统一转成 RETIRED；新知识9键来源与V317迁移见[数据模型](03-数据模型设计.md#35-模型运营配置与调用准备)。

模型价格 `inputPricePerMillionCents`、`outputPricePerMillionCents` 和 `pricePerQuantityCents` 在 Java 中使用 `BigDecimal`；JSON 只接受非负普通十进制字符串或 `null`，支持最多6位小数分，最大值仍为 `9223372036854775807`。JSON number、负数、科学计数法、前导零和超精度输入明确拒绝，不进行舍入；响应使用普通十进制字符串并去除无意义尾零。单位与持久精度见[计费数值契约](14-用量与账单设计.md#计费数值契约)。

### 5.2 Agent 模板发布、校验与安装

平台管理端使用 `POST /api/v1/platform/agent-definitions/validate` 校验请求体 `{definition_id,expected_revision}`，返回 `{valid,issues:[{path,code,message}]}`。校验至少覆盖模型必选、基础能力已发布且为公共版本、技能依赖完整、能力槽类型、委派槽定义和运行预算范围；草稿保存可以不完整，发布动作只接受可运行模板。模板正文包含系统提示词、公开角色说明、名称、头像、固定默认 LLM、`AgentExecutionConfig` 预算、公共 `SKILL` 与内置 `PLATFORM TOOL` 基础能力，以及可选 `resource_slots` 和 `delegation_slots`。

机构端使用 `GET /api/v1/agents/templates/detail?templateId=…` 查询模板详情和待绑定槽位。响应公开名称、头像、角色说明、固定模型摘要、预算摘要、基础能力摘要、`resource_slots` 与 `delegation_slots` 的键和约束，不返回系统提示词正文、凭据或平台内部连接信息。

机构端使用 `POST /api/v1/agents/install-template` 安装已发布模板，请求体为 `{template_id,name?,request_id,resource_bindings:[{slot_key,mount:CapabilityMountRequest}],delegation_bindings:[{slot_key,target_agent_id}]}`，返回 `{agent,mounts}`。`resource_bindings` 只允许当前租户已发布且有效的 `TOOL`、`WORKFLOW` 或 `KNOWLEDGE_SOURCE` 资源；跳过可选槽位不阻止基础对话。`delegation_bindings` 只允许绑定当前租户已有 Agent，不自动创建配套 Agent，不复制资源凭据。

安装事务原子创建 Agent、部署内置工具、写入能力挂载与委派绑定、启用 Agent、递增安装计数和保存幂等回执。相同 `request_id` 且参数相同返回原 Agent 与挂载；同一请求标识但参数不同返回冲突；实例删除后原请求不能重建实例。所有资源绑定必须通过当前租户、发布状态和有效性校验。

`GET /api/v1/agents/install-template/result?request_id=…` 仅读取当前机构的原安装账本，成功返回 `{request_id,agent_id}`，并要求当前主体具有 Agent 读取权限和该实例的资源读取权限；找不到记录或原实例已删除时返回 204。204 不能证明原请求失败，也不能作为重新安装的依据。查询不会创建或发布 Agent；继续原安装是单独的写操作，仍使用原请求标识和完整参数。安装事务内明确回滚的客户端拒绝使用 `AGENT_INSTALL_REJECTED`；普通 HTTP 状态和请求标识冲突不能证明原操作未发生。

产品流程中平台使用独立模板详情页完成编辑、校验和发布；机构在模板详情页选择名称和可选增强能力，安装成功并启用后进入该 Agent 的对话入口。可选增强能力也可以在安装后由机构能力管理页补充配置。

### 5.3 Workflow Builder 控制契约

Workflow Builder 复用版本化 Workflow 管理 API，不建立另一套可变“编辑器资源”。资源写入和审核分别由 [WorkflowAssetService](../../backend-java/skillforge-core-workflow/src/main/java/com/skillforge/core/workflow/WorkflowAssetService.java) 与 [WorkflowReviewService](../../backend-java/skillforge-core-workflow/src/main/java/com/skillforge/core/workflow/WorkflowReviewService.java) 在模板行锁下执行。控制契约至少区分以下操作，具体路径和字段由同版本 OpenAPI 定义：

| 操作 | 契约要求 |
| :--- | :--- |
| 创建容器/草稿 | 返回稳定 workflowId、draftId 与 revision；新建态不使用空 ID 或字符串哨兵代替资源身份 |
| 保存草稿 | 只允许修改 draft；请求携带 If-Match/revision，并与审核共用同一模板锁和当前状态检查；允许保存带 warning 或未解决 error 的草稿，但并发冲突不得静默覆盖，冲突返回后保留本地快照并重新读取当前 revision |
| 服务端校验 | 返回稳定问题 code、severity、对象引用、字段路径和可选修复提示；覆盖 schema、图结构、能力槽与策略 |
| 审阅差异 | 比较 draft revision 与指定 DefinitionVersion；布局/viewport 变化不混入运行定义差异 |
| 提交审核 | 只提交当前 draft revision；审核与保存使用同一模板锁，必须再次校验 revision、状态和校验结果；锁竞争或版本变化返回冲突，不创建第二个并行审核事实 |
| 审核决定 | 审核决定 API 使用 `workflow_id` 与 `expected_updated_at`；服务端在同一模板锁下确认仍是 `review` 状态，竞争失败返回 409；驳回需持久化理由，通过前执行安全扫描 |
| 发布 | 仅从通过校验且已完成允许流程的 draft 生成不可变 DefinitionVersion；已发布版本没有原地 PUT 语义，后续修改必须从已发布版本创建新 draft |
| 安装/升级 | 将已发布版本解析为 Workflow Instance 或 Agent Mount，并冻结能力槽绑定 |
| Builder snapshot | 保存关联 draft revision 的 layout/viewport；不修改 DefinitionVersion 或 Execution checkpoint |
| 测试 | 创建隔离测试 Session 并提交 Unified Inbound；结果通过 Session Outbox、TraceView 和 Execution 投影读取 |

节点目录和导入校验读取与服务端相同版本的 Workflow schema。ToolCallNode 与 KnowledgeQueryNode 只提交 requirement slot，不能提交 Connector 凭证、Provider URL、租户全局名称或任意共享服务引用。Builder 控制面没有 Tool invoke、Workflow run/resume、原始 dry-run 或 checkpoint 读取能力。

Builder 自动保存只能追加或更新当前 draft revision，并向用户呈现 saving、saved、failed、conflict；自动保存、提交审核和审核决定共享模板锁及版本竞争语义。自动保存 layout/viewport 进入 BuilderSnapshot，不能借局部保存更新已发布定义。测试运行产生独立 rootInputId、TraceContext、UsageEvent 和 Audit 记录，测试标记不豁免 PolicyChain、租户隔离或 ExternalInvocationGuard。

### 5.4 机构 Agent 保存并发布

机构配置页可以一次确认保存当前表单并发布，独立保存草稿与发布入口仍保留。命令只面向当前机构成员，不接入外部执行身份；保存并发布须同时具有 `foundation.agents.update/publish` 和目标 Agent 的管理、读取权限。发布的是本次表单配置及已经保存的挂载，不包含挂载抽屉中尚未提交的编辑；已接受的执行继续使用原冻结配置。

| 方法与路径 | 输入与结果 | 事务与恢复 |
| --- | --- | --- |
| `POST /api/v1/agents/save-and-publish` | `{agent_id, request_id, payload}`；请求 ID 为 UUID，payload 沿用更新字段且不接受 status；成功 data 为 `{request_id, agent_id, publication_id, revision, published_at}` | 原 Agent 行锁下先查原命令，再保存、校验和追加发布，一次提交；发布失败连同本次保存回滚 |
| `POST /api/v1/agents/publish-with-receipt` | `{agent_id, request_id}`；成功返回同样的五字段回执，只要求发布操作权及目标 Agent 管理、读取权限 | 原 Agent 行锁下先查原命令，再发布当前已保存草稿；不更新表单 |
| `GET /api/v1/agents/save-and-publish/result?agentId=...&requestId=...` | 当前 Agent 读权限及原操作者归属；有记录为 200 和原五字段回执，无可见已提交回执为 204 | 仅查询成功记录；204 不证明原事务失败或没有在途请求，不执行保存或发布 |

相同机构、Agent、请求 ID、原操作者、操作类型和参数重复 POST 返回原发布回执，不再次保存或切换当前发布指针；不同操作、参数或操作者返回 `409 AGENT_SAVE_PUBLISH_REQUEST_CONFLICT`。后续已有新发布时，原请求仍返回当时的发布 ID、修订及时间，不能用当前对象充当原回执。读取其他操作者的原回执返回 404；每次 POST 按对应操作重新检查当前权限，回执不产生执行授权。

页面派发时冻结请求身份和对应命令。网络失败或服务端结果未知时，页内保留原请求，提供“核对原操作”只读查询和“继续原操作”同键同参提交；不自动更换 ID。刷新后仅从会话存储恢复操作类型及请求身份，自动只读核对原回执，不恢复配置正文或自动重新提交。成功先保存原回执，后续详情刷新失败只重读。不把提示词、配置正文或凭据持久化到浏览器；离开未核对页面须明确确认。持久身份及保留归[数据模型](03-数据模型设计.md#33-租户表约束)和[清理规范](../04-指南与运维/11-数据清理与保留规范.md#21-postgresql-表登记)。

## 6. SSE 事件

### 6.1 线格式

持久业务事件使用 `id`、`event` 与单行 JSON `data`。`id` 取自 `data.event_id`，是稳定且不透明的事件标识，重放保留原 id；顺序由 `session_sequence` 表达并单调递增，客户端不得解析或按字符串比较 `id`。临时通知可以只有 `event` 和 `data`，不分配事件 id，也不参与 cursor。

### 6.2 传输事件

| event | 用途 |
| :--- | :--- |
| `connected` | 临时通知：连接建立 |
| `execution.accepted` | 持久事件：当前输入已绑定 `session_id`、`run_id`，用于精确取消；不表示开始或完成 |
| `message.delta` | 持久事件：当前消息正文累计快照，按消息版本原位更新 |
| `message.preview` | 持久展示事件：非权威正文候选累计安全快照，不进入消息历史或业务触发 |
| `message.card` | 持久事件：结构化卡片或任务摘要 |
| `message.card.update` | 持久事件：按 `message_id` 原位更新结构化卡片 |
| `hitl.required` | 持久事件：用户可交互的 Pending 投影 |
| `process.started` | 持久事件：当前 Run 的公开过程项已开始 |
| `process.delta` | 持久事件：过程项的公开状态或进度，不包含供应商私有推理正文 |
| `process.finished` | 持久事件：过程项已收敛到成功、失败、取消或结果未知；已校验模型结果的中途说明以 `type=commentary`、`presentation.summary` 公开 |
| `execution.completed` | 持久事件：当前 Run 的一次公开状态收敛为 `completed`、`failed`、`cancelled` 或 `waiting_hitl`，状态位于 `data.status` |
| `collaboration.updated` | 临时通知：协作快照已更新，不创建 Model Run |
| `error` | 临时通知：当前流无法继续，包含稳定错误码与是否可重试 |
| `replay.completed` | 临时通知：一次 `/chat/replay` 回放结束 |

当前传输实现不发布 `input.accepted`、`message.completed`、`execution.updated`、`session.closed`、`plan.*` 或独立的 `execution.queued|started|step|hitl|resumed|failed|loop_terminated|cancelled` 事件；未列入本表的名称不构成 v1 SSE 契约。连接每 15 秒发送一次 `heartbeat` SSE comment（只有 `:heartbeat`，没有 event、id、data 或业务序号），它不是事件，也不参与重放或确认。

持久完成事件的线格式示例（`event_id` 与 `session_sequence` 仅作不透明值示例）：

```text
event: execution.completed
id: output:<opaque-event-id>
data: {"session_id":"ses_…","event_id":"output:<opaque-event-id>","session_sequence":17,"input_id":"inp_…","root_input_id":"inp_…","caused_by_event_id":null,"event_version":1,"occurred_at":"2026-09-27T10:00:00+08:00","run_id":"run_…","status":"completed","runtime_event_id":"run_evt_…","durability":"persistent"}
```

### 6.3 执行事件投影

正文预览使用 `message.preview`，固定字段为 `preview_message_id/session_id/run_id/root_input_id/input_id/attempt_id/ordinal/preview_sequence/role/content/state/authoritative`，其中 `role=assistant`、`authoritative=false`。`content` 是同次真实 Provider 调用的累计安全前缀，按累计全文检查并保留跨块安全尾部；不含 reasoning、工具参数或未过滤原文。`state` 为 `streaming/rejected/unavailable/failed/unknown/cancelled`，后五者清除候选正文且不代表正式结果。事件身份为本 attempt 与递增预览序号，Outbox `session_sequence` 拥有重连与去重顺序；消费者按 Run、ordinal、attempt 选择当前候选，同 attempt 整体替换快照，新 attempt 整体替换旧候选，不拼接轮次。正式 `message.delta` 的消息身份及版本保持原值，新增 `preview_message_id` 关联应替换的候选；仅 `phase=final` 且 `state=completed` 的正式消息成为成功答复。`execution.completed` 同样携带该关联，关闭并清除该 Run 预览；消费者记录已终结 Run，忽略后续迟到预览，不能将断流或候选正文作为成功。预览持久化故障停止该调用的后续预览并记录脱敏诊断，真实模型仍连续消费、计量并保存原终态，禁止因此新增调用或清除 UNKNOWN。普通消息历史、模型上下文、成果发布及业务回调不得消费 `message.preview`。宿主按显式 `Duration` 与单调时间在当前模型回调线程合并预览，生产默认间隔 100ms：首个真实正文片段立即检查并发布（可以为空，以清除上一 attempt），后续到期才对累计全文执行同一安全检查并发布安全前缀；合并期间不公开未检查正文。真实模型成功返回后补一次尚未检查的安全前缀，仍保留安全尾部、`authoritative=false`，失败/UNKNOWN 清除及检测到的安全拒绝不受发布间隔限制。末次预览写入失败只停止预览并记录脱敏诊断，不能覆盖已取得的真实结果或触发重试。合并不创建线程、定时任务或队列，无新片段时不自行唤醒；正式终态仍沿原路径提交完整结果。该节奏减少高频分片的写入次数和累计快照字节，仍保留累计快照语义，不代表已消除全部存储放大。

正文消费保留流式到达语义：`message.delta.content` 是完整累计正文，按 `message_version` 合并，不追加重复文本；中途快照按浏览器帧合并，最终正文立即可见，不附加固定速度逐字播放。GET 重连使用有上限的指数退避、随机抖动和 `Retry-After`；收到业务事件或有效心跳后恢复初始退避。去重集合有界，权威 `session_sequence` 防止已淘汰旧事件回放覆盖当前状态。

页面刷新或重新进入会话后，先读取带 `event_cursor` 的历史快照，再从该游标持续观察 Session Outbox；恢复观察不重新提交用户输入。排队、运行和挂起状态继续跟踪，终态自动收敛；切换会话或离页释放观察，迟到响应不得覆盖新会话。分页与后台观察串行应用，避免旧分页覆盖较新的结果。

历史响应的 `closed` 表示当前 Session 已关闭，与单次 Run 的终态及 `history_retention.closed_at` 无关。服务端在已授权的历史读取中一并返回该状态，客户端不必额外查询会话详情。独立会话端读取到关闭状态后保留历史、会话切换和新建对话入口，禁用消息、补充、附件、引用及待办答复等写入；同一会话后续收到较早或迟到的未关闭快照，不恢复编辑。关闭状态随历史读取收敛，不依赖尚未发布的 `session.closed` 事件。

消息历史按 `before_message_id` 向前读取，每页 `messages` 按创建时间和消息 ID 正序排列；`has_more/next_before_message_id` 只描述该页之前是否还有消息。机构调试页在同一会话内发送、运行完成或恢复观察后读取最新页时，按 `message_id` 和最高 `message_version` 合入已加载消息，不以最新一页替换已展开的较早记录，也不重开已读完的旧分页；加载较早页前插去重并推进最早分页边界。旧分页仅补消息与分页位置，不回写当前待办、运行状态或最新事件游标。切换会话重新建立消息集合；当前授权、历史可用性与事件退休声明仍各按其契约生效，最新页未包含某条旧消息本身不是删除指令。

历史活动 `activities` 保留状态、卡片、render、`message_id` 和开始时间，不复制回答正文；公开正文由分页消息的 `messages[].content` 承载。活动关联和全部状态仍可用于恢复，不因删除冗余 `output` 字段而改变 Runtime 原输出、SSE 或 Outbox 正文。

执行事件类型与发布语义直接引用 [Harness 03](../../harness-design/03-核心对象模型与状态机.md#35-执行事件-executionevent01-fr-3-事件表--02-43-概念草案)。SSE 只传递受控摘要，产品任务清单从统一执行事实生成，不维护同义事件；节点快照、关系和记忆原文、凭证及未授权状态不进入传输投影。

聊天过程项以 `process_id` 稳定合并；身份、状态和排序字段包括 `session_id/root_run_id/root_input_id/run_id/input_id/actor_agent_id/actor_name/reference_id/type/sequence/ordinal/updated_sequence/status/started_at/finished_at/stage`，全部可读内容集中到明确的 `presentation`。`sequence` 固定首次位置，`ordinal` 排列同源条目，`updated_sequence` 表示来源更新顺序，均不替代 Outbox `session_sequence`。`presentation` 形状及公开边界见 §7；旧 `title/summary/detail` 不与新结构并存。`type` 为 `commentary/reasoning/skill/tool/workflow/memory/knowledge/delegation/public_validation`，状态为 `running/waiting/succeeded/failed/cancelled/outcome_unknown`。历史与在线增量共享同一投影，客户端只接受更新序号前进的内容；已知业务失败和结果未知不能被后到的 `action.succeeded`、根 Run 完成或取消覆盖。没有明确公开结果契约时只展示状态和稳定说明。

已采纳的工具结果若在标准结果封装中明确标记 `isError=true`，该工具过程显示失败；原调用的确定结果、模型反馈和后续执行保持不变。平台工具由各自的输出契约声明业务拒绝，不能从外部工具任意业务字段推断失败；未声明标记时不凭字段猜测状态。

一个根 `Run` 对应一个过程容器，公开 `commentary` 与执行记录按来源顺序交错展示；每个非终结模型决策或工具批次必须提供非空公开 `commentary`，用 1～2 句概述关注点、已确认结果或下一步，最多 600 个 Unicode 码点；不新增动作或模型轮次，`Respond` 与 `AskUser` 不携带 `commentary`。原生模型响应中的正文与工具调用继续保留；原生 assistant 正文独立于上述有界 commentary，不将长正文裁剪后当成执行摘要。结构化决策只接受显式 `commentary`。说明必须来自已校验并提交的模型结果，不能从 `reasoning_content` 或其他私有推理事实提取。公开投影使用 `process.finished`、`type=commentary`、`presentation.summary`，说明与模型状态不计入工具操作数量；实时、历史、补投和回放共享同一投影函数并按稳定身份去重。对应原生 assistant 段已承载的说明只按同一精确模型来源抑制重复 process commentary，不按文本相似度跨来源合并。

`stage` 为可空 `{id,index}`，由已验证冻结调用的 Run、Loop 与 iteration 生成，`index` 沿用从 1 开始的 iteration。同一模型阶段的摘要与工具调用共享阶段身份；Workflow 节点及其工具继续执行不伪装为 Agent 阶段。客户端只能按显式阶段归属组织过程，缺失阶段作为独立记录。业务工具标题取调用时冻结的 `discovery.title`，缺失使用准确通用名称，不从技术标识猜译。

等待状态不表示任务失败：30 秒无业务进展显示提示，60 秒只读核对当前已受理 Run；45 秒传输静默仅重连 GET，心跳续期传输但不续期业务进展。新 POST 等待回执期间不能采用上一轮终态解锁发送或取消上一轮，恢复观察不重发 POST。

模型调用过程保留 `reasoning` 类型及真实状态，但供应商 `ReasoningDelta`、`reasoningContent` 和 `reasoning_content` 属于内部续接事实，不进入实时 delta、历史 presentation 或公开 Trace 内容。持久化成功不构成公开授权；公开摘要不从私有推理首行截取，也不以敏感词或测试 canary 特判代替边界。Trace 隐去正文时明确标记内容可用性，内部 SessionLog、模型账本与协议续接仍保留原始事实。

`execution.completed.updated_sequence` 与历史 `activities.render.updated_sequence` 使用来源 SessionLog 序号，客户端据此合并根 Run 状态，拒绝迟到快照回退；外层 Outbox `session_sequence` 不参与这一比较。

最终 assistant 消息与历史元数据携带 `phase=final/state=completed`、`root_run_id` 和 `root_input_id`，正文从已完成 Run 的持久结果一次发布；原生工具参数和未采用模型文字不作为公开增量。只有运行状态 completed 且同轮最终答复就绪时，客户端才执行一次自动收起；用户手动展开后，重复事件和历史刷新不能再次收起。折叠只隐藏过程容器中的合法说明与步骤；等待、错误和需要用户操作的交互卡在过程容器外保持可见。

模型准备指令 `agent.preparation-instructions`、上下文快照 `agent.context-snapshot` 和上下文视图 `agent.context-view` 的完整正文同属内部模型上下文。公开 Trace 的 phase 与 content 均标记 `REDACTED`，仅返回脱敏原因；不公开拼接指令或各模块正文。独立诊断仍可返回版本、模块类型及计量元数据，受控验收通过内部只读证据通道读取原始事实。

历史 `event_cursor` 在当前访问授权完成后、读取消息和过程快照前获取，表示该时刻的已提交 Outbox 输出位置；不得在读取历史后再取游标而跳过并发新增输出。`GET /chat/events` 与回放直接读取已提交的冻结 Outbox 条目并推进观察游标，Web 输出不再维护额外领取、投递确认和重试状态。Webhook 的真实网络投递由独立 delivery 账本负责。历史与增量的重叠按 `event_id`、`message_version`、`process_id + updated_sequence` 去重。消息 `message_version` 独立于事件 schema version 和 Run revision：首次公开版本为 1；同 ID 的卡片、累计正文或正文终态变化才递增，重复同一来源不递增。

当前固定 Action 快照或 Runtime 事件格式不符合目标协议时，历史、成员详情和事件观察返回 HTTP 409、`CHAT_HISTORY_UNSUPPORTED`、`retryable=false`。公开正文只说明该历史无法读取并引导新建会话，不返回原始快照、内部身份或解析细节；技术故障仍按可重试错误处理，不能把所有参数异常视为永久历史错误。客户端只对 `EVENT_CURSOR_EXPIRED` 执行 GET history 恢复；收到永久历史错误立即停止观察，不循环 GET 或重发 POST。首次读取、手动重连和过期游标恢复统一消费 `503 + TASK_OUTPUT_PUBLICATION_PENDING` 的有界发布等待，最多五次 GET，等待可被取消或会话切换打断；仅成功取得所属会话的历史后采用新游标。普通 503、其他错误码或身份拒绝不进入该等待，不扩大 POST 重试资格。

Outbox 公开投影的成功检查点保存在 `nw_chat_session_outbox_sequences`：来源 sequence/event、政策版本及尚需跨批恢复的公开过程与活动正文状态，与该批 Outbox 输出原子提交。Run 收口后移除活动正文检查点，历史仍从不可变来源恢复。受理输出按完整 SessionOwner、Run 与 input 定位首个不可变 SessionLog 来源，始终复用其 eventId 和 trace 派生同一 Outbox 身份；跨批、迟到诊断和政策重建不重复形成受理事件，检查点不累积全部历史受理键。相同成功来源直接返回；新来源只扫描成功水位之后的事件，不能丢失待结束过程或已知失败。拒绝回执独立于成功检查点，失败批次回滚不推进成功游标；重启从检查点继续，政策变化按原始来源重建。最新来源使用完整 SessionOwner 内的倒序索引读取，首源使用 owner/Run/input/sequence 索引，不全量扫描以寻找水位或受理来源。

活跃跟随按页复用已读 SessionLog 来源：页尾限定本次投影上界，锁后权威 checkpoint 决定重叠裁剪、政策重建与缺口补读。实际来源只准备一次，同时用于输出与目标 Run 最新边界判断；投影事务返回后才推进本跟随者游标，不能因其他跟随者水位更远而跳过未观察的 Run 状态。已有页被覆盖时仍判断该页的目标 Run 边界，resumed/running 清除先前 suspension。此路径不把历史或模型输入材料读取改为后台异步。

公开投影在原事务与序号锁内收集有序、类型化的输出命令，按 eventId 一次识别已存在条目，只为新增项一次预留连续序号并批量写入 Outbox、Webhook delivery 和投影检查点；任何失败整体回滚。普通单条输出使用同一批写入口。全部重放返回原行和原 createdAt，不重新建立投递责任；活跃 Webhook 订阅只为本批新增项读取一次。收集阶段不产生持久回执，首条输出时间等诊断使用事务提交后的真实回执。

Outbox 公开投影复用 `nw_chat_session_outbox_sequences` 的序号锁行，保存原 SessionLog 最高 sequence、水位 event identity、当前投影与公开检查政策版本及精确格式拒绝原因。失败投影事务先回滚，再独立提交永久拒绝；同一来源及政策的拒绝不重复投影或告警，来源或政策改变后重新判断。较旧回执不能覆盖较新水位，同来源已成功的回执不能被迟到失败覆盖。此记录不占传输序号，不改变已提交输出游标、Run/Goal 状态或原历史事实，也不提供旧格式兼容读取。

工具的确定业务结果优先于后到的 Action 成功确认：后者可以推进来源水位，不能覆盖已有 summary、结果、引用与 finishedAt，或重复发布相同 `process.finished`。失败、取消和结果未知收敛为已知仍产生实际更新。过程事件可带可选 `changes`：`artifacts=true` 仅表示成果工具结果已 ready 且成果非空；`team_work=true` 仅来自已受理的委派 start/send 或 cancel_requested，读取 targets/list/get/wait 与拒绝结果不声明变化。非空 changes 即使 presentation 不变也发布；来源和 eventId 幂等仍成立。

通用计划沿用 `/chat/work`、`/chat/work/history`、`/chat/work/tasks/detail`、`/chat/work/controls`。公开快照包含 `input_id/run_id`、工作修订、计划及批准版本、PRIMARY/MEMBER 执行者、依赖、步骤状态、等待原因和结果引用；会话历史携带对应消息页的计划快照。用户补充、批准和取消显式携带 `work_id`，步骤补充同时携带 `task_id`，详情和成果按当前授权读取。

DAG 更新先与工作事实一起持久写入 SessionLog 的 `work.updated`，再由公共事件投影发布可回放通知。公共通知只携带计划身份与修订信息，客户端重新读取授权快照；它不能以包含私有完整 DagWork 的源事件直接替代公开 DTO。客户端分别比较工作/计划及主 Run 的修订，合并重复刷新，取消切换会话后的旧请求，用户选中的历史计划不被最新计划推送替换。成员全部结束不等于整项工作完成，最终收敛仍包含主 Agent 的答复事实。


机构端与会话端按明确变化刷新成果或协作数据，首次进入、重连及必要终态保留补齐；每个资源最多一个在途读取，期间通知合并为一次后续读取。切换会话或卸载中止原读取并使用代次守卫，旧响应及旧 finally 不能更新或清除新会话请求。

SSE/回放入口一次验证不透明事件 cursor 的租户与 Session 归属，再以服务端实际已发送的 sequence 连续读取和推进；对外不接受裸 sequence 替代事件身份。在线循环继续复核当前 Session 授权，撤权后停止观察。

实时链路按已持久提交的过程与结果事件发送：SSE 响应禁用缓存和内容转换，服务端与已启用代理关闭缓冲。Native 最终正文在完整模型响应及本地门禁通过后发布，不能将参数分片提前标作最终答复；过程事件不应为等待正文而滞留。传输正确性在实际消费边界验证，不能用 text/event-stream 或心跳代替事件到达证据。

### 6.4 流生命周期

前端先用本轮 `execution.accepted` 的 `run_id` 与 `input_id` 绑定目标 Run；绑定后只消费同一 `run_id` 的后续事件。Runtime 终态事件的固定因果 `input_id` 可能不是本轮提交的 input，不能因终态事件的 `input_id` 与本轮不相同而丢弃目标 Run。目标 Run 到达明确终态后只停止本次前端订阅。服务器侧 Session 订阅保持到 Session 关闭或订阅超时，不能因某个 Run 终态关闭 Session 或丢弃其他活动 Execution 的输出。

- 普通回复：目标 Run 的终态事件到达后，前端结束本次观察；终态事件的因果 input 不必等于本轮提交的 input。
- 前台执行：可发送执行摘要与消息；前端在目标终态后结束本次观察，服务器订阅继续保持。
- 挂起：发送 Pending 投影后结束当前请求；恢复由新的 Inbound 驱动，不长期占用请求事务。
- 后台执行：初始请求返回已接纳状态，完成通知经 Outbox 进入后续输出。
- 断线重连：客户端发送 Last-Event-ID，服务端从持久输出或缓存投影重放；客户端按 id 去重。

### 6.5 SSE、Webhook 与 Cursor Pull 一致性

三种传输读取同一持久事件 schema 和 Outbox：SSE 面向在线增量，Webhook 面向异步通知，cursor pull 面向断线恢复与对账。持久 Session 事件保留 `event`、`event_id`、`session_id`、`session_sequence`、`input_id`、`root_input_id`、`caused_by_event_id`、`event_version`、`occurred_at` 和 `data`；其中 `event_id` 是稳定不透明的 Outbox 标识，`session_sequence` 由权威 Session Outbox 生成并用于顺序。完成事件使用 `event: execution.completed`，状态等业务字段位于 `data`。`data` 在存在 Runtime 过程来源时可带 `runtime_event_id` 和公开过程项的 `sequence`，不能假定每条事件都有这些字段，也不能发明 `runtime_sequence`。传输适配器不得改变顺序、内容引用或完成状态。

当前 `POST /api/v1/messages` 的主动消息路径先写消息记录和 Session Outbox，并返回 `queued`，不把进程内 SSE 连接是否在线当作送达确认。`connected`、`error` 和 `collaboration.updated` 是临时传输通知，不写入 Outbox 序号；普通消息、HITL、执行与完成事件写入同一 Outbox。`GET /api/v1/chat/events` 与 `GET /api/v1/chat/replay` 只按连续 cursor 读取冻结事件，不领取、不确认，也不重新执行输入；在线订阅按自身 cursor 持续读取，客户端离线时用同一 cursor 重放恢复。出站 Webhook 与对外 cursor pull API 仍以 [相关设计](../../harness-design/README.md) 为准，不能据此把所有渠道交互能力视为已完成。

## 7. 渲染契约

渲染数据表达语义，不表达某个前端框架的组件实现。

图片及图文消息的目标投影保留有序内容和受管媒体引用，纯图消息即使文本为空也必须在实时、历史和重放中可见。客户端按图片项显示受权材料，不用空文本过滤消息，也不把原始文件路径、长期外部 URL 或 Base64 正文当图片身份。图片获取沿用当前个人归属，模型消费、内容冻结和恢复语义归[多模态专题](../../harness-design/03-多模态内容与媒体引用.md)；浏览器任务面板的截图投影复用这一机制。

| 类型 | 最小内容 |
| :--- | :--- |
| 文本 | messageId、content |
| 卡片 | cardId、type、content、actions |
| Pending | executionId、提示、允许动作、到期时间 |
| 任务摘要 | executionId、mode、status、summary |
| 错误提示 | errorCode、message、retryable |

过程可读内容使用 `ProcessPresentation{title,summary,results,references}`。`results` 是封闭联合：`{kind:"text",format:"plain"|"markdown",text}`，或 `{kind:"table",columns:[{key,label}],rows:[(string|number|boolean|null)[]]}`；行宽必须匹配列数。`references` 为 `ChatReferenceView` 列表，展示 label 与结构化选择器分离。工具拥有者显式提供 `public_presentation` 才能产生业务结果块；未知工具、内部 schema 或原始返回 JSON 不产生兜底展示。面向技术工作的代码和业务 API 字段可按任务需要公开，不能按 `id` 字段名或 UUID 外形清洗业务资料。

公开正文、结果块、材料 label、成员名称、Pending question、卡片 title/plan/message，以及表单 schema 的 label/description/enum 展示值，针对宿主已知私有路径、明确标记的敏感内容及[明确凭据格式](12-代码执行沙箱与产物交付.md#52-元数据与原子发布)执行公开检查。普通 Run/Action/event/schema/工具名称和非授权型文件标识不因身份类型被拒绝，也不把普通 password/token 字段讨论或 UUID 形状当作秘密；明确凭据赋值仍按所属格式检查。受管凭证、授权票据、结构化敏感字段脱敏及私有推理边界继续由所属来源保护。公开检查不扫描会话历史来收集普通标识。结构化 selector、resume 与因果身份保留程序用途。命中时固定显示“内容未通过公开检查，本次交付未完成。”，不回显命中的值；Runtime 的 `PUBLIC_OUTPUT_REJECTED` 是交付失败，不能通过额外模型重试掩盖。原私有证据保留，SSE、历史与重放独立复核公开边界。

公开 assistant 文本投影携带上述 phase 和根归属；只有 `phase=final` 的已完成段且所属 Run 真正 completed 才属于最终答复，pending 与 commentary 段保持独立公开消息，过程条目不得伪装成最终消息。等待确认、补充输入和错误恢复所需的交互卡属于独立 Pending/错误投影，即使过程容器折叠也保持可见。

独立会话端将用户消息、公开工作摘要、过程和最终答复按来源顺序组成时间线；过程仅在明确完成且同轮最终答复就绪后自动折叠一次，用户仍可展开。运行中补充通过 `/chat/runs/steer` 提交，输入区独立保留下一条消息草稿，消费状态以 `/chat/runs/steering` 的回执为准。成果卡按 `run_id/result_run_ids` 关联对应运行，固定版本引用与预览票据沿用成果接口；浏览器设备属于当前授权用户，其全局管理入口不依赖当前选中的会话。

独立会话端支持经公开检查的 Markdown 正文中的受控图形围栏，不扩展 `ProcessPresentation.results` 的封闭联合。只有完整、顶层的 `mermaid` / `chart` 围栏且源码不超过20,000个 JavaScript 字符时才尝试渲染；未闭合、无效、超限或不支持的内容保留为源码。普通 Markdown 仍进行 HTML 净化，不允许任意 HTML 成为交互组件。

展示形式由 Agent 根据用户意图与证据选择，属于按需的智能 UI 能力，不是每次答复必须填满的模板。简单问答优先自然段，事项或步骤才用列表，比较可用表格，量化数据才考虑图表，步骤关系或条件分支才考虑流程图；用户明确指定的格式优先。前端只按已准入的语义内容渲染，不根据关键词自行把文字改成图形，不为了展示组件重复正文或编造数据。

- `mermaid`：本轮仅支持 `graph/flowchart`，方向为 `TD/TB/BT/LR/RL`，最多200条边。使用本地锁定依赖、严格安全模式和 SVG 净化，拒绝配置指令、frontmatter、HTML、点击动作、样式及外部资源语法；渲染失败保留源码。
- `chart`：封闭 JSON 对象 `{type:"bar",title?,unit?,max?,items:[{label,value}]}`。`items` 为1至12项；`label` 为非空字符串、最多120字符，`value` 为0至10^12的有限数值。可选 `title` 最多160字符、`unit` 最多12字符，提供时须非空；`max` 为大于0且不超过10^12的有限数值，不能小于任何 `value`。未知字段不渲染。缺省 `max` 时按最大值确定刻度，全零时刻度为1；百分比使用 `unit:"%",max:100`，正文须说明统计口径，不能从文字推测数值。

上述展示动画由真实公开事件驱动。Native Agent 的完整正常正文在[Runtime 最终答复检查](../../harness-design/03-核心对象模型与状态机.md#561-headless-模型准备与提交协议)通过后，与可信引用元数据及 Run 终态一起提交，再公开为最终消息；模型侧没有终结工具，内部 Respond、完成事件和 final 阶段继续保留。正文伴随工具调用时只是本次 assistant 消息的一部分，客户端不得提前当作已完成答复，也不得把私有推理、原始候选或工具参数增量当作最终答复。首批协议替换不公开暂存正文，不将完整正文拆成计时模拟流式输出；后续流式体验须明确生成中、已提交与中断。富内容沿用完整围栏和既有渲染规则，正文引用只按已提交可信映射呈现，公共 citations 中的 `citation_id` 绑定正文的本地引用入口，客户端不按字符串重新推断来源；缺少新必需引用身份的旧平台完成事件明确拒绝。

同一个语义对象的直播与回放必须使用同一投影函数。客户端忽略未知展示字段，但服务端在预发布阶段可以删除错误语义字段，并同步更新客户端和 OpenAPI。

## 8. 幂等

Runtime 幂等层次、请求指纹、恢复竞争和外部副作用边界直接引用 [Harness 03](../../harness-design/03-核心对象模型与状态机.md#9-幂等体系)，SDK 请求身份见 [Harness 03](../../harness-design/03-核心对象模型与状态机.md#75-agent-runtime-sdk-façade)。传输适配器保留调用方稳定请求标识；同键异体、重复受理和竞争结果按下节映射，不能因换用 SSE、同步或 Webhook 产生另一套业务键。

Open Platform 的内部输入身份由完整可信命名空间和外部幂等键派生，`open-platform:` 加 SHA-256 十六进制摘要共78字符；该身份继续用于 Runtime input、Run、trace 和受理回执。转换为 `ChatRequest` 时，公开归档消息标识 `client_message_id` 单独按 `sha256("open-platform.public-message.v1\n" + input_id)` 派生为64字符。`context.input_id` 保留原内部身份，重复提交、只读回执核对和冷重建使用同一派生关系；公开消息容量限制不能改变原幂等输入身份，也不能放宽64字符归档契约。

## 9. 错误语义

通用状态分类与字段校验见[工程规范](../../.agents/skills/nw-engineering/references/engineering-standards.md#响应与错误分类)，重试须同时满足[副作用与预算要求](../../.agents/skills/nw-engineering/references/engineering-standards.md#外部调用超时与重试)。以下说明领域行为；业务处理结果与传输错误不混用。

| 类别 | 行为 |
| :--- | :--- |
| 身份或租户不匹配 | 拒绝并记录安全审计 |
| 输入重复 | 返回处理中或已有结果 |
| 状态竞争 | 返回当前状态，不重复恢复或取消 |
| 能力不可见 | 拒绝，不回退到全局搜索 |
| 能力类型或版本不匹配 | 拒绝，不按显示名称、旧字段或自由 Map 猜测目标 |
| ServicePrincipal scope 不足 | 拒绝并写安全审计，不根据正文角色或 tenantId 降级授权 |
| 资源 revision 冲突 | 返回当前 revision 与稳定冲突，不覆盖已发布版本 |
| ControlOperation 部分失败 | 返回逐项结果和可重试项，不把部分成功伪装成事务回滚 |
| 契约校验失败 | 不进入执行层 |
| 技术故障 | 保留 traceId 与原因链，按 retryable 指示调用方 |
| 配额耗尽 | C 端使用友好卡片；管理 API/OpenAPI 使用稳定 429 契约 |

错误码字面量必须来自实现中的统一错误枚举，禁止在文档中臆造。

可信渠道认证的聊天请求在月度配额耗尽时仍返回 HTTP 200，使用通用成功 envelope，在 `data.status` 中明确返回 `quota_exhausted`，并在 `data.card` 中返回 `{type:"info",code:"MONTHLY_QUOTA_EXHAUSTED",title,body,resets_at,retry_after_seconds}`。`resets_at` 为服务端计算的下一个北京时间月初，`retry_after_seconds` 为距离该时刻的秒数。该响应表示业务未受理，不创建 Run 或 input，`execution_id` 与 `input_id` 均为空。JWT 或 OpenAPI 请求返回 HTTP 429 及通用失败 envelope，响应头 `Retry-After` 为距离下一个北京时间月初的秒数。实现见 [ChatController](../../backend-java/skillforge-institution-service/src/main/java/com/skillforge/institution/controller/ChatController.java) 与 [QuotaExceededException](../../backend-java/skillforge-core-billing/src/main/java/com/skillforge/core/billing/quota/QuotaExceededException.java)。

## 10. 开放平台轨迹与费用

会话交互使用 TraceContext，以 rootInputId 查询问题到结果；资源发布、知识摄取和批量同步使用 ControlOperationContext，以 rootOperationId 查询操作时间线。ExternalInvocation 与 UsageEvent 通过 InvocationContext 关联其中一种，所有产生 Embedding、Rerank、模型或连接器费用的控制操作也必须经过 ExternalInvocationGuard。

开放平台可以按授权查询 integration、resource、controlOperation、Agent、Session、provider/model/service 和时间范围的用量；unknown、unpriced、unresolved 和不同未转换币种必须分别展示，不能并入已确认总额。

目标接口按平台有权机构集合及机构固定 Tenant/integration 读取同一平台发布流；现有应用 `GET /api/v1/integration/usage/events` 及其 summary/detail 属于待移除路由，不作为新接口继续代理。新固定路径、scope、游标 schema 和 SDK 以[GI-00 公开协议基线](#27-多机构接入公开协议基线目标)为准，由 GI-14 同步实现和生成物，技术方案见[相关设计](01-技术架构.md)。

增量事件保留稳定身份、真实来源、单位/数量、金额状态及确认/调整引用，发布水位独立于源时间和主键。筛选返回扫描位置，空匹配页可推进；游标绑定主体、授权和筛选范围，授权变化需明确重建，不能用旧水位跳过新获准机构历史。平台与机构视图不重复生成费用事件，消费者按稳定事件/attempt 及可靠结算指令幂等，成本修订不自动新增客户扣款。供应商中间、委派、最终回答及后台辅助实际调用均计量，unknown 保持显式未知，细则见[用量设计](14-用量与账单设计.md)。

## 11. 预发布演进规则

- 不保留旧 API 薄适配、旧 DTO 转换、legacy/new 路由开关或双事件名。
- 破坏性变更必须在同一发布单元更新 OpenAPI、客户端、测试和迁移。
- 真实外部调用方需要迁移时，先明确一次性迁移窗口；不因此把旧语义保留在 Runtime。
- 协议变更的 Note 触发与复用按 [Note 治理规范](../../.agents/skills/nw-docs/references/notes-governance.md#4-note-触发与复用)，请求/响应验证按[评审与验证规范](../../.agents/skills/nw-verification/references/candidate-driven-delivery.md)选择实际受影响的边界。

### 外部业务背景归档

`POST /api/v1/open-platform/sessions/context-messages` 仅归档后续模型可读取的外部背景。请求为 `{ "session_id": "...", "source_message_id": "稳定业务消息ID", "question": "", "answer": "已记录业务结果" }`；会话和来源ID最多256字符，question/answer各最多65536字符，至少一侧非空。来源ID命名空间包含当前Tenant、integration、Session与context-message操作类别，同来源同内容返回原message_id及replayed=true，异内容409。每次请求均复验当前sessions.write和会话归属，测试、关闭及群会话拒绝。

归档只追加一条固定user角色的外部背景记录，正文及metadata明确source/context_only，question/answer整体保留，禁止客户端指定角色或执行身份。背景不是当前请求、不授予工具执行权限、不证明平台执行成功，不启动或恢复Run，不写Outbox、计费或业务外发。响应为message_id、recorded、replayed，不包含run_id。仅后续新受理Run首次冻结历史时读取，既有Run的冻结输入与恢复保持不变；需要下一轮确定可见时应先等待归档成功。原业务消息由业务系统展示，该入口不向SSE或开放平台历史伪造正式助手结果。
