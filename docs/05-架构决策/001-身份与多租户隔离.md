# ADR-001：身份与多租户隔离

- **状态**：Accepted（2026-08-04 修订）
- **日期**：2026-08-03
- **决策者**：架构组
- **关联**：数据模型设计、非功能需求、技术栈与风险评估

## 背景

原方案依赖外部身份服务和共享身份域。当前采用应用内身份；基础设施和运行角色按[开发与部署指南](../04-指南与运维/01-开发与部署指南.md)配置。

## 决策

**默认采用应用内 JWT + 租户成员 RBAC：**

| 场景 | 方案 |
| :--- | :--- |
| **默认（绝大多数租户）** | 服务端 [ScopedJwtLogic](../../backend-java/skillforge-core-foundation/src/main/java/com/skillforge/core/foundation/security/ScopedJwtLogic.java) 签发并验证 access JWT；登录身份使用 Sa-Token 的登录 ID，机构认证由 [AuthService](../../backend-java/skillforge-core-foundation/src/main/java/com/skillforge/core/foundation/application/AuthService.java) 委托安全服务处理，验证 `iss`、`aud`、标准 `exp` 及服务端登录状态。refresh token 的随机部分由 32 字节 `SecureRandom` 生成并编码为 URL-safe Base64，不是 JWT。 |
| **企业强隔离** | 可选专属部署（On-Prem / Hybrid）；身份仍由应用内账号体系管理 |
| **平台内部员工** | 独立 `nw_platform_members` 账号体系（2026-08-05 起），与客户租户隔离 |

## 平台运营账号体系（2026-08-05 修订）

平台运营后台与机构管理后台不再共用同一账号体系：

- 平台运营账号独立存储于 `nw_platform_members` 表（无 `tenant_id`，不启用租户 RLS），
  登录接口为 `/api/v1/platform/auth/login|refresh|me`，不再要求 `tenant_slug`。
- 平台服务使用独立 `token-name`（`X-Platform-Token`）、签名密钥（`PLATFORM_SECRET_KEY`）与 issuer/audience；机构普通入口不接受平台令牌。机构服务的[指定平台管理入口](../../backend-java/skillforge-core-foundation/src/main/java/com/skillforge/core/foundation/integration/ManagementActions.java)是显式例外：验证平台令牌的签名、issuer、audience、有效期及安全会话后，还须检查对应管理权限与目标范围，不能将其视为机构成员令牌。
- 平台运营后台通过 `/api/v1/admin/tenants` 承担机构账号全生命周期管理：
  创建机构与初始管理员、成员增查改、停用/启用、重置密码、机构停用/启用；
  机构自助注册 `/api/v1/auth/register` 已关闭。
- 平台服务使用独立数据库角色 `skillforge_platform`（`BYPASSRLS`）执行跨租户读取；
  本地 Compose 中机构服务使用 `skillforge_institution` 并依赖 RLS 保持租户隔离，`skillforge` 是迁移所有者；实际部署角色由环境配置。平台侧写入租户表前，
  先绑定目标租户上下文（`TenantContext.setTenantId`）复用既有 RLS 策略。

**应用数据隔离由以下三层强制：**

1. PostgreSQL RLS + 请求事务 `SET LOCAL app.tenant_id`
2. Redis key 命名空间 `{tenant_id}:...`
3. 向量 / Elasticsearch 检索强制 `tenant_id` 过滤

access JWT 由 `ScopedJwtLogic` 负责签名和验证；验证除签名外必须核对 `iss`、`aud`、标准 `exp` 与服务端登录状态。refresh token 按当前轮换与撤销流程处理：机构端使用 `<tenant_id>.<随机部分>`，平台端使用 `platform.<随机部分>`；前缀用于定位身份作用域，不能单独作为认证凭据。明文只在签发响应中返回；服务端以 `nw_foundation_security_sessions.refresh_hash` 查找并以 CAS 轮换，刷新时仍核对会话及成员状态。Redis 用于尝试限流，不是刷新摘要的权威存储。客户端将 refresh 作为完整凭据保存与回传，不解析为 JWT 或据此前缀授予权限。

**C 端终端身份**按「租户 + 渠道作用域」建模，**禁止**全局 `wechat_openid` 唯一约束。管理 API **禁止**仅凭裸 `X-Tenant-ID` 鉴权；开发态可有明确开关，生产关闭。

## 后果

- 任务 2.11.x 改为「内置身份与 JWT 验签」，不再部署 Keycloak。
- Token 必须校验签名、issuer、audience、标准 exp 和服务端登录状态；refresh token 轮换与撤销沿用 `AuthService`。
- 渠道访问使用 `X-Channel-Token`（哈希入库，明文仅创建时返回一次）。

## 不做的事

- 不自研 OAuth 联盟协议全集；需要时可对接外部 IdP 作为后续扩展。
- 不把 JWT claim 当作数据隔离的唯一手段。
